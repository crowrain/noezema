## 1. Семантика `as_of` по спецификации

### 1.1 Что говорит ARCHITECTURE.md

Текстового определения «что означает `as_of`» в `ARCHITECTURE.md` **нет**:
поле фигурирует только как поле claim'а и как вход расчёта срока:

- §8.2 (`ARCHITECTURE.md:1068–1088`) — поля семантического claim'а:
 `valid_from` (1078), `valid_to: nullable` (1079), `as_of` (1080),
 `observed_at` (1081), `reverify_after` (1082);
- §8.6 (`ARCHITECTURE.md:1121`): «Reverify deadline выводится из claim type,
 volatility, `as_of` и valid interval. `valid_to=NULL` означает неизвестный
 конец действия» (T3.7: «Freshness: reverify_after из
 claim type/volatility/as_of; истечение меняет только freshness_status»,
 `docs/PLAN_FROM_SCRATCH.md:320`);
- §8.7 (`ARCHITECTURE.md:1161`) — правило claim type задаёт «volatility и
 расчёт `reverify_after`»; (`ARCHITECTURE.md:1173`): «temporal_fact E3:
 external_fact rule + **обязательные as_of и temporal scope**»;
- §14 (`ARCHITECTURE.md:1900`) — таблица `claims`: `valid_from, valid_to,
 as_of, observed_at, reverify_after`;
- §22.2 (`ARCHITECTURE.md:2607`) — гейт: «due/stale time-sensitive claims
 <20%».

Т.е. спека фиксирует **роль** `as_of` (базовая дата reverify-deadline вместе
с volatility), но не даёт семантического определения «что это за дата».
Определение даёт ADR-0007.

### 1.2 Что говорят ADR (действующее определение)

- ADR-0007:44–52: claim scope выводится хостом из «ВОПРОСА сессии +
 типизированного `as_of` claim»: «`as_of`: **дата, названная в вопросе**
 (детерминированный закрытый набор форм: …). **Дата вопроса ПЕРВИЧНА**:
 модельный `as_of` не может сдвинуть опорную дату (иначе due/stale-механика
 §22.2 — `reverify_after = as_of + 30d` — управлялась бы моделью). Вопрос
 без даты → типизированный `as_of` claim (валидированная структура, не
 free-form)».
- ADR-0007:163–171 (уточнение T7.18): «Для относительных форм опорная дата =
 **дата сессии по доверенным часам хоста (UTC)**, а не `as_of` модели».
- ADR-0007:172–175: «Модельный `as_of` не сдвигает опорную дату ни вперёд,
 ни назад, когда вопрос несёт дату-якорь (явную или относительную); он
 сохраняется только в строке claim и в staging/audit».
- ADR-0007:200–201: «Базовая дата due/stale (`reverify_after = as_of + 30d`,
 §22.2) **не меняется** — по-прежнему от типизированного `as_of` claim».

**Действующее определение (одной фразой)**: `as_of` — типизированное поле
claim'а, базовая дата due/stale-механики; его надлежащее значение —
**опорная дата вопроса** (явная дата вопроса; для «на текущую дату» — дата
сессии по часам хоста, T7.18; для вопроса без даты — сам типизированный
`as_of` как fallback). «Дата наблюдения источником» и «дата события» в
спеке/ADR как значения `as_of` **не предусмотрены** — это то, что модель
фактически пишет (артефакт).

### 1.3 Конкретный вопрос: источник «по состоянию на 15.06.2026», вопрос
«на текущую дату» задан 21.09

- **Какой `as_of` правилен по спеке**: опорная дата = дата сессии
 (2026-09-21): ADR-0007:163–171 (относительная форма → дата сессии) +
 «дата вопроса ПЕРВИЧНА» (ADR-0007:48–49). Дата из текста источника
 (15.06.2026) — свойство контента источника; отдельно система её не
 моделирует: evidence scope получает время **наблюдения** = `retrieved_at`
 источника (хост-деривация, `packages/memory/scope.py:245–263`), а корпус-
 конвенция — «источник, полученный не раньше D, — лучшее доступное
 свидетельство о состоянии на D» (ADR-0007:64–71).
- **Корректно ли считать такой claim просроченным**: механизм работает
 честно — `due` есть свойство `(reverify_after, now)`, а `reverify_after`
 выводится из записанного в claim `as_of` (§8.6:1121; T7.27/ADR-0014).
 Но по существу это **модельный артефакт, а не честный сигнал «данные
 источника старые»**: источник получен в день сессии (свежий), claim
 отвечает на вопрос «на текущую дату»; срок истёк только потому, что
 модель записала в `as_of` дату, отличную от опорной. Обратная сторона,
 которую фиксирует разбор: при надлежащем `as_of` (дата сессии) такой
 claim был бы `fresh` — **хотя контент источника на 3 месяца старее**.
 Т.е. в рамках конвенции корпуса ADR-0007:64–71 механизм freshness вообще не
 отслеживает «возраст контента источника» (только расписание перевалидации
 от `as_of`) — «честный сигнал «данные источника старые»» в текущей спеке
 не существует ни при каком варианте `as_of`.

## 2. Откуда берётся значение: путь «вывод модели → `claims.as_of` → `reverify_after`»

1. **Схема** `packages/domain/schemas/staging.py:56` —
 `ClaimProposal.as_of: datetime | None`; хост-валидация
 `validate_against` (`staging.py:96–98`) проверяет **только наличие**
 (`temporal_fact requires as_of`), сверки с опорной датой нет.
2. **Промпт куратора** `prompts/curator.md:23` — «`as_of` — для
 `temporal_fact` момент времени (ISO-8601)»; `curator.md:46` —
 «`temporal_fact` обязателен `as_of`; без него используй
 `external_fact`». Это **всё**, что модель видит: не сказано, какая дата
 (опорная дата вопроса? дата из источника? дата события?). И модель не
 может знать текущую дату: context builder даты в контекст **не вставляет**
 (`packages/cognition/context.py` — ни одной инъекции даты), в промптах
 explorer/planner/verifier дат тоже нет.
3. **Хост-проверки на коммите** (`packages/memory/service.py`):
 - опорная дата хоста выводится: `session_date = sessions.created_at`
 (`service.py:314–317`), `derive_claim_scope(question, as_of,
 session_date)` (`service.py:387, 407`; `scope.py:200–242`) — приоритет:
 явная дата вопроса > относительная форма → `session_date` > модельный
 `as_of` (fallback). Модельный `as_of` опорную дату не сдвигает
 (`scope.py:218–220`) — это ушло в **scope** (покрытие → grade);
 - строка claim получает `as_of` **как есть от модели**:
 `as_of_raw = payload.get("as_of")` (`service.py:349`),
 `as_of=datetime.fromisoformat(as_of_raw) if as_of_raw else None`
 (`service.py:400`);
 - **сверки модельного `as_of` с опорной датой, которую хост уже выводит
 по T7.18, на этом пути нет**: опорная дата идёт в scope, модельный
 `as_of` — в строку claim. Два механизма («два разных `as_of`»):
 scope-`as_of` (хост, → grade) и claim-`as_of` (модель, → freshness).
4. **Расчёт `reverify_after`** (`packages/memory/service.py:954` —
 `claim.reverify_after = reverify_after(result, claim.as_of, now)`;
 `packages/memory/rules_engine.py:263–267`):
 `base = as_of if (as_of is not None and result.reverify_after_days == 30)
 else now; return base + timedelta(days=result.reverify_after_days)`.
 Для `temporal_fact` volatility `configurable` → 30 дней
 (`rules_engine.py:30`, `VOLATILITY_REVERIFY_DAYS`; payload
 config-v4: `temporal_fact.volatility = "configurable"`,
 `requires_as_of = true`). Т.е. `reverify_after = модельный as_of + 30d`.
 `freshness_status` при коммите пишется по тому же правилу
 (`service.py:955`, T7.27).

**Корень артефакта**: `as_of` — вход гейта 6 (через `reverify_after`),
который производит **модель** без инструкции о надлежащей дате и без
доступа к текущей дате; хост опорную дату знает (T7.18), но использует её
только для scope, а не для `as_of` claim'а. Тот же класс расхождения, что
ADR-0007 устранил для scope/grade («входы, влияющие на оценку, производит
модель», ADR-0007:30–33; AGENTS.md §3/§3.7).

Набор: **22 claim'а с as_of раньше опорной даты** = 16 просроченных

дизайну корпуса — в набор не входят.) Классификация по источнику даты:

- **(a)** дата из источника = честная дата наблюдения: источник помечает
 состояние/факт датой D («по состоянию на D», «проверенная D»,

 ная запись в источнике);

 (либо только день.месяц с ЧУЖОГО года, либо дата соседней статистики).

### 3.3 Ключевые наблюдения

1. **Датные кластеры**. 2026-06-15 написан в 5 разных вопросов с 5 разными
 парами источников (07d655cf, d55274cf, fb1fa50c, 80c1908c, 2023c86f);
 2026-08-13 — в 4 (84e78a00, 013701c2, dc4b5dda, cdecbf1f). Разные
 источники не могут давать одну и ту же «свою» дату — модель **штам-
 пует** дату (день.месяц берётся из текста страницы — «Дата обращения»,
 «Архивировано», дата релиза — а год подставляется текущий, 2026).
 В statement та же дата продублирована («По состоянию на 2026-06-15 …») —
 дата-квалификатор в утверждении тоже не подкреплён evidence.
2. **Модель не знает текущую дату**: в контексте и в промптах дат нет
 (§2, п.2) — «напиши опорную дату» моделью выполнить не по силам;
 единственный детерминированный источник даты для неё — текст источника
 и вопрос.
 3. **12 из 22 — (c)**: даты в evidence нет вообще (либо только день.месяц с
 чужого года / дата соседней статистики). Формулировка отчёта T7.27 «модель
 записала дату из текста источника» точна для (a)+(b) = 10 (дата видна в
 источнике — как дата события или наблюдения, но не как опорная); для 12 (c)
 модель выдала дату без видимого основания.

**Структурный вывод (важнее выбора as_of)**: на данных EVAL-4d гейт 6
провален **при любом варианте** — даже при идеальном поведении модели
остаются 6 заложенных корпусом просрочек: 6/28 = 0.2143 ≥ 0.20 (строгое
`below`, T7.28). Чтобы 6 заложенных просрочек сами по себе не валяли гейт,
нужно N_temporal ≥ 31 (6/31 = 0.1935). Т.е. «гейт 6 провалится на любом
корпусе» верно **только** для корпусов с заложенными просрочками при
N ≤ 30; на корпусе без заложенных просрочек as_of-артефакты были бы
единственной причиной провала.

**Рекомендация (решение за пользователем)**:

1. **Коротко (до новой заморозки) — (i) + (v1)**: гейт честно следует
 спеке (ADR-0014 §5 — гейт не фильтрует артефакты), менять поведение не
 нужно; в отчёте и freeze зафиксировать разбивку due (6 по дизайну +
 16 модельных as_of, из них 11 — без видимого основания в evidence) и
 структурный вывод (6/28 ≥ 0.20 → failed при любом as_of).
2. **К новому прогону — (iii)+(iv)**: перенести базовую дату
 `reverify_after` на хост-выводимую опорную дату (аналог T7.18 для
 scope) + отдельное audit-поле для даты источника. Это закрывает класс
 «вход гейта 6 производит модель» (ADR-0007:30–33, AGENTS.md §3.7) и
 делает g6 независимым от модельного поля; для этого нужны ADR-0016 +
 изменение `ARCHITECTURE.md` (явное решение пользователя) и тесты.
 Чистый вариант (ii) без инъекции текущей даты в контекст не закрывает
 случай «на текущую дату» (модель дату не знает) — как самостоятельный
 вариант слаб.
3. **Корпус (v2)**: в следующей заморозке держать N_temporal ≥ 31
 (или уменьшить число заложенных old-as_of вопросов) — иначе g6
 непроходим по дизайну независимо от as_of (T7.28, ADR-0015).

Текст источников — content-addressed файлы
`<artifact-store>/artifacts/<sha256[:2]>/<sha256>`, где `sha256 =
sources."metadata"->>'normalized_sha256'` (для EVAL-4d —
`/home/denis/dsh1/eval4d-data/artifacts/`, для EVAL-3d —
`/home/denis/dsh1/eval3d-data/artifacts/`).

```sql
-- 28 current temporal_fact: вопрос, сессия, as_of, reverify_after
SELECT c.id, c.statement, c.as_of, c.reverify_after,
 s.created_at AS session_started, q.text AS question_text
FROM claims c
JOIN claim_assessment_heads h
 ON h.claim_id = c.id AND h.assessment_state = 'current'
 AND h.config_snapshot_id = (SELECT active_config_snapshot_id
 FROM runtime_config_heads WHERE scope='global')
JOIN sessions s ON s.id = c.created_in_session
LEFT JOIN questions q ON q.id = s.question_id
WHERE c.claim_type = 'temporal_fact'
ORDER BY c.as_of;

-- supporting evidence и sha256 контента источника
SELECT left(c.id::text, 8) AS c8, src.canonical_uri,
 src."metadata"->>'normalized_sha256' AS sha
FROM claims c
JOIN claim_assessment_heads h
 ON h.claim_id = c.id AND h.assessment_state = 'current'
 AND h.config_snapshot_id = (SELECT active_config_snapshot_id
 FROM runtime_config_heads WHERE scope='global')
JOIN claim_assessments a ON a.id = h.current_assessment_id
JOIN assessment_evidence ae ON ae.assessment_id = a.id
JOIN evidence e ON e.id = ae.evidence_id
LEFT JOIN sources src ON src.id = e.source_id
WHERE c.claim_type = 'temporal_fact' AND ae.role = 'support';

-- гейт 6 по правилу (T7.27), gate_now = '2026-09-22 08:59:42+00'
WITH gate AS (
 SELECT count(*) AS total,
 count(*) FILTER (WHERE c.reverify_after IS NOT NULL
 AND c.reverify_after <= '2026-09-22 08:59:42+00'::timestamptz) AS due
 FROM claims c
 JOIN claim_assessment_heads h
 ON h.claim_id = c.id AND h.assessment_state = 'current'
 AND h.config_snapshot_id = (SELECT active_config_snapshot_id
 FROM runtime_config_heads WHERE scope='global')
 WHERE c.claim_type = 'temporal_fact'
)
SELECT due, total, round(due::numeric/total, 4) AS ratio,
 CASE WHEN due::numeric/total < 0.20 THEN 'passed' ELSE 'failed' END
FROM gate;
```

Пересчёт вариантов (ii)/(iii)/(iv): правило «новый `reverify_after`»
вычисляется на стороне проба (Python, функция `derive_claim_scope` репо):
опорная дата = явная дата вопроса > относительная форма → дата сессии
(`sessions.created_at`, UTC) > модельный `as_of`; новый срок = опорная
дата + 30d (volatility `configurable`, `rules_engine.py:30`); сравнение с
gate_now. Фрагменты дат: поиск в тексте артефактов форм даты
(ISO / д.м.гггг / «D месяц ГГГГ» / «Month D, YYYY») для дня.месяца `as_of`
— полный год варьируется, чтобы поймать «день.месяц с чужого года».
