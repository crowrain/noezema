# Контрольный набор вопросов T7.118 (control-set-v1)

Документ о том, как замерять честность ответов узла отчётом `hostctl honesty-report`
(`packages/memory/honesty_report.py`). Отчёт — **инструмент наблюдения**: он только читает
записанное и ничего не пишет; набор вопросов ниже — общая линейка для прогонов после выпуска.

## Зачем

Оценки rules engine говорят «насколько подтверждено», но не говорят «ответил ли узел ровно на
вопрос, не перепечатал ли один источник дважды, не выдал ли чужую публикацию как свою». Для
этого нужен отчёт над уже записанным (сессии, утверждения, группы независимости, лента шагов) и
нужна зафиксированная серия вопросов, на которой отчёт можно перечитывать после каждого выпуска.

## Состав набора

Файл `docs/eval/control-set-v1.jsonl`, ровно пять строк (поля `id`, `text`, `kind`, `expect`);
тексты закреплены тестом `tests/unit/test_control_set_t7118.py`:

| id | kind | о чем |
|---|---|---|
| c1 | official+independent | реальные зарплаты 2026: Росстат отдельно, hh.ru / SuperJob / аналитики банков отдельно |
| c2 | official+independent | безработица: Росстат отдельно, индексы hh.ru и оценки банков отдельно |
| c3 | independent-forecasts | прогнозы инфляции Сбербанк / ВТБ / Альфа-Банк / Газпромбанк против прогноза Банка России, каждый с источником и датой |
| c4 | official-figure | годовая инфляция сентября 2026: одна официальная цифра Росстата |
| c5 | computation | сколько простых чисел меньше 10000; ожидание — 1229 вычислением (`python.execute`), без сетевых поисков |

Суффикс метки ` (контроль <метка>)` добавляет скрипт при отправке: повторный прогон другой меткой
— это другой вопрос (дедуп intake по тексту не сольёт прогоны), а отчёт отберёт их по
`--control-tag`.

## Как запускать после выпуска (оператор)

1. Развернуть новый код на стенде (обычный путь `deploy/dev-stand/bootstrap.sh`).
2. `deploy/dev-stand/control-run.sh <метка>` — только на ВМ стенда, только оператором (AGENTS:
   агент к `.92` не обращается). Скрипт прочитает JSONL, отправит пять вопросов приоритетом 9 с
   суффиксом метки, подождёт idle-узла (потолок 10 минут, иначе честный `SKIP`), будит `wake_now`,
   дождётся каждой сессии (потолок 45 минут) и напечатает журнал `ASKED` / `DONE` / `TIMEOUT`
   (id, время UTC, состояние узла). В базу и файлы скрипт ничего не пишет.
3. Команду отчёта печатает сам скрипт, выполняет оператор:
   `noezemactl honesty-report --control-tag <метка> --json control-<метка>-honesty.json`.
4. Для сравнения одинаковых окон: первый прогон сохранить JSON, второй —
   `--baseline <тот-же-json>` и читать раздел «Было → стало (сравнение с baseline)».

## Как читать отчёт

- **Шапка отбора** — какие критерии применены и какие вопросы взяты (потолки 100/400/400: при
  превышении команда отказывается, а не режет молча).
- **Вопрос**: «Ответ есть» или «Ответ не записан» (есть ли сессия с результатом).
- **Сессии**: состояние, причина завершения, длительность, вызовы модели и токены
  (`model_runs`), затем шаги: поиски (официальные хосты — из констант модуля: rosstat.gov.ru,
  gks.ru, cbr.ru, minfin.gov.ru, economy.gov.ru, nalog.gov.ru — против прочих), поиски без
  последующего чтения, успешные чтения и отказы по хостам, повторные заходы на отказавший в этой
  сессии хост, повторные чтения того же содержимого, отказы ворот (почти-повтор запроса, гейт
  недоступного хоста).
- **Утверждения** раздельными корзинами: созданные этим прогоном / переиспользованные (вошли в
  ответ без переоценки) / переиспользованные перепроверкой / опертые (присутствуют в ответе как
  опора). Для каждого: начало формулировки, E-уровень и статус действующей оценки активного
  снимка правил, причины оценки из ленты, подпись о производителе; для E2+ — состав групп
  независимости с родителем по записи значения или страничному указателю.
- **Итог прогона** — суммы и доли: доля поисков без чтения, доля отказов, доля переиспользованных
  утверждений (важно для повторных прогонов — см. ниже).

## Флаги — эвристики, не вердикты

Каждый флаг помечен «требует ручной проверки»; отчёт не меняет оценки и не краснит карточку.

- **Ф1 «E2+ при общем производителе»**: у утверждения с действующей оценкой E2/E3/E4 две группы
  независимости ведут к одному эффективному родителю (по записям происхождения значения или по
  страничным указателям). Чего НЕ ловит: вторую ветку «текст группы называет производителя» —
  не реализована (потребовала бы детекторов атрибуции из `apps/`, что задачей запрещено); группы,
  склеенные уже группировщиком (там общий родитель уже схлопнут в одну группу — флаг про
  «формально две группы при одном производителе»).
- **Ф2 «возможно не по вопросу»**: пересечение значимых основ слов утверждения и вопроса пусто,
  либо связь держится на одной общей основе-якоре (например «росси») при трёх и более значимых
  основах утверждения. Нормализация — то же зеркало ворот почти-повторов T7.111a/T7.112
  (`normalize_search_query` → основы `_prefix_stem`), своих словарей нет. Реализация уточнена
  относительно буквального «доля пересечения мала»: доля ошибается на честных развёрнутых
  ответах (нормальный ответ о зарплатах даёт пересечение 2 из 7 основ) — закреплено тестом.
  Чего НЕ ловит: тематический дрейф, когда утверждение прямо цитирует источники и слова самого
  вопроса (пример ниже: «безработица … по данным Росстата, цитата по hh.ru» под вопросом о
  зарплатах проходит чисто).
- **Ф3 подпись «Опубликовано производителем (X)», X не назван в формулировке**: сличение по тем же
  основам слов; срабатывает только при единственной группе без счётчиков и причине оценки
  «недостаточно независимости/свидетельств». Чего НЕ ловит и что ложно срабатывает: словарь
  народных названий («Росстат») живёт в `apps/`, отчёт его не видит — формулировка «Росстат
  опубликовал…» при подписи «Федеральная служба государственной статистики» даст флаг; это
  закреплено unit-тестом как известное ограничение. Если у имени подписи нет ни одного
  сравнимого слова — флаг не выставляется вообще (fail-closed).

## Повторный прогон и переиспользование

База знаний накапливается: повторный прогон набора (другой меткой) частично отвечает
уже записанным — отчёт обязан и честно показывает это отдельными корзинами (reused / reverified)
и долей в «Итоге прогона». Сравнивать «чистый» первый прогон и повторный напрямую нельзя; для
сравнения служит `--baseline` (та же схема JSON, окно «было → стало»). Повторный прогон той же
меткой невозможен: intake отклоняет повтор по тексту и возвращает тот же id вопроса.

## Чего отчёт не видит вообще

- Не меняет и не пересчитывает оценки, группы, карточку ответа — только читает записанное
  (в тесте т6 счётчики восьми ключевых таблиц до и после отчёта равны).
- Качество рассуждений модели, промпты и конфигурации — вне области видимости.
- Атрибуционные ветки, живущие в `apps/` (текст группы называет производителя; словарь народных
  имён хостов) — отчёт их повторяет по записям, но не перепроверяет.
- Деление поисков «официальные/прочие» — по хосту запроса из констант модуля; запрос со словом
  «Росстат» без домена в эту половину не попадает (документировано тестом).
