# Упрощение интерфейса NOEZEMA: разбор и проект (2026-10-05)

Источник: исходники страниц `apps/web/api.py` (главная, сессия, знание, утверждение, диагностика, метрики, evaluation), перечисления `packages/domain/models/enums.py`, таблицы grade/типов в `README.md` и `ARCHITECTURE.md`. Это проектный документ для сессии A (развитие): по нему пишутся брифы харнессу. Решения пользователя по разделу 7 пока не приняты.

## 1. Что не так сейчас

Интерфейс собран инженером для инженера: это панель управления узлом, а не «задай вопрос и получи ответ». Основные проблемы:

| Проблема | Примеры на экране |
|---|---|
| Внутренние ссылки и номера задач в тексте для человека | «operator intake, T7.59», «§5.2.1: обходит тайминг расписания, шлюзы admission остаются», «Метрики (§16)», «Evaluation (§22.2)» |
| Англицизмы и сырые значения БД без перевода | `state`, `pr`, `origin: message`, `candidate`, `verified`, `session_running`, `committing`, `head current/pending/invalid`, `grade E2`, `conf`, `as_of`, `trust_class` |
| Термины без объяснения | «Узел», «Фаза», «Конфиг (sha256)», «admission», «wake now», «priority», «FIFO», «снапшот», «барьеры инвалидации», «джобы переоценки», «writer gate», «fence», «lease owner», «restore drill», «PITR», «retention» |
| Неточный или двусмысленный перевод | «Рекомендация/коммит» (на самом деле сверка фиксации результата, reconciliation), «Ресурсы: вопросы N · сессии N» (это счётчики, а не ресурсы) |
| Главное скрыто среди служебного | Ответ на вопрос и «можно ли ему верить» нигде не показаны одним взглядом; нужно открыть сессию, потом знание, потом утверждение |
| Нет подсказок «что делать» | Узел «paused», «a session is already running», `interval_not_elapsed` — пользователь не знает, это норма или поломка |
| Сессия — лента сырых событий | `session_state_changed`, `context_packed: 244 tokens`, `question_selected` без пояснения этапов |

## 2. Принципы

1. **Два слоя.** «Простой режим» по умолчанию (вопрос → ответ → насколько можно верить → как получено) и «Для инженера» (нынешние страницы, но с понятными подписями и подсказками). Переключатель в шапке.
2. **Один словарь на всё.** Единый модуль подписей (код → короткая подпись + пояснение + «что делать»), который используют и страницы, и API (добавляются поля `label`, `hint`, существующие поля не меняются). Тест: у каждого значения каждого перечисления есть подпись, иначе красный.
3. **Язык человека.** Русские слова вместо кодов; англицизм в скобках только при первом упоминании. Никаких `§` и `T7.xx` в видимом тексте (ссылка на раздел остаётся в подсказке-tooltip для инженера).
4. **Ответ важнее процесса.** Страница вопроса показывает результат и надёжность, ход работы сворачивается.
5. **Всегда «что дальше».** У каждого состояния и отказа короткое объяснение и действие (кнопка или фраза).

## 3. Словарь замен (рекомендуемые подписи)

**Статус вопроса** (`QuestionState`): `candidate` — «ждёт очереди»; `selected` — «взят в работу»; `researching` — «исследуется»; `partially_answered` — «есть частичный ответ»; `verified` — «ответ получен и проверен»; `rejected` — «отклонён»; `deferred` — «отложен».

**Откуда вопрос** (`origin`): `message` — «от вас»; `seeded` — «из тестового набора»; `model_proposal` — «предложен самой системой»; `conflict` — «из-за противоречия в знаниях»; `unknown_term` — «непонятный термин»; `unverified_claim` — «непроверенное утверждение»; `previous_result` — «продолжение прошлого результата»; `local_corpus` — «из локальных материалов».

**Приоритет** (`priority`, число −100…100): заменить числом-полем на выбор «Обычный / Срочно (вперёд очереди) / Потом» (значения 0 / 9 / −5; точное число — в «дополнительно»).

**Состояние узла:** `idle` — «свободен»; `session_running` — «идёт обработка вопроса»; `paused` — «на паузе (после нескольких неудач подряд или по вашей команде)» + кнопка «Возобновить».

**Этапы сессии** (`SessionState`, 5 понятных шагов вместо 14 кодов): `waking/orienting` — «подготовка»; `selecting_question/planning` — «выбор вопроса и план»; `exploring` — «поиск ответа (расчёты, чтение источников)»; `verifying/consolidating` — «проверка и оформление выводов»; `reporting/committing/reconciling_commit` — «запись результата»; `succeeded` — «готово»; `succeeded_partial` — «готово частично»; `failed/aborting/aborted` — «не удалось / остановлено».

**Надёжность ответа** (главный бейдж; вычисляется из `epistemic_status`, `effective_grade`, типа утверждения; пороги `supported` из README: computed_result/local_observation/self_model — E2, external_fact/procedural/empirical_conjecture/temporal_fact — E3, formal_theorem — E4):
- **«Проверено» (зелёный)** — статус `supported` (оценка достигла порога для типа).
- **«Подтверждено слабо» (жёлтый)** — гипотеза с E1–E2, ниже порога для типа: «есть одно подтверждение, нужно ещё».
- **«Не проверено» (серый)** — E0 / гипотеза без проверок.
- **«Спорно» (оранжевый)** — `disputed`: источники противоречат друг другу.
- **«Опровергнуто» (красный)** — `refuted`.
- **«Отложено» (серый)** — `deferred`: ждёт данных.
Рядом строка «как проверено» из evidence: «вычислено в изолированной среде», «подтверждено N независимыми источниками», «прочитан 1 источник», «цитата сверена с источником».

**Оценка доказательств** (`grade` E0–E4, для инженера): E0 «не проверено»; E1 «цитата сверена с источником (целостность)»; E2 «подтверждено одним методом»; E3 «подтверждено независимо (несколько источников или повтор)»; E4 «формально доказано или многократно воспроизведено».

**Свежесть** (`freshness_status`): `fresh` — «актуально»; `due` — «пора перепроверить»; `stale` — «устарело»; `evergreen` — «не устаревает (факт вне времени)»; `unknown` — «срок не определён». Показывать только если важно (факт про «сейчас»): «актуально на <дата>, перепроверить после <дата>».

**Тип утверждения** (`claim_type`): `computed_result` — «результат вычисления»; `external_fact` — «факт из внешнего мира»; `local_observation` — «наблюдение на месте»; `formal_theorem` — «доказанная теорема»; `empirical_conjecture` — «эмпирическая гипотеза (по экспериментам)»; `procedural` — «способ действия, инструкция»; `temporal_fact` — «факт, зависящий от времени»; `self_model` — «о самой системе».

**Состояние записи в графе знаний** (`head`: `current/pending/invalid/none`): `current` — «действует»; `pending` — «ждёт пересчёта оценки»; `invalid` — «признано недействительным»; `none` — «оценки нет».

**Команды оператора:** `wake_now` — «Запустить сейчас (обработать вопрос из очереди)»; `pause` — «Поставить на паузу»; `resume` — «Возобновить»; `stop_gracefully` — «Остановить после текущего шага»; `abort_session` — «Прервать сейчас».

**Причины, по которым сессия не стартует** (admission/расписание → «что делать»):
`interval_not_elapsed` — «Ещё рано по расписанию (интервал между сессиями не прошёл). Кнопка «Запустить сейчас» обходит это»;
`nonterminal_session` / `session_in_progress` — «Сейчас уже идёт другая сессия, дождитесь её окончания»;
`paused` — «Узел на паузе; нажмите «Возобновить»»;
`unresolved_commit_attempt` — «Прошлый результат ещё сверяется; подождите или откройте «Состояние системы»»;
`activation_slot_busy` — «Идёт смена конфигурации»;
`reassessment_backlog` / `repair_backlog` — «Система сначала дорабатывает старые выводы»;
`disk_quota_exceeded` — «Мало места на диске»; `gpu_unavailable` — «Недоступна видеокарта»;
`no_question` (итог сессии) — «Очередь пуста: задайте вопрос».

**Технические блоки «Диагностики»** (подпись + одна строка «что это» + «когда беспокоиться»):
«Активация конфига» → «Какая версия настроек действует»; «Backup/PITR» → «Резервные копии и проверка восстановления»; «Рекомендация/коммит» → «Сверка записи результатов (все ли сессии записались до конца)»; «Барьеры инвалидации» → «Перечёркнутые выводы, по которым идёт каскадная проверка зависимых»; «Джобы переоценки» → «Очередь перепроверки старых выводов»; «gate/fence/lease owner» → в раскрывающийся блок «для инженеров».

## 6. Риски и ограничения
- Страницы рисуются JavaScript'ом из JSON-API: словарь нужно держать на сервере, чтобы тесты могли его проверять (не дублировать в JS).
- Надёжность для человека — упрощение оценки; точные E0–E4 и статус остаются доступны («для инженера»); правила бейджа должны точно следовать порогам из `ARCHITECTURE.md`/`README.md` (иначе введём пользователя в заблуждение), поэтому бейдж проектируется и тестируется как отдельная функция.
- Не раскрывать лишнего в «простом» режиме: id сессий и хэши скрыты, но доступны по ссылке «подробно».
- Профиль `sealed` (нет сети) на стенде: «как проверено» должно честно писать «вычислено», «источников нет», а не создавать впечатление проверки.

## 9. Замечание реализации (T7.74, ответ виден там, где его не создавали)

«Ответ вопроса» для человека — это то, что вопрос сделал со знанием, а не только то, что он
записал новой строкой. Перепроверка и повтор существующего утверждения ответа ранее не имели:
и карточка, и «Мои вопросы» показывали «Ответ не записан». Теперь связка расширена до
«затронул»: у утверждения печатается отношение — «создано этим вопросом», «перепроверено этим
вопросом», «уже было в знаниях, принято повторно» (категория `claim_relation`), а итог вопроса
вместо ложного «не записан» получает «Ответ есть: подтверждено заново», «Ответ есть частично:
подтверждено» или «Ответ есть: уже было, подтверждено».

Правила простоты при этом сохранены: отношение и история оценки («было: … → стало: …») — одна
короткая строка под утверждением, причины берутся из уже существующих подписей причин оценки;
слово «проверено» по-прежнему произносит только бейдж надёжности; ни кодов перечислений, ни

запросом к одним данным, поэтому они не могут показать разное. Действующее утверждение остаётся
