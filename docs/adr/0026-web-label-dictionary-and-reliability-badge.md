# ADR-0026: Единый серверный словарь подписей и представление надёжности — presentation layer, не источник истины (T7.64)

Статус: accepted

Дата: 2026-10-05

Контекст: `docs/ui-simplification-design.md` (разделы 2.2, 3, 5.1), §8.7 (пороги типов и
`epistemic_status`), §13.6–§13.7 (Query/Command API), T7.64. Затронутые файлы:
`apps/web/labels.py` (новый), `apps/web/reliability.py` (новый), `apps/web/knowledge.py`,
`apps/web/api.py` (аддитивно), тесты `tests/unit/test_web_labels.py`,
`tests/unit/test_web_reliability.py`, `tests/scenario/test_web_labels_api.py`.

## Контекст

Интерфейс показывает сырые значения БД и внутренние ссылки (`head current`, `E2`,
`session_running`, `§5.2.1`, `T7.59`). Дизайн-документ требует «один словарь на всё»: модуль,
который по коду значения даёт короткую русскую подпись, одно предложение пояснения и подсказку
«что делать», и который используют и страницы, и API (поля `label`/`hint` добавляются,
существующие не меняются). Отдельно требуется бейдж надёжности ответа.

Два ограничения делают это решением, а не косметикой:

1. **Оценка знания — не право presentation-слоя.** §3 и §8.7: grade/confidence/epistemic_status
   производит только rules engine; «Verifier, оператор, LLM grade не назначают». Значит бейдж
   обязан быть переводом уже вычисленной оценки, а не второй реализацией оценки. Иначе в репо
   появятся два места, решающих «можно ли верить», и они неизбежно разъедутся.
2. **Страницы рисуются JavaScript'ом из JSON-API.** Если словарь будет жить в JS, тесты его не
   видят и он задублирует доменные коды (риск: экран начнёт «помнить» свои пороги). Поэтому
   единственный источник — серверный модуль, а страницы (T7.65/T7.66) будут только читать.

## Решение

1. **`apps/web/labels.py` — единственный словарь подписей.** Таблица `категория → значение →
   (label ≤ 40 знаков, hint — одно предложение ≤ 160, action «что делать» ≤ 120)`; категории —
   пользовательские перечисления домена, состояния узла и head, типы/состояния команд, причины
   пропуска запуска (admission/расписание), строки отказа Command API, закрытые итоги сессии,
   типы событий ленты, роли и виды доказательств, состояния барьеров/джобов/попыток фиксации,
   состояния сообщений и состояние восстановления узла. Публичный API: `describe(category, value)`,
   `glossary()`, `session_stage(state)` (пятиступенчатая шкала), `refusal_key(reason)` +
   `describe_refusal`/`describe_reason`, `WAKE_REASON_KEYS`.

2. **Запасной путь честный, а не выдуманный.** Неизвестное значение получает `label` = сам код,
   пустые `hint`/`action`. Это делает отсутствие подписи видимым на экране вместо правдоподобной
   фразы из головы.

3. **Полнота закрепляется тестом, источник значений — код.** `tests/unit/test_web_labels.py`
   собирает значения не списком в тесте, а из рабочих мест: перечисления домена, константы
   `apps/orchestrator/scheduler.py` (`REASON_*`/`WAIT_*`), константы `apps/web/host_status.py`,
   `apps.web.api.NODE_STATES`, строки отказа, вынутые регуляркой из исходника Command API, и итоги
   фиксации из `FinalizeOutcome` (`commit_<итог>`). Новое значение enum или новая фраза отказа без
   подписи краснит тест (краснота проверена временными пробнами: значение в `QuestionOrigin` и
   заменённая строка отказа; обе отменены до коммита). Отдельный тест следит за текстами: длины,
   непустота, запрет `§`, номеров задач плана, кодов snake_case и uuid/sha-подобных строк.

4. **Бейдж надёжности — чистая функция над уже вычисленной оценкой**
   (`apps/web/reliability.py`): `reliability(claim_type, epistemic_status, effective_grade, *,
   head_state, min_grade_for_supported)` → `{level, label, hint, color}` по шкале
   «Проверено (green) / Подтверждено слабо (yellow) / Не проверено (gray) / Спорно (orange) /
   Опровергнуто (red) / Отложено (gray)». Соответствие: `supported → verified`;
   `disputed/refuted/deferred` проходят как есть и **не зависят от уровня**; гипотеза E1–E2 →
   weak с подсказкой, называющей, чего не хватает по порогу именно этого типа; гипотеза E0 или без
   оценки, а также head `pending/invalid/none` → unverified. Функция ничего не пересчитывает и не
   повышает статус.

5. **Пороги берутся из действующего снапшота правил.** Вызывающий код (`apps/web.knowledge`)
   читает `claim_type_rules` effective-снапшота через `runtime_config_heads` и передаёт
   `min_grade_for_supported` в функцию; запасная таблица модуля существует только чтобы текст не
   зависел от удачи запроса, и тест сверяет её с `docs/eval/config-v13-payload.json`. Пороги, пороги
   групп и сами правила при этом не менялись: зеркало проверяется тестом, а не правкой.

6. **«Как проверено» говорит только о том, что есть в данных.** `describe_verification(evidence_rows,
   *, source_groups, environment_groups)` строит фразы из реально переданных полей (вид
   доказательства и его количество, сохранён ли артефакт, число прочитанных источников, зафиксированные
   группы независимости источников/условий, число возражений). Групп не было — фраза про
   независимость не появляется; данных нет — «подробности проверки недоступны». Про «изолированную
   среду ничего не утверждается: profile `sealed` действительно без сети, но это свойство запуска,
   а не поле доказательства (риск дизайн-документа §6).

7. **API дополняется, не переустроается.** Ни один существующий ключ и значение не изменены; новых
   полей нет в телах ответов, которых тесты сравнивают целиком (состав evidence/source в provenance
   не тронут). Добавлен открытый `GET /api/v1/glossary` — тот же словарь для будущей страницы
   «Справка» (T7.66), чтобы текст не дублировался между API и JS.

## Границы: чего это решение сознательно не делает

- Не трогает rules engine, модели, миграции, payloads `config-v*`, промпты, пины,
  `tool_schema_hash`, пороги и поведение оркестратора; HTML/JS страниц не переделывает (этапы
  T7.65/T7.66).
- Не переводит тексты ошибок валидации приёма вопроса (`invalid_question` и его detail) — это
  отдельные строки сервиса intake, их подписи относятся к этапу главной страницы.
- Не изобретает подписей для свободных строк: `termination_reason` — свободное текстовое поле
  (сырые строки модели, формулировки сверителя), поэтому неизвестная строка остаётся на запасном
  пути. Полный перевод возможен только если поле станет закрытым перечислением — это решение про
  модель данных, не про интерфейс.

## Частные решения, не очевидные из кода

1. **«weak = гипотеза E1–E2» против правил.** rules-v2 даёт предположению максимум E1 (E2+ бывает
   только у `supported`). Комбинация «hypothesis + E3/E4» product-кодом не производится; если такая
   запись пришла (устаревшая или повреждённая оценка), она показывается как «не проверено» с текстом
   про несогласованность записи, а не как «подтверждено слабо». Матричный тест фиксирует этот угол.
2. **Состояния узла.** Веб показывает тройку `idle/paused/session_running` (`api.NODE_STATES`), а
   доменное перечисление содержит ещё `sleeping`. Подписаны все; `sleeping` помечен как служебное,
   на экран узла не выводимое.
3. **`head_state = none`** синтезируется запросом знания (COALESCE), это не значение
   `AssessmentState`; категория подписей head-состояний включает его отдельно.
4. **Пятиступенчатая шкала.** Дизайн-документ оставил без этапа `created`, `stopping`, `aborting`.
   Принято: `created` → этап 1 «подготовка»; `failed/cancelled/stopping/aborting` → вне линейной
   шкалы (`index = null`) с человеческим названием исхода; успешная линия покрывает ровно 5 этапов.
5. **Отказ команды может быть кодом допуска.** Command API в поле `reason` отдаёт и человекочитаемые
   фразы, и коды планировщика; подпись подбирается по обоим видам (сначала нормализация фразы,
   затем код), поэтому один и тот же ответ не остаётся без пояснения.

## Последствия

- Любое новое значение пользовательского enum или новая фраза отказа обязана получить подпись в
  `apps/web/labels.py` — иначе красный тест. Правило записано в AGENTS.md §7.
- Тексты подписей стали проверяемыми: длина, непустота и запрет внутренних ссылок/кодов — часть
  теста, а не договорённость.
- Экран по-прежнему не является источником истины: если подпись и данные расходятся, виноваты
  словарь и тест полноты, а не rules engine; проверить можно `GET /api/v1/glossary`.
