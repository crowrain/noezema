# ADR-0025: Одна сессия на узел — session-level advisory lock на отдельном соединении (T7.61(а), §5.2.1, §8.7.2)

Статус: accepted

Дата: 2026-10-05

Контекст: нарушение инварианта «одна сессия на узел» на dev-стенде 192.168.1.92 — одновременно шли
сессии, запущенные веб-командой «wake now» и запланированным `noezema-dev-tick.service`. Касается
`apps/orchestrator/node_guard.py` (новый модуль), `apps/orchestrator/scheduler.py`,
`hostctl/cli.py` (wake-tick, eval-run), `apps/web/api.py`, `apps/orchestrator/main.py`.

## Контекст

§5.2.1 делает списком авторитетным ответ на «можно ли будить узел», и одно из его условий — «нет
незавершённой сессии с живым lease». В коде это `SELECT count(*) FROM sessions WHERE state NOT IN
(<terminal>)` (`WakeScheduler._admission`). Строка запущенной сессии появляется в phase 1
(`Orchestrator._run_to_committing`, T7.20/ADR-0009) и остаётся невидимой другим соединениям до финальной
транзакции. Между `decide()` другой точки входа и видимостью её строки есть окно в несколько десятков
секунд — длиннее тика (60 с). Маркер `node_state='session_running'` в admission не участвует, и участвовать
не должен: T5.2/T7.59(в) специально сделали остаточный маркер неблокирующим, чтобы убитый юнит не клинил
узел. Ни одна существующая проверка не является взаимным исключением процессов.

Наблюдение на стенде (2026-10-05): «wake now» → сессия `7f6b28a7` (05:26:52, ~40 с); через 36 с тик
получил wake и запустил `fa5448d5`. Оба дошли до succeeded — то есть конфликт не обнаружен нигде.

## Решение

Каждая точка входа, запускающая `run_session` (wake-tick, веб «wake now», eval-run, ручной
`python -m apps.orchestrator`), берёт **session-level advisory lock** PostgreSQL и держит её всю сессию:

- имя замка — `node_session_lock_name(node_owner)` = `noezema:node_session:<node_owner>`; хеш считает
  PostgreSQL (`pg_try_advisory_lock(hashtext(:name))`), поэтому ключ идентичен во всех процессах узла.
  Python `hash()` запрещён: PYTHONHASHSEED солит его на процесс, и каждый systemd unit взял бы свой замок.
- try-режим без ожидания: занято → skip с точной причиной `REASON_SESSION_IN_PROGRESS` (§5.2.1), а не
  очередь и не ошибка. Веб отвечает той же оператору понятной формулировкой, что и в локальном случае
  («a session is already running»).
- Замок живёт на **отдельном** соединении (`NullPool` + AUTOCOMMIT) и никогда не входит в транзакцию сессии:
  §5.9.1 уже требует, чтобы admission-гейты жили вне короткой доменной транзакции, а §5.2.2 описывает
  канонический порядок блокировок строк — advisory-гейт в него не входит и не может его ни пополнить, ни
  нарушить (тот же принцип у writer gate `packages/memory/cascade.py` и offline rules
  `hostctl/offline_rules.py`, §8.7.2: «DB ownership — session-level PostgreSQL advisory lock на scope; это
  не lease и не fencing protocol»).
- Снятие идемпотентное, в `finally` каждой точки входа: нормальный конец сессии, исключение внутри неё,
  отмена задачи (веб-shutdown), fail-closed отказ. Дополнительно замок снимает сам PostgreSQL, когда гибнет
  соединение-держатель (`§12`: «advisory lock держит не транзакция, а соединение»), что подтверждено тестом
  с `pg_terminate_backend`. То есть убитый `systemctl` юнит не оставляет ни клина, ни мусора: освобождение
  не требует reconciler-политики, ручных сбросов маркера и новой таблицы.

Порядок в точке входа неизменный: admission → замок → маркер `session_running` → сессия → учёт исхода
(backoff/пауза) → снятие замка. `decide()` и §5.2.1 список не изменены: guard — дополнительная защита окна
decide→start, а не замена admission (условие «нет незавершённой сессии» по-прежнему проверяется: сам замок
не знает, есть ли на узле живая сессия с lease, — он знает только, что кто-то уже вошёл в лейн).

## Альтернативы (отклонены)

- **Делать `session_running` условием admission.** Ломает T5.2/T7.59(в): остаточный маркер от убитого юнита
  клинит узел до ручной чистки; плюс не закрывает одновременный старт (оба видят `idle`).
- **Писать маркер изнутри phase 1.** COMMIT строки `system_constants` возможен только вместе с phase 1, а
  отдельная запись из середины фазы — незащищённая запись состояния вне state-machine.
- **`SELECT … FOR UPDATE` по узлу/вопросу на всю сессию.** Держит row lock минуты (§12 предупреждает о
  висящих транзакциях), конфликтует с финальной транзакцией, не даёт crash-safety.
- **Таблица node-lease с heartbeat и TTL.** Потребовала бы миграции, reconciler-политики и правила
  «кому верить»; §8.7.2 прямо говорит, что для DB-владения хостного контура нужен advisory lock, а не lease.

## Последствия и риски

- +1 короткое соединение к PostgreSQL на каждую точку входа (NullPool — открывается/закрывается вместе с
  wake),Cost тривиален по сравнению с открытием sandbox-контейнера на сессию (T7.58).
- Session-level advisory lock требует одного DB session на клиент: за transaction-mode pooler (pgbouncer)
  гарантией он быть перестанет. Прямого pooler в проекте нет (`deploy/`, тестовый контур — прямые
  соединения); при его появлении guard должен стать долговременной строкой с lease.
- Guard решает только «кто может **начать** сессию». Авторизацию коммита по-прежнему даёт lease сессии и
  fenced commit (§5.2.3, §3 AGENTS): two-phase гонок внутри одной сессии он не каскадирует.
- Локально проверено: исключение между двумя процессами (веб + CLI-подпроцесс), освобождение при смерти
  бэкенда, освобождение при отмене задачи, независимость разных `node_owner`. Не проверено на реальном
  стенде: `systemctl kill` посреди сессии и поведение юнита после него.
