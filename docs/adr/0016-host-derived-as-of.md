# ADR-0016: Опорная дата `as_of` выводится хостом; модельная дата — аудиторская (T7.30, §8.2, §8.6, §8.7)

Статус: accepted

Дата: 2026-09-22 (решение пользователя от 2026-09-22 — варианты (iii)+(iv)
разбора T7.29)

## Контекст

Разбор T7.29 (`docs/eval/EVAL-4d-as-of-analysis.md`) зафиксировал:
базовая дата due/stale-механики (§22.2) — `claims.as_of`
(`reverify_after = as_of + 30d`, §8.6:1121,
`packages/memory/rules_engine.py:263–267`) — на коммите записывается
**как есть от модели** (`packages/memory/service.py`:
`as_of = datetime.fromisoformat(payload["as_of"])`). При этом:

- **модель не видит текущую дату**: context builder даты в контекст не
  вставляет, промпт куратора говорит лишь «момент времени (ISO-8601)»
  (`prompts/curator.md:23,46`) — «напиши опорную дату» моделью
  выполнить не по силам; её единственный источник дат — текст вопроса
  и источников;
- **улика EVAL-4d** (SELECT, `noezema-eval4d`): 22 claim'а с `as_of`
  раньше опорной даты — 16 просроченных + 6 непросроченных; из 22 —
  **16 модельных артефактов** (8 — дата события/наблюдения из
  источника, 12 — без видимого основания: модель штампует
  день.месяц из страницы + текущий год; кластеры 2026-06-15 ×5 и
  2026-08-13 ×4 по разным источникам). Сверка с EVAL-3d: тот же
  паттерн (3×(c) + 1×(b)) — стабильное поведение модели, не
  случайность;
- **класс дефекта** — тот же, что ADR-0007 устранил для
  scope/grade: «вход гейта производит модель» (ADR-0007:30–33,
  AGENTS.md §3.7). Хост опорную дату **уже выводит** (T7.17/T7.18 —
  `derive_claim_scope`, `packages/memory/scope.py`: явная дата
  вопроса > относительная форма → дата сессии по часам хоста >
  модельный `as_of`), но использовал её **только для scope** (→
  grade), а в строку claim (→ freshness → гейт 6) уходил модельный
  `as_of`. Сверки модельного `as_of` с опорной датой нигде не было.

Т.е. гейт `due_stale_time_sensitive` (§22.2) — как и grade до ADR-0007,
— управлялся моделью: 16/22 просрочек EVAL-4d — не «данные источника
старые», а модельный артефакт в входе гейта.

## Решение

**Определение: `as_of` := хост-выводимая опорная дата** — базовая дата
`reverify_after` (§8.6) выводится доверенным хостом из вопроса
сессии; **модельная дата — аудиторская** (не входит ни в строку
claim, ни в расчёт срока; ADR-0007:172–175 для scope расширен на
freshness):

1. **Одна функция, один источник истины** — `derive_claim_as_of`
   (`packages/memory/scope.py`), тот же приоритет, что T7.17/T7.18
   использует для scope (`derive_claim_scope` теперь вызывает его —
   копия логики нет):
   - вопрос с **явной датой** → `claims.as_of` = эта дата (полночь
     UTC);
   - вопрос с **относительной формой** («на текущую дату» и т.п. —
     закрытый детерминированный набор, T7.18) → `claims.as_of` =
     **дата сессии по часам хоста (UTC)** — якорь **начало сессии**
     (`sessions.created_at`), не момент commit (ADR-0007 п.2: сессия,
     пересекающая полночь, не переякоряет дату);
   - вопрос **без опорной даты** → прежний fallback: модельный
     `as_of` как есть (Спутник 1957, релизы — дата события
     остаётся).
2. **`reverify_after = новое `claims.as_of` + срок по volatility** —
   формула `reverify_after()` (`rules_engine.py:263–267`) **не
   меняется**; меняется только вход: базовая дата due/stale
   (§22.2) — хост-дата. Точки записи (коммит, переоценка)
   пересчитывают `reverify_after` от сохранённого `claims.as_of` —
   теперь хост-деривация; модельная дата в пересчёт не возвращается.
3. **Модельный `as_of` не теряется — сохраняется для аудита** там же,
   где ADR-0007 п.3 хранит модельные значения:
   - **staging payload** (`session_staging`, durable, неизменяем) —
     `as_of` предложения модели;
   - **audit** `claim_created` (по образцу
     `scope`/`assessed_scope`, ADR-0007): `as_of` = модельное
     значение, `assessed_as_of` = хост-выводимое значение, записанное
     в строку claim.
   Новая колонка/миграция **не нужна**: без них модельное значение не
   теряется (staging + audit).
4. **Переиспользование (dedup)**: при каждом коммите `as_of` строки
   claim **ре-деривируется из вопроса ТЕКУЩЕЙ сессии** — ровно как
   scope (claim утверждается для даты, которую анкрит этот вопрос:
   относительный claim — «состояние на дату ЭТОЙ сессии», ADR-0007
   T7.18), и `reverify_after` на коммите (пересчёт для каждого
   claim'а) опирается на свежую хост-дату, а не на устаревшую.
5. **Statement хост НЕ переписывает** (известное ограничение — см.
   ниже).

## Что НЕ меняется

- **Схема `CuratorProposal`** (`packages/domain/schemas/staging.py`):
  `as_of` остаётся полем предложения модели; валидация
  `temporal_fact requires as_of` (`staging.py:96–98`) — как есть.
  Схема уходит движку halogen — изменение = нарушение ADR-0012.
- **Промпт куратора** (`prompts/curator.md`) — часть замороженного
  protocol snapshot (`service.py:330–334`) — не меняется.
- **Формула** `reverify_after()` (`rules_engine.py:263–267`) — не
  меняется.
- **Rules engine** (предикат покрытия, `claim_type_rules`,
  `requires_as_of`, правило E3), **`rules_version`** (остаётся
  `rules-v2`), **`rules_hash`** (хэш payload'а `claim_type_rules` —
  не тронут), **пороги §22.2** — не меняются: изменилась только
  хост-деривация значения (сторона хоста, `packages/memory/`), как
  T7.18 (ADR-0007:194–203).
- **Замороженные payload'ы** config-v2…v5 и **корпуса** v2/v3 (их
  хэши) — не тронуты.
- **Сохранённые данные прошлых прогонов** (`noezema-eval*`) — НЕ
  переоцениваются и не пересчитываются (SELECT only).
- **Retrieval, гейты, web/blind-выгрузка** — читают сохранённые
  `claims.as_of`/`reverify_after` (freshness по §8.6/T3.7 на момент
  чтения, T7.27) — код не меняется; читают теперь хост-деривированные
  значения.
- **Переоценка** (`reassessment.py`): `reverify_after` пересчитывается
  от сохранённого `claims.as_of` (хост-дата) — код не меняется;
  модельную дату не возвращает (её в строке claim нет).

## Почему не другие варианты

- **Уточнить только промпт/описание (вариант ii T7.29)**: модель не
  видит текущую дату (§2, разбор T7.29) — «напиши текущую дату»
  выполнить не сможет; для бездатовых вопросов («Спутник»)
  «правильная» дата — дата события, инструкция неоднозначна;
  соблюдение локальной моделью не гарантируется. Вход гейта остался
  бы модельным.
- **Отдельное поле `source_as_of`** (дата источника): не введено —
  дата-наблюдение источника не моделируется как значение `as_of`
  (ADR-0007:44–52: в спеке значения «дата наблюдения
  источником»/«дата события» нет; evidence scope несёт время
  наблюдения = `retrieved_at`, ADR-0007:64–71); новое поле меняло бы
  схему (движок halogen) и требовало бы правки промпта (замороженный
  snapshot) — срез, который решение (iii)+(iv) не требует.
- **Ничего не менять (вариант i)**: оставляет вход гейта 6 модельным —
  класс дефекта ADR-0007 не закрыт; 16/22 просрочек EVAL-4d —
  артефакт, а не сигнал.

## Следствия

- **Форма EVAL-4d на новом прогоне** (фикстура, не БД улик;
  пересчёт T7.29 §4): 14 относительных → `as_of` = дата сессии →
  `reverify_after` = +30d → fresh; остаются due: 6 заложенных
  (явная старая дата вопроса) + 2 бездатовых (модельный fallback) =
  **8/28 = 0.2857 → failed** (строгое `below`, T7.28). Гейт больше не
  зависит от модельного поля; структурный вывод T7.29 сохраняется: на
  корпусе с 6 заложенными просрочками при N ≤ 30 g6 провален при
  ЛЮБОМ as_of (6/28 ≥ 0.20) — N_temporal ≥ 31 — задача корпуса v4
  (следующая заморозка).
- **`external_fact`** (volatility `configurable`, 30d): базовая дата
  `reverify_after` тоже становится хост-опорной датой для вопросов с
  явным/относительным якорем — следствие единого поля `as_of` и
  единой деривации (§8.6: «Reverify deadline выводится из claim type,
  volatility, `as_of` и valid interval»). Гейт 6 считает только
  `temporal_fact`; на гейты других типов не влияет.
- **Сопоставимость**: новый прогон — новый baseline для
  as_of/reverify_after относительных и явных claim'ов (как смена
  модели в EVAL-4); прошлые данные не переоцениваются.

## Известное ограничение

- **Statement может содержать дату источника, отличную от `as_of`**
  («По состоянию на 2026-06-15 …» при `as_of` = 2026-09-21): хост
  statement **не переписывает** — это утверждение модели; расхождение
  видно в паре `statement` / `claims.as_of` + `as_of` (модель) в
  staging/audit. Freshness-механизм в рамках конвенции корпуса
  (ADR-0007:64–71) и до, и после не отслеживает «возраст контента
  источника» — только расписание перевалидации от опорной даты.
