# ADR-0031: Операторский спор утверждения = коррекция графа источников (§11.3); ручное «снять утверждение» не сделано — остановлено по критерию (T7.81)

- Статус: **accepted** для части (а) («оспорить») — код и тесты в T7.81; **отклонено/отложено** для части (б)
  («снять утверждение вручную») — требуется явное решение пользователя, варианты перечислены в §6
- Дата: 2026-10-08
- Контекст: стендовый пропуск `c970bc08…` на ВМ 192.168.1.92 — «независимые оценки совпали: _rosstat_ и
  _sbercib_», голова `current` / `supported` / E3, бейдж «Проверено». Вторая группа независимости — страница
  банка, дословно пересказывающая пресс-выпуск. Решение пользователя от 2026-10-08: нужен вход оператора для
  спора и для ручного снятия; оба — «через существующие механизмы, с аудитом и идемпотентностью».

## 1. Почему прежние механизмы этот пропуск не закрывают

| попытка | почему не работает |
|---|---|
| атрибуция производности (T7.75 / T7.78, ADR-0029) | склейка по значению не состоялась из-за округления: «около 5,6%» против «5,59%» (T7.78 §13); `parent_source_id` у пересказа не появился |
| группировка источников v2 | `registrable_domain("rosstat.example") ≠ registrable_domain("sbercib.example")`: два разных домена ⇒ две группы ⇒ `min_independence_groups = 2` выполнено ⇒ E3 (`packages/memory/independence.py`, `claim_type_rules.external_fact` в config-v18) |
| переоценка (`reassessment_jobs`) | worker пересчитывает **только из существующих улик** (§8.6:1148): улики не изменились → та же E3. Голова, переведённая в `pending`/`invalid` без изменения фактов, возвращается в `current` с прежней оценкой на ближайшем тике maint-юнита (60 с на стенде) |

Вывод: чтобы бейдж уехал честным путём, оператор должен изменить **не оценку, а факт о происхождении
источника**. Спека такой вход даёт прямо: «Исправление ложного объединения оформляется как отдельная
source-graph correction с проверяемой provenance-цепочкой, actor и audit record»; «если correction объединяет
ранее разные группы, зависимые claim assessments инвалидируются и пересчитываются» (§11.3:1667–1669).

## 2. Решение (а): спор как merge-коррекция графа

Носитель решения — строка **существующей** таблицы `source_graph_corrections` (миграция 0011), ни одной новой
таблицы и колонки:

| поле | что в него идёт | почему именно так |
|---|---|---|
| `kind` | `'merge'` | закрытый CHECK `('merge','split')`: оператор склеивает пересказ с первоисточником; `split` — механизм T7.75 для обратного случая |
| `actor` | `operator:web` (форма витрины) или `operator:hostctl` (хостовая консоль) | TEXT-колонка без CHECK (миграция 0011:52–77): новое значение актора не требует миграции; актор обязывает подпись в словаре (`labels.py`, категория `dispute_actor`) |
| `from_source_id` / `to_source_id` | пересказ → первоисточник | пара берётся **из улик именно этого claim'а**: адрес вне `sources` утверждения — отказ (§11.3 требует provenance-цепочки, а не произвольного утверждения про интернет) |
| `basis_artifact_id` | `observation_artifact_id` улики пересказывающей страницы | «проверяемая provenance-цепочка»: спор опирается на уже прочитанное хостом наблюдение, а не на слова оператора |
| `reason_audit_event_id` | событие `operator_command_received`, payload `operator_reason` | причина живёт в ленте (актор + время), читается UI по id события — без текстовых эвристик (запрет T7.74) |
| `rules_version` | `RULES_ENGINE_VERSION` | часть естественного ключа: коррекция относится к действующим правилам |

Дальше работает только существующий контур: `apply_source_graph_change` (`packages/memory/source_graph.py`)
инвалидирует головы всех утверждений, чьи улики затрагивают эти источники (head → `pending`, NULL-пара,
`prepared_by = 'system:source_graph'`, задача пересчёта с причиной `source_graph_change`), поднимает
`domain_revisions.scope='source_graph'`, а рабочий переоценки на следующем тике считает оценку заново — теперь
с одной группой независимости ⇒ `insufficient_independence` ⇒ E1/`hypothesis`. **Бейдж меняется потому, что
независимости стало меньше, а не потому, что так захотел оператор** (ADR-0026 остаётся целостным:
presentation ничего не назначает).

Перепроверка — ordinary вопрос в существующую очередь (`packages/domain/services/question_intake.py`,
origin `message`, дедуп по точному тексту) с цитатой statement'а якоря (требование T7.73): если перепроверка
найдёт настоящую независимость, оценка поднимется сама — решение остаётся за правилами.

Отменяемость: та же строка с `valid = false` (ничего не удаляется) + повторный каскад по той же паре. Пересчёт
без merge возвращает прежнюю E3; коррекция, лента и все прежде сделанные оценки остаются в базе (§14 «знание не
удаляется»).

## 3. Почему спор — отдельная mutating-точка, а не новый тип команды

`operator_commands.type` — закрытый enum, материализованный в CHECK миграцией 0002:193–206 («Free text is never
parsed into this», §13.2:1783). Новое значение (`dispute_claim`) означало бы правку CHECK‑списка миграцией —
стоп-критерий этой задачи. Хуже того: scratch-БД тестов строятся с нуля и CHECK получили бы новое значение, а
размеченная база стенда — нет, то есть зелёные тесты и падение на живом стенде.

Выбран путь, уже принятый для приёма вопросов (ADR-0024): свои mutating-эндпоинты Command-API‑семейства —
`POST /api/v1/knowledge/claims/{claim_id}/dispute` и `…/dispute/cancel`, тот же `X-Admin-Token`, тот же
fail-closed гейт здоровья юнитов (423 при нездоровом снимке). Идемпотентность — естественный ключ коррекции
`UNIQUE (actor, from_source_id, to_source_id, kind, rules_version)`; клиентский `idempotency_key` не
принимается (§20.10 «Idempotency hijack»). Повтор того же оператора возвращает `replayed: true` и ту же
коррекцию, второй оператор на той же паре получает отказ `dispute sources already grouped` (ошибка отката —
не пишется ничего, включая событие received).

## 4. Что сознательно НЕ сделано в (а)

- прямые UPDATE `claim_assessment_heads` / `claim_assessments` из оператора — запрещено AGENTS §3 и §8.6;
- новое значение `prepared_by` («operator…»): CHECK 0022:50–60 его не содержит, добавление = миграция;
- presentation‑фильтр, прячущий `current`‑оценку (слово «проверено» имеет один источник — бейдж T7.65/ADR-0026);
- скрытие утверждения из ленты и из ответа: спорный claim остаётся видимым, но с честной отметкой
  «оспорено оператором» и без подтверждённого бейджа после пересчёта;
- новый `AuditEventType`: использованы уже существующие `operator_command_received` /
  `operator_command_completed`, продуктивного продюсера у которых до сих пор не было (факт 10 анализа).

## 5. Изменённые границы: чего это НЕ трогает

Пороги группировки, PSL-список, `group_source_graph`, правила rules engine и payload'ы config‑v1…config‑v18 —
без изменений; миграций нет; enum'ов новых нет; `ARCHITECTURE.md` не правился. Аудит пишется в той же
транзакции, что изменение (AGENTS §3). Отказы whole-way: `DisputeError` выходит из транзакции API и CLI →
откат, ни строки коррекции, ни события журнала.

## 6. Часть (б): «снять утверждение вручную» — остановлено по критерию, варианты на решение пользователя

Ни один вариант не реализован. Все четыре требуют либо запрещённого этой задачей шага, либо нарушают
инварианты:

1. **Новый тип команды `withdraw_claim`** + прямой перевод головы в `invalid` и вызов `start_cascade`.
   Требует: миграцию CHECK `operator_commands.type` (стоп-критерий) и новое значение `prepared_by` головы
   (тоже CHECK). Дополнительно: `start_cascade` (`packages/memory/cascade.py:454`) не имеет продуктового
   продюсера — его вызывают только тесты; её актёр bound CHECK‑списком. Цена: две миграции и новый путь,
   которого спека для оператора не предусматривает.
2. **Прямой UPDATE головы в `invalid` без типа команды.** Не требует миграций, но нарушает два инварианта
   сразу: статус знания меняет не rules engine (AGENTS §3), и голова «самоуничтожается» — на ближайшем тике
   worker пересчитает её из unchanged‑улик и вернёт `current`/E3 (факт 6 анализа). То есть получился бы
   бейдж-фликер на 60 с, а не снятое знание.
3. **Новая таблица-флаг «снято оператором»** (`claim_withdrawals`) со своим каскадом инвалидации зависимых.
   Решает вопрос честнее: знание помечается, а не переоценивается; но это новая таблица и новое долговременное
   состояние знания вне закрытого набора `current|pending|invalid` (§8.6) → миграция и правка §13/§14 спеки.
4. **Presentation‑фильтр**: витрина прячет утверждение пометкой, БД не меняется. Не требует миграций, прямо
   противоречит ADR-0026 и §13.5 (UI не назначает статус и не оформляет действующее знание по-своему) и
   оставило бы «снятое» утверждение в контексте сессий — то есть знанием оно бы продолжало работать.

Рекомендация агента: для стендового случая пользоваться спором (§2) — он убирает ложное «Проверено» и
оставляет полное следствие; если пользователю нужен именно долговременный статус «снято», наименее разрушительный
вариант — 3 (отдельная таблица + каскад, без права назначать grade), и он требует явного решения и отдельной
задачи с миграцией.

## 7. Тесты, закрепляющие решение

- `tests/unit/test_claim_dispute.py` (12): границы причины, нормирование адреса (http/https, query, хвостовой
  слэш, порт), fail-closed выбор пары среди улик claim'а, текст вопроса с цитатой statement'а и его потолок,
  полнота подписей для отказов спора, отсутствие нового enum‑значения в CHECK `prepared_by` миграции 0022,
  отмена = `valid = false` без удаления строки.
- `tests/scenario/test_claim_dispute.py` (10): реальный HTTP-путь → коррекция + лента + `pending` + задача
  пересчёта + вопрос; бейдж «Проверено» уходит **только после** пересчёта правилами (`insufficient_independence`,
  одна группа с основанием `correction:merge`); повтор = replay без дубликов; затронуты все утверждения, чьи
  улики используют эти источники, а связанные только `claim_dependencies` — нет (честный предел каскада §11.3);
  отказ подписан и ничего не пишет; второй оператор не может наложить вторую склейку на ту же пару; отмена
  возвращает E3 и сохраняет историю (в том числе прежнюю причину спора); без admin-токена — 401, при нездоровом
  снимке юнитов — 423; provenance называет спор высказыванием оператора.
- `tests/scenario/test_cli_claim_dispute.py` (6): `noezemactl claim-dispute …` → exit 0 с id коррекции и
  вопроса, actor `operator:hostctl`; повтор = идемпотентный повтор; `claim-dispute-cancel` → спор снят, строка
  осталась, после пересчёта прежняя E3 возвращается; отказы → exit 2 с кодом причины и без трейсов; полный uuid
  обязателен.
- `tests/unit/test_web_labels.py`: новые категории словаря (`graph_correction_kind`, `dispute_state`,
  `dispute_actor`) и краснота полноты по построению для нового актора/отказа спора.

## 8. Что остаётся открытым

- выбор варианта (б) — за пользователем (§6); в T7.81 (б) не реализована, и это не «недоделано», а
  остановка по стоп-критерию задачи;
- активация на стенде `.92`: шаги менеджера — `deploy/dev-stand/README.md` (раздел «Как оспорить утверждение»);
  агент к `.92` не обращался;
- спор по умолчанию работает только там, где у хоста есть артефакт прочтения пересказывающей страницы: без
  `observation_artifact_id` коррекция остаётся attestation'ом без provenance-цепочки, а §11.3 такого не
  требует для merge — но и не делает его проверяемым; отдельный кандидат — требовать артефактfail-closed.
