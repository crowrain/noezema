# ADR-0007: Scope оценки выводит доверенный хост (rules-v2)

Статус: accepted

Дата: 2026-09-17

## Контекст

Для `external_fact` и `temporal_fact` правило `requires_scope=true`
(§8.7, `claim_type_rules` в config snapshot): каждый supporting evidence
должен ПОКРЫВАТЬ scope claim. В rules-v1 покрытие —
`_scope_covers` (packages/memory/rules_engine.py): каждый КЛЮЧ scope
claim должен присутствовать в scope evidence с равным значением.

Оба scope придумывала модель свободной формой: scope claim — в
предложении куратора; scope evidence — хост копировал scope claim при
commit, но при переиспользовании claim (dedup по statement+type) и при
reassessment scope evidence = то, что модель написала в ДРУГОЙ сессии
для того же claim. Свободная форма не согласуется: в проверке T7.15
наблюдались РАЗНЫЕ ключи для одного предмета
(claim `{domain,entity,target,property}` vs evidence
`{object,subject,relation}`) → `scope_not_covered` → E1. E3 в T7.15
получился только потому, что вопрос диктовал scope-объект, скопированный
дословно в claim и в evidence. В замороженном корпусе v2 (50 вопросов)
такой подсказки нет ни в одном вопросе, и добавлять её нельзя — гейт
`external_temporal_e3` (§22.2) выполнялся бы по построению. На прогоне
EVAL-3b это одна из двух причин нулевого числа external/temporal
claims (docs/eval/EVAL-3b-postmortem.md).

Суть дефекта: входы, влияющие на grade, производила модель — в
противовес §3.7 (grade считает rules engine по evidence, их scope и
independence) и §11.2/AGENTS.md §3 (ID и другие grade-входы генерирует
хост, не LLM). Нормализация ключей/значений (вариант 2) не решает
проблему принципиально: конечный синоним-словарь не покрывает
свободного изобретения ключей («область_рассмотрения», «geo», …).

## Решение

**Scope, который проверяет rules engine, выводит доверенный хост**
(вариант 1 задачи T7.17), модельный free-form scope игнорируется для
покрытия и служит только аудитом/предложению:

1. **Claim scope** — из ВОПРОСА сессии (доверенный ввод: операторский
   или зафиксированный артефакт с origin) + типизированного `as_of`
   claim:
   - `as_of`: дата, названная в вопросе (детерминированный закрытый
     набор форм: русские/английские названия месяцев, `д.м.гггг`,
     ISO `гггг-мм-дд`; левейшее валидное совпадение). Дата вопроса
     ПЕРВИЧНА: модельный `as_of` не может сдвинуть опорную дату
     (иначе due/stale-механика §22.2 — `reverify_after = as_of + 30d` —
     управлялась бы моделью). Вопрос без даты → типизированный
     `as_of` claim (валидированная структура, не free-form);
   - `source_domains`: registrable domain источников, названных
     вопросом (та же гранулярность, что у independence-групп §11.3).
     Вопрос без источников → пустой список = нет ограничения.
2. **Evidence scope** — из PROVENANCE строки evidence (дurable
   `sources` row): registrable domain `canonical_uri` и
   `retrieved_at`; для не-source evidence — время наблюдения
   (commit time). При переиспользовании claim все строки evidence
   claim'а (включая созданные старой версией движка) ре-деривируются из
   provenance на месте (идемпотентно, в той же tx commit'а).
3. **Семантика покрытия** (каноническая, `host-scope-v1`,
   fail-closed):
   - дата D claim: evidence должен быть НАБЛЮДЁН не раньше D
     (`T >= D`). Источник, полученный раньше опорной даты, не может
     говорить о ней; источник, полученный не раньше D, — лучшее
     доступное свидетельство о состоянии на D (конвенция корпуса для
     «по состоянию на D» по стабильным фактам; строгое равенство
     дат технически невыполнимо — страницу нельзя дозапросить на
     прошлую дату). Отсутствие времени наблюдения при объявленной
     дате → НЕ покрывает (не пропуск);
   - source_domains claim: registrable domain evidence обязан быть
     среди них. Домен не назван вопросом → НЕ покрывает (subject
     другой). Отсутствие домена при объявленных доменах → НЕ
     покрывает;
   - не объявленные измерения не проверяются (вопрос без даты и
     источников → ограничение отсутствует).
4. **Legacy-данные**: scope без маркера `host-scope-v1` (free-form
   dict старой версии) оценивается ИСХОДНЫМ key-by-key предикатом без
   изменений. Апгрейд движка не переоценивает существующее знание ни
   в одну сторону (fail-closed в обе стороны); канонический claim
   scope НЕ покрывается legacy evidence scope (измерений там просто
   нет).
5. **Версия движка**: `rules-v1` → `rules-v2` (в assessment фиксируется
   версия; payload-правила, пороги §22.2, `requires_scope` и правило
   E3 — два независимых источника, минимум два source_assertion — не
   менялись).

Модельный free-form scope остаётся: в staging payload, в
`audit_events` (`claim_created`: `scope` = предложение модели,
`assessed_scope` = хост-деривация) — для аудита и отладки, но в
предикат не входит.

## Почему не другие варианты

- **Нормализация ключей/значений (вариант 2)**: конечный словарь
  синонимов не покрывает свободное изобретение ключей моделью — дефект
  остался бы, только уже на экзотических ключах. Нормализация дат
  (15.04.2026 = 2026-04-15) вхолощена в деривацию как часть
  детерминированного парсера даты вопроса.
- **Оставление свободного scope с проверкой «по смыслу» (вариант 3)**:
  хост не имеет семантики (NLP вне системы, §3.5 — локальная модель не
  входит в доверенный контур оценки). Единственные детерминированно
  проверяемые измерения — время наблюдения и источник (provenance),
  которые хост и проверяет.

## Следствия

- external/temporal claims больше не зависят от того, совпадут ли
  ключи, которые модель придумала для claim и evidence: путь к E3
  открыт при двух независимых источниках, названных в вопросе, и
  наблюдениях не раньше опорной даты;
- fail-closed сохранён и усилен: evidence из источника, не названного
  вопросом (другой subject), и source, полученный раньше опорной даты
  (другая дата), не поднимает grade — закрыто тестами
  `tests/scenario/test_scope_coverage.py`;
- хост может видеть scope в `claim_assessments.assessed_scope` и
  `evidence.scope` как машиночитаемый структурированный объект
  (маркер `scope_schema`, ISO-дата, list доменов), а не free-form dict
  — blind-гейт `blind_scope` (§22.2) работает без изменений
  (assessed_scope/evidence.scope не пусты);
- план сессии (`sessions.plan`) в деривацию НЕ входит: это предложение
  модели, и его URLs расширили бы source scope, который нужно
  покрывать, — модель влияла бы на grade-вход, что запрещено
  §3.7/§11.2. Вопрос — единственный scope-якорь;
- legacy БД (EVAL-3/EVAL-3b как улики) не переоцениваются: их
  free-form scope идёт через исходный предикат.
