# ADR-0007: Scope оценки выводит доверенный хост (rules-v2)

Статус: accepted

Дата: 2026-09-17

## Контекст

Для `external_fact` и `temporal_fact` правило `requires_scope=true`
(§8.7, `claim_type_rules` в config snapshot): каждый supporting evidence
должен ПОКРЫВАТЬ scope claim. В rules-v1 покрытие —
`_scope_covers` (packages/memory/rules_engine.py): каждый КЛЮЧ scope
claim должен присутствовать в scope evidence с равным значением.

Оба scope придумывала модель свободной формой: scope claim — в
предложении куратора; scope evidence — хост копировал scope claim при
commit, но при переиспользовании claim (dedup по statement+type) и при
reassessment scope evidence = то, что модель написала в ДРУГОЙ сессии
для того же claim. Свободная форма не согласуется: в проверке T7.15
наблюдались РАЗНЫЕ ключи для одного предмета
(claim `{domain,entity,target,property}` vs evidence
`{object,subject,relation}`) → `scope_not_covered` → E1. E3 в T7.15
получился только потому, что вопрос диктовал scope-объект, скопированный
дословно в claim и в evidence. В замороженном корпусе v2 (50 вопросов)
такой подсказки нет ни в одном вопросе, и добавлять её нельзя — гейт
`external_temporal_e3` (§22.2) выполнялся бы по построению. На прогоне
EVAL-3b это одна из двух причин нулевого числа external/temporal
claims (docs/eval/EVAL-3b-postmortem.md).

Суть дефекта: входы, влияющие на grade, производила модель — в
противовес §3.7 (grade считает rules engine по evidence, их scope и
independence) и §11.2/AGENTS.md §3 (ID и другие grade-входы генерирует
хост, не LLM). Нормализация ключей/значений (вариант 2) не решает
проблему принципиально: конечный синоним-словарь не покрывает
свободного изобретения ключей («область_рассмотрения», «geo», …).

## Решение

**Scope, который проверяет rules engine, выводит доверенный хост**
(вариант 1 задачи T7.17), модельный free-form scope игнорируется для
покрытия и служит только аудитом/предложению:

1. **Claim scope** — из ВОПРОСА сессии (доверенный ввод: операторский
   или зафиксированный артефакт с origin) + типизированного `as_of`
   claim:
   - `as_of`: дата, названная в вопросе (детерминированный закрытый
     набор форм: русские/английские названия месяцев, `д.м.гггг`,
     ISO `гггг-мм-дд`; левейшее валидное совпадение). Дата вопроса
     ПЕРВИЧНА: модельный `as_of` не может сдвинуть опорную дату
     (иначе due/stale-механика §22.2 — `reverify_after = as_of + 30d` —
     управлялась бы моделью). Вопрос без даты → типизированный
     `as_of` claim (валидированная структура, не free-form);
   - `source_domains`: registrable domain источников, названных
     вопросом (та же гранулярность, что у independence-групп §11.3).
     Вопрос без источников → пустой список = нет ограничения.
2. **Evidence scope** — из PROVENANCE строки evidence (дurable
   `sources` row): registrable domain `canonical_uri` и
   `retrieved_at`; для не-source evidence — время наблюдения
   (commit time). При переиспользовании claim все строки evidence
   claim'а (включая созданные старой версией движка) ре-деривируются из
   provenance на месте (идемпотентно, в той же tx commit'а).
3. **Семантика покрытия** (каноническая, `host-scope-v1`,
   fail-closed):
   - дата D claim: evidence должен быть НАБЛЮДЁН не раньше D
     (`T >= D`). Источник, полученный раньше опорной даты, не может
     говорить о ней; источник, полученный не раньше D, — лучшее
     доступное свидетельство о состоянии на D (конвенция корпуса для
     «по состоянию на D» по стабильным фактам; строгое равенство
     дат технически невыполнимо — страницу нельзя дозапросить на
     прошлую дату). Отсутствие времени наблюдения при объявленной
     дате → НЕ покрывает (не пропуск);
   - source_domains claim: registrable domain evidence обязан быть
     среди них. Домен не назван вопросом → НЕ покрывает (subject
     другой). Отсутствие домена при объявленных доменах → НЕ
     покрывает;
   - не объявленные измерения не проверяются (вопрос без даты и
     источников → ограничение отсутствует).
4. **Legacy-данные**: scope без маркера `host-scope-v1` (free-form
   dict старой версии) оценивается ИСХОДНЫМ key-by-key предикатом без
   изменений. Апгрейд движка не переоценивает существующее знание ни
   в одну сторону (fail-closed в обе стороны); канонический claim
   scope НЕ покрывается legacy evidence scope (измерений там просто
   нет).
5. **Версия движка**: `rules-v1` → `rules-v2` (в assessment фиксируется
   версия; payload-правила, пороги §22.2, `requires_scope` и правило
   E3 — два независимых источника, минимум два source_assertion — не
   менялись).

Модельный free-form scope остаётся: в staging payload, в
`audit_events` (`claim_created`: `scope` = предложение модели,
`assessed_scope` = хост-деривация) — для аудита и отладки, но в
предикат не входит.

## Почему не другие варианты

- **Нормализация ключей/значений (вариант 2)**: конечный словарь
  синонимов не покрывает свободное изобретение ключей моделью — дефект
  остался бы, только уже на экзотических ключах. Нормализация дат
  (15.04.2026 = 2026-04-15) вхолощена в деривацию как часть
  детерминированного парсера даты вопроса.
- **Оставление свободного scope с проверкой «по смыслу» (вариант 3)**:
  хост не имеет семантики (NLP вне системы, §3.5 — локальная модель не
  входит в доверенный контур оценки). Единственные детерминированно
  проверяемые измерения — время наблюдения и источник (provenance),
  которые хост и проверяет.

## Следствия

- external/temporal claims больше не зависят от того, совпадут ли
  ключи, которые модель придумала для claim и evidence: путь к E3
  открыт при двух независимых источниках, названных в вопросе, и
  наблюдениях не раньше опорной даты;
- fail-closed сохранён и усилен: evidence из источника, не названного
  вопросом (другой subject), и source, полученный раньше опорной даты
  (другая дата), не поднимает grade — закрыто тестами
  `tests/scenario/test_scope_coverage.py`;
- хост может видеть scope в `claim_assessments.assessed_scope` и
  `evidence.scope` как машиночитаемый структурированный объект
  (маркер `scope_schema`, ISO-дата, list доменов), а не free-form dict
  — blind-гейт `blind_scope` (§22.2) работает без изменений
  (assessed_scope/evidence.scope не пусты);
- план сессии (`sessions.plan`) в деривацию НЕ входит: это предложение
  модели, и его URLs расширили бы source scope, который нужно
  покрывать, — модель влияла бы на grade-вход, что запрещено
  §3.7/§11.2. Вопрос — единственный scope-якорь;
- legacy БД (EVAL-3/EVAL-3b как улики) не переоцениваются: их
  free-form scope идёт через исходный предикат.

## Уточнение T7.18 (2026-09-18): относительная опорная дата выводится хостом

### Дефект, найденный на шаге 1 перезапуска EVAL-3c (прогон 91c1be43,
БД `noezema-eval-draft2`, оставлена как улика)

Вопрос корпуса «Какова ключевая ставка Банка России **на текущую
дату**… (cbr.ru + consultant.ru)» дал claim `temporal_fact`
«Ключевая ставка Банка России составляет 14,00%» со статусом
hypothesis/E1 (`scope_not_covered`). Причина: `parse_question_date`
распознаёт только **явные** даты; «на текущую дату» → `None` →
`derive_claim_scope` брал **типизированный `as_of` модели**. Модель
написала `as_of = 2026-09-19` (завтра), evidence был получен
`2026-09-18` → evidence раньше опорной даты → `scope_not_covered` →
E1. То есть для вопросов «на текущую дату» вход, влияющий на grade,
**по-прежнему производила модель** — ровно то, что ADR-0007 должен был
исключить.

Отчёт T7.17 утверждал, что «на текущую дату» «поддерживается». По
коду это не так: тест
`tests/unit/test_scope.py::test_parse_question_date_no_date`
закреплял лишь, что `parse_question_date` НЕ видит «на текущую дату»
(возвращает `None`) — то есть закрывал путь, который и уводил
опорную дату в модельный `as_of`. Это поправка к отчёту T7.17.

### Решение

1. **Хост распознаёт относительные формы опорной даты** в вопросе —
   закрытый детерминированный набор (`question_uses_relative_date`,
   `packages/memory/scope.py`): «на текущую дату», «на сегодня»,
   «сейчас», «текущий/текущая» (все падежные формы по стволу),
   «as of the current date», «as of today», «currently». По замороженному
   корпусу `question-set-v2.jsonl` реально встречаются ровно две —
   «на текущую дату» (20 вопросов) и «сейчас» (3 вопроса); полный
   закрытый набор покрыт.
2. **Для относительных форм опорная дата = дата сессии по доверенным
   часам хоста (UTC)**, а не `as_of` модели. Якорь — **начало сессии**
   (`sessions.created_at`, часы хоста/БД), а не момент commit:
   (а) «текущая дата» в вопросе = дата, на которую задан вопрос =
   начало сессии; (б) любой evidence сессии наблюдается не раньше её
   начала (одни часы), поэтому относительный claim покрывается
   evidence той же сессии; (в) момент commit для сессии, перешагнувшей
   полночь, сдвинул бы опорную дату назад относительно уже полученного
   в первой части сессии evidence (ложный `scope_not_covered`).
3. **Модельный `as_of` не сдвигает опорную дату** ни вперёд, ни назад,
   когда вопрос несёт дату-якорь (явную или относительную); он
   сохраняется только в строке claim и в staging/audit (как
   free-form-предложение модели).
4. **Вопрос без даты (ни явной, ни относительной) — текущее поведение
   сохранено**: опорная дата = типизированный `as_of` claim
   (валидированная структура, не free-form). Решение по корпусу: в
   `question-set-v2.jsonl` все «текущие» temporal-вопросы несут
   относительную форму (теперь хост-деривация), все факты с прошлой
   датой — явную; бездатовые вопросы — timeless external/historical
   факты (`as_of` опционален, обычно `None` → ограничения по дате нет,
   claim стабилен между днями) и follow-up-вопросы переиспользования.
   Привязка бездатовых вопросов к дате сессии навязала бы freshness-
   проверку timeless-фактам и деградировала бы переиспользование
   между днями (старый evidence оказывался бы «ранее» нового якоря,
   предикат `all(...)` не покрывал).
5. **Fail-closed сохранён**: evidence, полученный раньше явной даты
   вопроса, по-прежнему не покрывает; для относительных форм — раньше
   даты сессии. Предикат покрытия (`_canonical_covers`) не менялся.

### Версии и заморозка

- `rules_version` **не меняется** — остаётся `rules-v2`: не менялся сам
  rules engine, предикат покрытия, пороги §22.2, `claim_type_rules`,
  `requires_scope` и правило E3; изменилась только хост-деривация
  опорной даты (сторона хоста, `packages/memory/scope.py`).
- `rules_hash` **не меняется** — это хэш payload'а `claim_type_rules`
  (замороженный конфиг), который не тронут.
- Базовая дата due/stale (`reverify_after = as_of + 30d`, §22.2)
  **не меняется** — по-прежнему от типизированного `as_of` claim.
- Замороженные `config-v2/v3-payload.json` и `question-set-v2.jsonl`
  (их хэши) не тронуты.

### Известное следствие (переиспользование между днями)

Для относительного claim опорная дата на каждой новой сессии
задаётся датой **этой** сессии. При переиспользовании claim между
днями (якорная сессия и follow-up в разные календарные дни) evidence
из более раннего дня оказывается «ранее» нового якоря и по
неизменённому предикату `all(...)` не покрывает — claim может
опуститься до E1. Это взаимодействие существует и в T7.17 (там якорь
также «ехал» вперёд через модельный `as_of` = «сегодня»), T7.18 его не
вводит и не меняет; в однодневных прогонах (шаг 1 smoke, 3 вопроса)
не срабатывает.

## Уточнение T7.25 (2026-09-21): переиспользование между днями — корректный fail-closed, не дефект

### Вопрос

Последствие выше стало блокером длинного прогона: EVAL-4 (69 сессий,
оценка 9,5–20 ч, EVAL-4-freeze §3.2) практически неизбежно пересекает
00:00 UTC; попытка запуска EVAL-4c 2026-09-21 19:06 UTC была
остановлена через минуту именно по этому риску. Задача T7.25: решить,
дефект ли это. Варианты: (а) корректный fail-closed — данные
устарели, E1 правильно, ограничение «утренний старт» —
операционное; (б) смешение двух механизмов — scope-покрытие делает
работу freshness/reassessment, и вместо календарного дня нужно окно
допуска; (в) иное.

**Решение: (а). Не дефект. Код не тронут.** Предикат покрытия и
деривация опорной даты не изменены; `rules_version` остаётся
`rules-v2`, `rules_hash` — без изменений (`claim_type_rules` не
тронуты), пороги §22.2, замороженные payload'ы config-v2…v5 и корпуса
v2/v3 — без изменений (хэши перепроверены 2026-09-21).

### Обоснование спецификацией

1. **Покрытие — предикат предмета, а не часы.** §11.3: «Источник
   поддерживает claim только в пределах scope и provenance»; §8.7:
   правило задаёт «предикат покрытия claim scope»; §6.4: grade
   вычисляет rules engine по evidence set, их scope, independence
   groups и версии правил. Опорная дата — часть scope claim'а:
   относительный claim, созданный в день N, — это «X на день N». На
   день N+1 scope переиспользуемого claim'а — «X на день N+1»
   (вопрос — единственный scope-якорь). Evidence дня N не говорит о
   состоянии на день N+1 — ровно как и в случае явной даты: источник,
   полученный в день N, не говорит о «на день N+1» (один и тот же
   предикат, fail-closed с T7.17: «Источник, полученный раньше
   опорной даты, не может говорить о ней»). Собственный
   машиночитаемый пример правила в спеке определяет покрытие как
   `every(scope_covers_claim) == true` (§8.7) — по ВСЕМ
   supporting-evidence.
2. **Хост-деривированная относительная дата и явная дата вопроса —
   один и тот же вид входов** (оба — доверенный ввод хоста; модельный
   `as_of` не сдвигает ни одну). Строгий предикат для одной и окно
   для другой — произвольная асимметрия: §8.7 задаёт ОДИН предикат на
   тип claim, а не на происхождение даты.
3. **Вариант (б) ошибочен в посылке.** due/stale — другой механизм,
   который работу покрытия не делает: §8.6 «Истечение срока меняет
   freshness, но не confidence»; §8.2 «Confidence … не [меняется] из-
   за одного течения времени». due/stale отслеживает расписание
   перевалидации (`reverify_after = as_of + окно volatility`) и
   кормит гейт g6; он не снижает и не повышает grade. Claim может
   быть одновременно fresh и не покрыт — это как раз случай явной
   даты. Claim T7.25-сценария — E1 И fresh одновременно (закреплено
   тестом): два независимых поля, ровно как в спеке (§20.3 —
   контроль смешения confidence/freshness/lifecycle — независимые
   поля).
4. **Окно не имеет основания в спеке и ломает заморозку.** Поля
   правила §8.7 (kinds, счётчики, AND/OR, предикат покрытия, max
   grade, volatility/reverify_after) не содержат окна покрытия. Окно,
   выведенное из volatility (30 дней), означало бы «на текущую дату» =
   E3 по evidence 29-дневной давности — ровно то смешение
   (grade из течения времени), которое запрещают §8.2/§8.6, и
   противоречие корпорус-конвенции «по состоянию на D». Новое поле в
   `claim_type_rules` изменило бы `rules_hash` — запрещено для
   замороженных payload'ов config-v2…v5 и §22.2 («SLO и пороги
   меняются только до нового evaluation run с новой config version»).
5. **Вариант (в) (зафиксировать scope при создании / dedup с датой)
   противоречит решению ADR** «вопрос — единственный scope-якорь»:
   follow-up-вопрос «на текущую дату» в день N+1 получал бы claim о
   дне N — ответ «про вчера» на вопрос «про сегодня», scope-несоответствие
   в обратную сторону. Fail-closed говорит «о сегодня я не знаю» (E1),
   а не «вчера-значимо = сегодня-значимо».
6. **Взаимодействие уже задокументировано как известное следствие, а
   не как дефект** (уточнение T7.18 выше): оно существовало и в T7.17
   (модельный `as_of` = «сегодня» тоже «ехал» вперёд), T7.18 его не
   вводит и не меняет.

### Новое следствие (зафиксировано как факт, не дефект)

В прогоне, пересекающем полночь, относительный claim, созданный до
полночи и переиспользованный после, опускается до E1 и **как правило
остаётся на нём до конца прогона**:

- idempotent-рифетч T7.11 НЕ обновляет `sources.retrieved_at` для
  неизменённого контента (source-row переиспользуется по content
  hash) — повторный фетч неизменённой страницы не создаёт нового
  evidence (identity_hash неизменён → dedup);
- предикат `every(...)` идёт по ПОЛНОМУ evidence-set claim'а: даже
  если новый evidence появляется (страница изменилась), старая
  непокрывающая строка остаётся в наборе (строки evidence
  неизменяемы) — claim остаётся E1.

Это ожидаемый и честный результат (EVAL-3-freeze §9.6: «провал гейта
— результат»; прогон не останавливается и не переигрывается) — и
именно поэтому ограничение «старт утром UTC» существует: это
операционное митигирование (снижает вероятность взаимодействия
внутри прогона), а не дефект кода. Оно остаётся в чек-листе
(EVAL-4-freeze §6, п.8); если прогон всё же пересечёт полночь, E1-
опускания «текущих» temporal-claim'ов и исходы гейтов по ним
