# ADR-0032: Опора ответа на уже записанное знание — факультативное поле кураторского ответа, payload существующего события, отдельная связка карточки (T7.82(б))

- Статус: **proposed** (код, тесты и payload `config-v19` сделаны в T7.82(б), коммит `fff30ba`; активация на
  стенде .92 — за менеджером)
- Дата: 2026-10-09
- Контекст: замер подставки .92 (сессия `f0d7e844`, config-v18): ответ использовал уже записанное утверждение
  `9266248e…` («годовая инфляция 2025 = 5,59%», E4) из своего контекст-пака, но карточка вопроса показывала
  только два новых claims. Связь «этот вывод опирается на прежнее знание» не была видна ни оператору, ни ленте.

## 1. Почему это не перепроверка и не переоценка

Три разные вещи нельзя склеивать:

1. **перепроверка** (T7.34/T7.73): новая улика проверяет утверждение → `claim_reverified`, новая оценка,
   fail-closed отказ предложения при неразрешимом id;
2. **оценка**: grade/confidence производит только rules engine (§3), ни куратор, ни витрина;
3. **опора в выводе**: куратор использовал прежнее утверждение как готовое знание, не проверяя его заново.

Для (3) нет ни права, ни необходимости менять строку claim или оценку. Поэтому операция не вводится:
по опертому утверждению не выполняется ни одной staging-операции, не пишется `claim_reverified`, не
начисляется оценка, head и строка claim не изменяются. Это ровно тот же принцип, что у дедуп-повтора
(T7.74): связь витрины строится поверх уже существующих записей.

## 2. Канал записи: payload уже существующего `claim_created`

Новый AuditEventType не заводится (список закрыт, §3; прецедент дедуп-повтора T7.74), миграции нет:
факт живёт в payload события фиксации кураторского предложения:

- `relied_claim_ids` — канонические полные uuid-строки разрешённых опор;
- `relied_claims_rejected` — честные причины отказа каждого неразрешённого id (до 10 строк).

Ключи появляются только когда они непустые: payload старых сессий и сессий без опоры байт в байт прежний.
CuratorProposal (`extra="forbid"`) получает факультативное поле `relied_claim_ids: list[str]` без лимита в
схеме — специально: лишнее и мусорное отбраковывает не pydantic-гейт всего предложения, а хостовый
разрешатель (иначе один выдуманный id крал бы весь вывод сессии). Полем занимался и промпт: curator-v9 —
тело curator-v8 байт в байт + пункт протокола + правило 10 (3 ханка diff); без разрешения схемы поле было
бы недоступно движку (response schema строится из pydantic-модели).

## 3. Разрешение id: тот же строгий разрешатель, иная дисциплина отказа

`resolve_claim_reference` против `_pack_claim_ids(knowledge)` (строки `[c:<uuid>]` контекстного пакета):
полный UUID или однозначный hex-префикс. Отличие от гейта перепроверки осознанное: опора — метка честности,
а не операция, поэтому неразрешимый id не роняет предложение, а получает причину отказа в том же payload
(«claim … is not visible to the session», «no visible claim matches prefix …»). Дедупликация полного id и
его же префикса; потолок записи `RELIED_CLAIMS_LIMIT=8`.

Разрешитель на витрине не повторяется: карточка читает уже разрешённые канонические id из payload
(`jsonb_array_elements_text` с uuid-регуляркой как гардом от мусора в исторических строках), поэтому
витрина не может показать то, что хост не разрешил.

## 4. Витрина: отдельная связка «использовано из знаний»

RELATION_KEYS дополнен значением `relied`, но `touched_claims_cte` (источник created/reverified/reused)
его не выдаёт — семантика прежних рангов результатов не изменилась. Опертые claims — отдельный блок
карточки под записанными выводами (`card.relied_claims`, потолок `MAX_RELIED_CLAIMS=16`): бейдж и строки
подтверждения — тот же `assessment_view`/`describe_verification` по действующей голове (пересчёта нет),
уже показанные в основном блоке claims исключаются, подписи — только из словаря labels (полноту проверяет
`tests/unit/test_web_labels.py`). Слово «проверено» блок не утверждает сам: оно приходит только бейджем
прежней оценки (§T7.65 дисциплина).

## 5. Промпт и конфигурация

curator-v9 (`8897e6c5d7fb…`) — факультативность подчёркнута: «поле можно не приводить вовсе», пустое — `[]`;
перепроверка по-прежнему идёт через `existing_claim_id`, и куратору сказано различать эти два случая.
config-v19 = config-v18 ровно с одной правкой (пин curator-v9), canonical `4d76c000a873…` (файл — другое
число, дuality AGENTS §6); payload'ы v1…v18 не переписаны, v18 (`b5605e4eb04d…`) — documented-откат;
bootstrap/reset-db dev-стенда по умолчанию активируют v19.

## 6. Что НЕ тронуто

Закрытый список AuditEventType и миграции; staging-модель (§3); правила оценки и пороги; `validate_against`
(гейт evidence/question-ссылок не трогает relied-поле); промпты explorer-v9/curator-v8 и все прежние;
`touched_claims_cte`, `claim_assessments.created_in_session` как источник created/reverified/reused;
бюджеты карточки вопросов (≤4 SELECT списка «Мои вопросы» — relied-блок добавлен только в карточку ответа).

## 7. Тесты

`tests/scenario/test_relied_claims.py` (3): полный id + тот же id префиксом → один канонический id;
выдуманный uuid и мусор → отказные причины, сессия succeeds; нет `claim_reverified`, нет новой строки
`claim_assessments`, head прежний, staging сессии — только claim+evidence; карточка: блок
«использовано из знаний» с прежним бейджем E3 и без дублей основного блока; предложение без нового поля →
payload события прежний (набор ключей байт в байт). `tests/unit/test_dev_stand_scripts.py` — дефолт v19,
откат v18, canonical-префиксы. Краснота на прежнем коде доказана временным откатом `packages apps`: поле
отвергается `extra="forbid"`, 2 теста красные, контрольный зелёный.
