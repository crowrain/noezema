# ADR-0032: Опора ответа на уже записанное знание — факультативное поле кураторского ответа, payload существующего события, отдельная связка карточки (T7.82(б))

- Статус: **proposed** (код, тесты и payload `config-v19` сделаны в T7.82(б), коммит `fff30ba`; активация на
  стенде .92 — за менеджером)
- Дата: 2026-10-09
- Контекст: замер подставки .92 (сессия `f0d7e844`, config-v18): ответ использовал уже записанное утверждение
  `9266248e…` («годовая инфляция 2025 = 5,59%», E4) из своего контекст-пака, но карточка вопроса показывала
  только два новых claims. Связь «этот вывод опирается на прежнее знание» не была видна ни оператору, ни ленте.

## 1. Почему это не перепроверка и не переоценка

Три разные вещи нельзя склеивать:

1. **перепроверка** (T7.34/T7.73): новая улика проверяет утверждение → `claim_reverified`, новая оценка,
   fail-closed отказ предложения при неразрешимом id;
2. **оценка**: grade/confidence производит только rules engine (§3), ни куратор, ни витрина;
3. **опора в выводе**: куратор использовал прежнее утверждение как готовое знание, не проверяя его заново.

Для (3) нет ни права, ни необходимости менять строку claim или оценку. Поэтому операция не вводится:
по опертому утверждению не выполняется ни одной staging-операции, не пишется `claim_reverified`, не
начисляется оценка, head и строка claim не изменяются. Это ровно тот же принцип, что у дедуп-повтора
(T7.74): связь витрины строится поверх уже существующих записей.

## 2. Канал записи: payload уже существующего `claim_created`

Новый AuditEventType не заводится (список закрыт, §3; прецедент дедуп-повтора T7.74), миграции нет:
факт живёт в payload события фиксации кураторского предложения:

- `relied_claim_ids` — канонические полные uuid-строки разрешённых опор;
- `relied_claims_rejected` — честные причины отказа каждого неразрешённого id (до 10 строк).

Ключи появляются только когда они непустые: payload старых сессий и сессий без опоры байт в байт прежний.
CuratorProposal (`extra="forbid"`) получает факультативное поле `relied_claim_ids: list[str]` без лимита в
схеме — специально: лишнее и мусорное отбраковывает не pydantic-гейт всего предложения, а хостовый
разрешатель (иначе один выдуманный id крал бы весь вывод сессии). Полем занимался и промпт: curator-v9 —
тело curator-v8 байт в байт + пункт протокола + правило 10 (3 ханка diff); без разрешения схемы поле было
бы недоступно движку (response schema строится из pydantic-модели).

## 3. Разрешение id: тот же строгий разрешатель, иная дисциплина отказа

`resolve_claim_reference` против `_pack_claim_ids(knowledge)` (строки `[c:<uuid>]` контекстного пакета):
полный UUID или однозначный hex-префикс. Отличие от гейта перепроверки осознанное: опора — метка честности,
а не операция, поэтому неразрешимый id не роняет предложение, а получает причину отказа в том же payload
(«claim … is not visible to the session», «no visible claim matches prefix …»). Дедупликация полного id и
его же префикса; потолок записи `RELIED_CLAIMS_LIMIT=8`.

Разрешитель на витрине не повторяется: карточка читает уже разрешённые канонические id из payload
(`jsonb_array_elements_text` с uuid-регуляркой как гардом от мусора в исторических строках), поэтому
витрина не может показать то, что хост не разрешил.

## 4. Витрина: отдельная связка «использовано из знаний»

RELATION_KEYS дополнен значением `relied`, но `touched_claims_cte` (источник created/reverified/reused)
его не выдаёт — семантика прежних рангов результатов не изменилась. Опертые claims — отдельный блок
карточки под записанными выводами (`card.relied_claims`, потолок `MAX_RELIED_CLAIMS=16`): бейдж и строки
подтверждения — тот же `assessment_view`/`describe_verification` по действующей голове (пересчёта нет),
уже показанные в основном блоке claims исключаются, подписи — только из словаря labels (полноту проверяет
`tests/unit/test_web_labels.py`). Слово «проверено» блок не утверждает сам: оно приходит только бейджем
прежней оценки (§T7.65 дисциплина).

## 5. Промпт и конфигурация

curator-v9 (`8897e6c5d7fb…`) — факультативность подчёркнута: «поле можно не приводить вовсе», пустое — `[]`;
перепроверка по-прежнему идёт через `existing_claim_id`, и куратору сказано различать эти два случая.
config-v19 = config-v18 ровно с одной правкой (пин curator-v9), canonical `4d76c000a873…` (файл — другое
число, duality AGENTS §6); payload'ы v1…v18 не переписаны, v18 (`b5605e4eb04d…`) — documented-откат;
bootstrap/reset-db dev-стенда по умолчанию активируют v19.

## 6. Что НЕ тронуто

Закрытый список AuditEventType и миграции; staging-модель (§3); правила оценки и пороги; `validate_against`
(гейт evidence/question-ссылок не трогает relied-поле); промпты explorer-v9/curator-v8 и все прежние;
`touched_claims_cte`, `claim_assessments.created_in_session` как источник created/reverified/reused;
бюджеты карточки вопросов (≤4 SELECT списка «Мои вопросы» — relied-блок добавлен только в карточку ответа).

## 7. Тесты

`tests/scenario/test_relied_claims.py` (3): полный id + тот же id префиксом → один канонический id;
выдуманный uuid и мусор → отказные причины, сессия succeeds; нет `claim_reverified`, нет новой строки
`claim_assessments`, head прежний, staging сессии — только claim+evidence; карточка: блок
«использовано из знаний» с прежним бейджем E3 и без дублей основного блока; предложение без нового поля →
payload события прежний (набор ключей байт в байт). `tests/unit/test_dev_stand_scripts.py` — дефолт v19,
откат v18, canonical-префиксы. Краснота на прежнем коде доказана временным откатом `packages apps`: поле
отвергается `extra="forbid"`, 2 теста красные, контрольный зелёный.

## 8. Дополнение (T7.115, 2026-10-15): опора из финальной rationale исследователя (случай 96a0c535)

Приёмка стенда `.92`: сессия `96a0c535`, вопрос `d2afe4a6` — финальный ответ исследователя
цитирует записанное знание по id («claims c:136a0ca0-…», «claim c:44bd1460-…»), но куратор
предложил 0 claims и не заполнил `relied_claim_ids`: карточка «Ответ не записан» показала
0 утверждений и ни одной связи «использовано из знаний», хотя ответ целиком лежит в знании.
Причина системная: запрос куратора не содержит финальной rationale исследователя, и в
разрешитель опоры (§3) не приходит ничего, кроме декларации куратора.

**Решение.** Хост добавляет в опору id ссылок `c:<полный uuid>` или `c:<hex-префикс не короче 8>`
из **финального** ответа (public_rationale шага `complete`) при условиях: (а) ссылка ровно этой
формы (регулярка с границей слова; висячий дефис и приклеенное к слову `c:` не матчатся);
(б) id разрешается тем же разрешителем по тому же контекст-паку, что и опора куратора:
`resolve_claim_reference` против `_pack_claim_ids(knowledge)` — неоднозначный префикс остаётся
честным отказом, хост не догадывается; (в) id не является операцией этой сессии
(перепроверка/склейка, включая конвертированные гейтом value-dup: перепроверка остаётся
операцией и в опору не дублируется). Приоритет за куратором: его id уже в списке;
потолок `RELIED_CLAIMS_LIMIT` общий, id куратора считаются первыми. Промежуточные шаги
не участвуют: парсится только финальный текст. Отклонённый COMPLETE (гейт покрытия T7.21)
— не ответ и не сохраняется.

**Хранение финального текста.** Целиком rationale сохраняется в памяти сессии:
`SessionContext.final_answer_rationale`. Ни аудит-обрезок `[:500]`, ни оконный сигнал
`final_rationale_signal` не пригодны: финальный ответ длиннее окна, а ссылка не должна
обрезаться. Новой схемы нет: поле живёт только в процессе сессии, в БД ничего не пишется
(прецедент `final_rationale_signal`, T7.82 часть а).

**Payload.** Опора из ответа объединяется с кураторской в тех же `relied_claim_ids`
и `relied_claims_rejected` (отказные строки с префиксом `answer[k]:`). Аддитивный ключ
`relied_from_explorer` — какие id опоры добавил хост из ответа, а не куратор. Все ключи
записываются только непустыми: сессии без ссылок в ответе остаются байт в байт прежними
(пинится и случаем «ссылка есть только в промежуточном шаге»).

**Целый отказ.** Если предложение куратора отклонено целиком (любой из четырёх гейтов)
и раунд исправления T7.106 тоже не принят, `CLAIM_CREATED` не пишется вообще (`return 0, 0`)
— опора из ответа никуда не записывается. Это прежнее поведение, оно не изменено: опора живёт
только в payload события фиксации, отдельного хранилища нет.

**Не тронуто.** `CuratorProposal` (новый источник id — хостовый код, поле модели не менялся),
промпты и конфигурации, rules engine, границы коммита и staging, миграции, `AuditEventType`,
карточка (она читает `relied_claim_ids` из payload как прежде, подписи не менялись).

**Тесты.** `tests/scenario/test_relied_from_answer_t7115.py` (7): реплей случая — три id
(полные и 8-hex префикс) из финального ответа при 0 claims куратора попадают в опору и в блок
карточки «использовано из знаний»; id вне пака и неоднозначный префикс — честные отказы;
объединение с опорой куратора (приоритет, отсутствие дублей, общий потолок); id операции
сессии не дублируется; ссылка только в промежуточном шаге — набор ключей payload байт в байт
прежний; опора переживает раунд исправления куратора. `tests/unit/test_relied_from_answer_t7115.py`
(9): чистый `_relied_from_answer` — формы ссылки, видимость только по паку, дедуп, исключение
операций, потолок. Краснота на `7478935`: 6 из 7 сценарных тестов и весь unit-модуль
(отсутствующий импорт); тест-гарант байтовой совместимости зелёный на обеих сторонах —
он и задуман как регрессия.

## 9. Дополнение (T7.116 часть в, 2026-10-15): снятие хостовой упаковки «c:» со ссылок опоры (случай 53be7fd6)

**Дефект.** Хост сам печатает ссылки утверждений конспекта контекст-пака в формах
`[c:<uuid>]` и `c:<uuid>` (`pack_claim_ids`), оператор переносит их в `relied_claim_ids` /
`existing_claim_id`, а разрешитель T7.34 понимал только «голый» uuid или hex-префикс: живой
стенд давал `unparseable claim reference` на `c:44bd1460-bb72-4521` и
`c:c6729d4c-72a7-4f74` — отказ на ссылке, созданной самим хостом.

**Правка.** `resolve_claim_reference` (`packages/memory/service.py`) перед разбором снимает
внешние квадратные скобки и/или метку `c:` (пробелы по краям тоже) — ровно один раз:
`c:c:<uuid>` остаётся непарсируемым (двойная упаковка — случай кураторского ответа, не хостовый
конспект); содержимое скобок без `c:` не трогается — прежний отказ сохраняется. После этого
разбор прежний: полный uuid или однозначный hex-префикс от 8. Наборы ошибок и тексты не
изменены; гейт якоря `existing_claim_id` (T7.73), `_pack_claim_ids` и промпты не тронуты.

**Тесты.** `tests/unit/test_claim_reference.py` 12 -> 19: полный uuid с меткой, усечённый префикс
с меткой, скобочная форма, пробелы по краям, регистронезависимость и одинарность метки,
`c:` с неоднозначным префиксом — прежний отказ `ambiguous_claim_prefix`, `c:` с невидимым по паку
утверждением — прежний отказ. Краснота до кода на `8ffb4c9`: семь новых тестов красные.

## 10. Дополнение (T7.128 часть 2, 2026-10-21): опора переживает отказ предложения целиком группы (а) (стендовый случай c1)

**Дефект.** Сессия c1 (a53d85b0, config-v29): предложение куратора — одна новая операция
(прогноз МЭР 2,2% на 2026 год) и семь `relied_claim_ids`. Единственную операцию снял гейт
периода/даты прогноза (`curator_reject_kind = claim_period_not_near_value`); так как новых
операций в предложении не осталось, хост отказал предложению ЦЕЛИКОМ — и в первом ответе, и
после раунда исправления. При отказе целиком `claim_created` не пишется вовсе, поэтому
разрешённая опора терялась, а карточка вопроса говорила «Ответ не записан», хотя ответ жил в
памяти: ровно те семь утверждений контекст-пака, на которые оперся вывод.

**Разделение отказов (группы).** Группа (а) — проверки, которые судят РОВНО ту операцию,
которую снимают: гейт «значение на связи» (T7.108, ADR-0034 §10) и гейт периода/даты прогноза/
даты документа (T7.121, ADR-0038 §2–§3). Группа (б) — проверки, которым безразличен разбор
предложения по операциям: структурные проблемы и `search_statements`, пустые `claims` при
объявленном в сводке намерении (T7.123), неразрешимая ссылка перепроверки (T7.34/T7.105),
`temporal_fact` без даты (T7.84), движок правил (T7.9). Группа (б) не тронута: её отказ
целиком остаётся отказом целиком, опора его не спасает.

**Правило.** Если после снятия ВСЕХ новых операций предложения группы (а) в этом же предложении
есть РАЗРЕШЁННЫЕ `relied_claim_ids` (тот же разрешатель T7.34/ADR-0032 §3, тот же контекст-пак
сессии, тот же потолок), то ВТОРОЕ предложение (после ровно одного раунда исправления, ADR-0034
§9) принимается как обычное частичное применение варианта B (T7.105): `claim_created` с
`relied_claim_ids`, `rejected_operations` (снятая операция и её прежняя именованная причина),
`claims_proposed: 1`, `claims_applied: 0`, `correction_round`. Ни одна снятая гейтом операция в
знание не попадает; ни одного нового типа события, ключа или миграции нет. Раунд исправления
предлагается по-прежнему: спасение возможно только на втором ответе, поэтому первое предложение
отказывается целиком как раньше.

**Порядок шагов границы.** Разрешение опоры перенесено ВЫШЕ гейтов группы (а) (было после гейта
значения): опоре нужно знать свой итог в момент, когда хост решает, отказывать ли предложению
целиком. Разрешение читает только контекст-пак сессии, поэтому порядок прочих проверок, строки
причин и журналы не изменились; сессии без такого случая остаются байт в байт прежними.

**Что НЕ изменено.** Отказ группы (б); снятие отдельной операции и её журнал; отказ отдельных id
опоры (`relied_claims_rejected`); витрина (блок «использовано из знаний» и карточка
`answered_from_relied` T7.121 читают payload как прежде); промпты и конфигурация.

**Тесты.** `tests/scenario/test_relied_survives_gate_rejection_t7128.py` (3): (а) гейт периода
снял все операции — после раунда ответ зафиксирован из одних опор, журнала отказа нет, снятая
операция в базу не попала, карточка `answered_from_relied`; (б) тот же сценарий без опор — прежний
отказ целиком (`curator_reject_kind`, additive `correction_round`), карточка `no_answer`; (в)
неразрешимая ссылка перепроверки — отказ группы (б) целиком и после раунда, опора не спасает.
Краснота на `c98e80e` (detached worktree): (а) красный, (б) и (в) зелёные по построению — это
регрессии неизменного поведения.
