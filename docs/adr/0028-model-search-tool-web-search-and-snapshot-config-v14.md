# ADR-0028: Инструмент поиска для модели — имя по §5.7, гейты по профилям, находки не становятся доказательствами; снапшот config-v14 без artifact.create (T7.71, §5.7/§5.12/§5.12.1, ADR-0027 пункт 4)

Статус: **proposed** (реализация T7.71 выполнена 2026-10-06 — код, тесты, payload `config-v14`,
explorer-v6; решения ниже приняты харнессом в пределах уже согласованного пункта 4 ADR-0027 и требуют
подтверждения пользователем в части имени и отказа профилю sealed — см. «Решения, требующие подтверждения»)

Дата: 2026-10-06 (анализ — STATUS §T7.70/T7.71 раздел «анализ до кода»; план — `docs/web-access-design.md` §6)

Контекст: решение пользователя 2026-10-06 (c) — «поиск модели нужен», вариант D поверх A (ADR-0027).
Само решение не определяло ни имени инструмента, ни того, каким профилям он положен, ни того, как его
находки соотносятся с доказательством. Все три вещи приходится решать в коде, и каждая меняет
наблюдаемое поведение сессий, поэтому фиксируется здесь отдельно от ADR-0027.

## Контекст (что уже было в спецификации и в коде)

1. `ARCHITECTURE.md` называет инструмент поиска **`web.search`** дважды: таблица профилей §5.7
   («sealed: локальный индекс; curated: SearxNG; open_lab: внешний API») и пример протокола §7
   (`{"tool": "web.search", "arguments": {"query": …}}`). ADR-0027 и `docs/web-access-design.md`
   писали имя неформально — `research.search`.
2. Тот же §5.7 называет загрузку страницы **`web.fetch`**, а реестр (`packages/policy/tools.py`) с
   T6.x знает только `research.fetch`; все payload'ы config-v1…v13 закрепляют `research.fetch` байтово
   (`policy.capabilities.tools` входит в canonical-хеш снапшота). Дрейф имени остаётся — он не чинится.
3. §5.7 помечает поиск как **observation**, а fetch в §5.7 тоже observation, но реестр помечает
   `research.fetch` классом `NON_IDEMPOTENT`. Класс определяет ретраи (`packages/broker/broker.py::RETRY_POLICY`,
   инвариант AGENTS §3: observation/non_idempotent/unknown → 0 ретраев); менять класс существующего
   инструмента нельзя — это изменило бы семантику повторов уже записанных сессий.
4. Сервис поиска существовал до задачи (`apps/research_proxy/service.py::search()`), в HTTP-API тоже;
   не хватало только пути от модели к нему.

## Решение

1. **Имя — `web.search`** (по §5.7 и §7), а не `research.search`. Следствие, принятое осознанно: в одном
   offered-списке живут `web.search` и `research.fetch`. Переименование `research.fetch` в `web.fetch`
   невозможно без переписывания замороженных payload'ов и без изменения `tool_schema_hash` прошлых
   прогонов — это отдельное решение, не эта задача.
2. **Класс идемпотентности — OBSERVATION** (по таблице §5.7): 0 ретраев, повтор идентичного вызова
   отсекается guard'ом T7.12 (`TOOL_REPEAT_DENY_LIMIT = 2`). Существующие классы не трогаются.
3. **Аргументы — ровно `{"query": str}`**, `min_length=1`, `max_length=500`, `extra="forbid"` как у всех
   инструментов реестра. Граница 500 (а не 1000, как у `memory.search`) выбрана сознательно: это строка
   поисковой системы, а не вопрос, и она же ограничивает объём темы, раскрываемой внешним движкам (§5.12.1).
4. **Гейты по профилям** (пересечение потолка `sandbox/policy/<profile>.yaml` и возможностей снапшота;
   снапшот умеет только сужать — `packages/policy/profiles.py::effective_profile`):

   | профиль | потолок | что делает инструмент |
   | --- | --- | --- |
   | sealed | **не выдан** (файл не изменён) | в схеме модели его нет; прямой вызов → deny «tool not allowed by profile 'sealed'» |
   | curated | выдан (аддитивная строка) | локальный индекс + upstream SearXNG с журналом и rate limit |
   | open_lab | выдан (аддитивная строка) | только локальный индекс: `modes.py` при open_lab принудительно `searxng_url=None`, «внешний API» из §5.7 для open_lab не реализован |

   Отказ профилю sealed при том, что §5.7 обещает ему «локальный индекс», — осознанное отклонение:
   в sealed сеть закрыта (`network: none`), и тот же FTS-индекс уже доступен модели pure-инструментом
   `memory.search`. Второй инструмент с нулём внешних данных дал бы модели лишний способ утверждать
   «я поискал» там, где искать негде, — то есть ровно ту путаницу, которую закрывает G8. Аддитивная
   строка в `sealed.yaml` возвращает его одной правкой; существующие sealed-снапшоты (в том числе
   `BOOTSTRAP_PAYLOAD`) его не запрашивают, значит их поведение не меняется ни на байт.
5. **Находки поиска не становятся доказательством.** `packages/orchestrator/evidence.py::observation_to_evidence`
   не получает ветки для `web.search` → возвращает None; строки `sources` и `artifact_chunks` не создаются.
   Провенанс по-прежнему рождает только `research.fetch`. Это правило закрепляется тестами (в том числе
   проверкой «декоративного» хита с полями `url`/`normalized_text`/`source_id`, который не должен быть
   принят за доказательство), а не подразумевается. Причина принципиальная: knowledge меняет только
   staging + rules engine (AGENTS §3), а заголовок из чужой выдачи — не наблюдение о мире, а навигация.
6. **Оформление наблюдения — чистый модуль** `apps/orchestrator/search_view.py` (§AGENTS: вынесенная чистая
   функция, рабочий модуль только вызывает): fence `<<<UNTRUSTED DATA BEGIN/END>>>` вокруг внешней части,
   бюджет `SEARCH_CONTEXT_BUDGET = 8_000` (против 40_000 у fetched-документа), потолки полям
   (заголовок 200 / фрагмент 400 / url 500), не более 10 хитов каждого рода, резка **целыми хитами**
   (наблюдение с незакрытым fence'ом — сломанная граница данных), нейтрализация литералов fence'а внутри
   чужих данных, отдельный помеченный блок «память узла» вне fence'а. Отдельно закреплено честное
   отсутствие: если upstream не выполнялся (режим или настройка) либо движок ответил пусто — текст говорит
   об этом прямо, выдумывать нечего.
7. **Аудит и лимиты переиспользуются, новых типов нет.** Действие проходит общий путь
   `action_proposed → policy_evaluated → action_started → action_completed/action_failed`; закрытый
   `AuditEventType` не расширяется. Volume-контроль — уже существующий upstream-журнал
   (`research_upstream_request{upstream_host, query, mode, status, results}`) и rate limit снапшота
   (`rate_limit_max`/`rate_limit_window_seconds`, 20/3600 в config-v13/v14), при исчерпании —
   `research_fetch_rejected{reason:"upstream_rate_limit_exceeded"}` и Observation `ok=false` без обращения
   к движку. Ограничений прямых `research.fetch` это по-прежнему нет → **T7.72 остаётся открытым**.
8. **Снапшот config-v14 = config-v13 ровно с двумя правками**: `policy.capabilities.tools`
   (`+web.search`, `−artifact.create`) и пин `prompts.explorer` → `explorer-v6`. Прежние payload'ы не
   переписываются никогда (AGENTS §8), их canonical-хеши и `tool_schema_hash` не меняются.
   `artifact.create` убирается из **возможностей снапшота**, а не из реестра (его в реестре нет): отсюда
   на `.92` и в серии MODELSEL шли предопределённые отказы шагов «unknown tool: artifact.create». Подпись
   `artifact.create` в `apps/web/labels.py` остаётся — тест полноты словаря берёт объединение реестра и
   возможностей `BOOTSTRAP_PAYLOAD`, где этот инструмент по-прежнему есть.

## Решения, требующие подтверждения пользователем

- Имя `web.search` (vs плановое `research.search`): выбор сделан в пользу ARCHITECTURE.md; если нужно
  именно `research.search`, это новая config-версия и новый payload — прежние не переписываются.
- Отказ профилю sealed в инструменте, который §5.7 ему обещает (пункт 4 выше).
- Дрейф `web.fetch`/`research.fetch` и класс `NON_IDEMPOTENT` у fetch — остаются как есть; согласовать
  их можно только отдельным решением с новой конфигурацией.

## Последствия

- Offered-список и `tool_schema_hash` меняются **только** у снапшотов, которые явно выдают `web.search`:
  config-v14 полный список 10 → `0cff269d74562bce…`, offered (без `message.reply`) →
  `a7adc9487f6536dde5889ece4fbf0bea5a5b61e6475079e9a7c6fcff81a97cbe`; config-v13 остаётся при своём
  (`c64d98d4…` / `f7628473…`). Молча ничего не вырезается (ловушка AGENTS §7).
- Риск-профиль расширяется в одном конкретном месте: тема запроса уходит внешним движкам (текст `query`,
  не URL, ≤500 знаков). Контроль — существующий upstream-журнал + rate limit; SearXNG на стенде —
  локальный контейнер с publish только на `127.0.0.1:8888` (T7.70), правила UFW пакет не меняет.
- Поверхность инъекции растёт там же, где и была (чужой текст), но теперь чужие заголовки и фрагменты
  попадают в контекст модели напрямую: тесты безопасности проверяют, что выданная подсказка не меняет
  возможности узла (профиль и реестр те же), что text скопированного из выдачи запроса требует оператора
  (backstop §11.2) и что poisoned-хиты остаются внутри одной пары fence-маркеров.
- Слово «проверено» и честные замечания карточки ответа не меняются: они по-прежнему опираются на
  research.fetch («внешние источники не использовались» остаётся верным при одном лишь поиске). Поиску
  добавляется шаг «поискал в интернете: <запрос>» — только для реально выполненных действий.

## Отклонённые альтернативы

- **`research.search`** — противоречит §5.7/§7 и создало бы третий вариант имени рядом с `web.fetch`
  в спецификации и `research.fetch` в реестре.
- **Выдать `web.search` профилю sealed** — дублирование `memory.search` при нулевом внешнем доступе.
- **Превращать хиты поиска в evidence/sources** — нарушило бы инвариант AGENTS §3 (оценку знания делает
  rules engine по доказательствам из наблюдений инструментов) и сделало бы заголовки фактами без чтения
  страницы; ровно тот дефект, который модели прощал explorer-v5.
- **Убирать `artifact.create` из реестра или из подписей** — реестра это не касается (инструмента там нет),
  а тест полноты словаря требует подписи на объединении реестра и снапшотных возможностей.

## Дополнение (T7.76): explorer-v8 и config-v16 продолжают этот ADR

Инструмент, реестр и гейты этого ADR не меняются: `web.search` остался
`{"query": ≤500}` / OBSERVATION, offered-список config-v16 = offered-список config-v14/v15
(`web.search` есть, `artifact.create` нет), `tool_schema_hash(allowed_tools)` не изменился
(текст контекста в него не входит), knowledge-ветки `observation_to_evidence` тоже.

Добавлено другое: модель наконец видит то, что и так было единственной схемой вызова. До T7.76
`model_tools_schema()` (полные схемы аргументов реестра) использовалась только тестами, а в
контекст шага исследоватора уходил один список имён инструментов — при этом хостовый текст
протокола перечислял поля кураторского конверта (`search_statements`, `as_of`, `scope`, …), и
модель передавала их аргументами инструмента: на стенде `.92` это дало отказ
`question.create {search_statements}` («Extra inputs are not permitted») при том что поле нужно
для перепроверки, и отклонённое действие стоит один шаг из `session_limits.max_explorer_steps`.
Хост рендерит схемы из того же реестра (`apps/orchestrator/tool_context.py`), а не хранит второй
текст схем; добавлены также блок бюджета шага («шаг N из M, осталось действий») и отметка повтора
чтения того же адреса. Это видимость, не ослабление: `extra="forbid"`, repeat-guard и
`policy_engine.evaluate` прежние. Пороги правил не менялись (см. ADR-0029); payload —
`docs/eval/config-v16-payload.json`, canonical `740ae9a1…`, прежний v15 (`b3801812…`) остаётся откатом.

## Дополнение (T7.127): отказ по лимиту поиска — понятный текст модели и отдельный учёт в отчёте честности

Замер стенда `.92` на config-v28 (прогон менеджера 2026-10-20, база `accd7e2`, журнал
`research_upstream_request`): за 5 сессий 22 успешных upstream-запроса и 7 отказов лимита, пик —
22 запроса в час при потолке `rate_limit_max = 20`; первый отказ — 11:32:40, последний успешный —
11:52:46, то есть лимит упирался в себя раньше, чем исчерпывался бюджет шагов исследователя.
После отказа модель не останавливалась: в сессии c3 за первым отказом последовали ещё 6 шагов, из них
4 поиска (`web.search, research.fetch, web.search, research.fetch, web.search, web.search`), в c4 —
7 шагов, из них 3 поиска. Причина — текст отказа: `upstream rate limit exceeded` не называет ни лимита,
ни окна, ни срока освобождения, ни выхода, и модель читает его как обычную ошибку движка.

Решение:
- машинный код отказа прежний — `ResearchProxyError(..., "rate_limited")` -> HTTP 429 в прокси и та же
  журнальная строка `research_fetch_rejected{reason:"upstream_rate_limit_exceeded"}`; в payload строки
  добавлен только ключ `window_seconds` — это содержание payload, новых журнальных типов нет;
- текст наблюдения строит чистая функция `apps/research_proxy/search.py::rate_limit_notice`: фактическое
  число запросов в окне и потолок («N из M запросов»), окно в секундах и в минутах, минуты до ближайшего
  освобождения и прямой выход — читать уже найденные адреса через `research.fetch` либо заканчивать с тем,
  что найдено; текст держится в 500 знаках, иначе его обрежет срезка наблюдения оркестратора (`str(exc)[:500]`);
- минуты считает `minutes_until_release` = `ceil((oldest + window_seconds - now) / 60)` не меньше нуля;
  при пустом окне текст честно говорит, что предсказать нечего, вместо выдуманного срока;
- состояние окна читается одним запросом `upstream_window_state` (число запросов в окне, время ранейшего,
  часы БД); `count_upstream_requests` сохранён как тонкая обёртка, публичный контракт модуля не сломан.

Отчёт честности (T7.118, read-only): отказы лимита получают ОТДЕЛЬНУЮ метрику `searches_rate_limited`.
`searches_total`, `searches_official`, `searches_other` их по-прежнему включают (число вызовов `web.search`
не меняется), а `wasted_searches` больше не считает отказ лимита «пустым поиском»: доля пустых считается по
поискам, дошедшим до движка — `wasted_searches / (searches_total - searches_rate_limited)`. Метрика аддитивная:
`SCHEMA_VERSION` отчёта не поднят, поэтому baseline прежней формы грузится и показывает «нет данных»,
а не 0 и не ошибку. В markdown отказы названы отдельной строкой и в сессии, и в итогах.

Что НЕ сделано и почему:
- дефолт `ModePolicy.rate_limit_max` в коде остаётся 20: потолок живёт в снапшоте, а не в коде
  (AGENTS §3 «Effective config»), новые числа не выводятся из правил;
- payload `docs/eval/config-v29-payload.json` = config-v28 ровно с одной правкой
  `research_proxy.rate_limit_max` 20 -> 60 (окно 3600 с не менялось, новых ключей в секции нет, разницей
  файлов является ровно одна строка), canonical `e0844baf…`, хеш payload-файла — другое число
  (`ea6e042a…`); он только подготовлен: активация — решение менеджера, dev-стенд и его база агентом не
  трогались, откатом v29 служит payload v28 (он не менялся);
- новых AuditEventType, новых колонок журнала и миграций нет; пороги правил оценки и правила `claim_type_rules`
  не менялись.

Ограничение названо честно: журнальную строку отказа пишет прокси, `session_id` у неё NULL, поэтому привязка
отказа к сессии идёт по интервалу жизни сессии из строки `sessions` и совпадению параметра запроса
(`q` в адресе отказа = запрос отклонённого `web.search`), с однократным расходом строки журнала. Времена
строк внутри одной долгой фазы совпадают (AGENTS §7), потому временем события внутри сессии привязать нельзя.
При перекрывающихся окнах сессий и одинаковых запросах привязка между сессиями неоднозначна, но сумма по узлу
не удваивается. Тесты: `tests/unit/test_config_v29_payload_t7127.py`,
`tests/unit/test_search_rate_limit_notice_t7127.py`, `tests/unit/test_rate_limit_search_attribution_t7127.py`,
`tests/scenario/test_rate_limit_refusal_notice_t7127.py`, `tests/scenario/test_honesty_report_rate_limit_t7127.py`.
