# ADR-0033: Дубль по значению в кураторском предложении — честная склейка перепроверкой либо честный отказ с причиной (T7.83)

- Статус: **proposed** (хостовый гейт и тесты — T7.83(а), коммит `8fc9d54`; пин куратора
  curator-v10 и payload `config-v20` — T7.83(б); активация стенда и разбор уже записанного дубля
  на карточке f452a978 — за менеджером)
- Дата: 2026-10-09
- Контекст: замер подставки .92 (сессия `f452a978`, config-v19): куратор в `summary` объявил
  перепроверку обоих утверждений контекст-пака, но обе операции принёс без `existing_claim_id`.
  Byte-exact дедуп T7.9 (`apps/memory/service.py::apply_claim_staging`, сверка канонизированных
  statement) перефразу не видит: рядом с E4/0.95 утверждением «Годовая инфляция в России по итогам
  2025 года (декабрь 2025 к декабрю 2024) составила 5,59% … опубликовано 16–21 января 2026»
  (`9266248e…`, первоисточник Росстата) записался новый claim `e189c80d…` «официальная годовая
  инфляция … составила 5,59% (по данным Росстата)» на единственном пересказе. На карточке одно и
  то же значение одного показателя за один период оказалось дважды — с разными бейджами. Связанный
  дефект честности витрины разобран в ADR-0032; здесь — вторая половина: значение не должно
  записываться вторым claim'ом рядом с уже записанным, которое куратор видел в контексте.

## 1. Определение дубля (консервативный критерий хоста, чистая функция)

`apps/orchestrator/value_duplicate.py` — чистый модуль, ни БД, ни LLM. Дубликатом операции
считается **кандидат** — утверждение контекст-пака этой сессии (id из `[c:<uuid>]`, голова оценки
в снапшоте конфигурации сессии: ровно та же видимость, что у перепроверки T7.34 и гейта reuse T7.9;
именно это значит «куратор видел в контексте»), — если:

1. операция не принесла явного `existing_claim_id` (явные операции целиком принадлежат T7.34);
2. `claim_type` операции равен типу кандидата;
3. множества значимых значений формулировок равны и **не пусты**. Значение — maximal-последование
   десятичных токенов (`5,59`, `14.5`); границы числа повторяют семантику assertion_window
   (ADR-0011, `_numeric_boundary_ok`): `5,6` ≠ `5,59`, «105,59» — одно число и никогда не вхождение
   «5,59», годы и целые без разделителя значениями не считаются; формулировка с неразбираемым
   токеном выбывает целиком (молчание безопаснее ложной склейки);
4. период согласован: множество лет операции (годы из текста + `as_of` кандидата-операции) непустое
   и является подмножеством лет кандидата (год его текста + `as_of`). Лишние годы кандидата
   допустимы — кандидат мог быть сформулирован шире.

Ничего текстово-семантического критерий не оценивает: «по данным Росстата» против «Росстат
опубликовал» не сопоставляются, совпадение показывает значение+период+тип. Ошибочная склейка
дороже пропущенной, поэтому во всех спорных случаях — молчание или явный отказ трогать.

## 2. Матрица решения (одно правило вместо движка)

Для каждой операции с ровно одним **строгим** кандидатом (строго = пункты 1–4):

| ситуация | решение гейта |
|---|---|
| ровно один строгий кандидат, все связи операции — `supports` | **(i) честная склейка**: staged-копия операции получает `existing_claim_id` кандидата; новый claim не создаётся; свежее evidence идёт в union-оценку кандидата |
| ≥2 строгих кандидата | **(ii) не трогать**: операция остаётся как предложена (`ambiguous value duplicate…`) |
| один кандидат, но в связях есть `counters` | **не трогать**: спор остаётся спором (counterevidence → disputed по §3) |
| один кандидат, но ни одной `supports`-связи | **не трогать**: нечего добавлять к оценке |
| строгих кандидатов нет | гейт молчит: payload сессии байт в байт прежний |

Решение каждой затронутой операции записывается ключом `value_duplicates` (список
`{claim_index, target, action, reason}`) в payload **уже существующего** события `CLAIM_CREATED`:
нового AuditEventType нет (список закрыт, §3), миграции нет. Ключ появляется только при непустом
списке. Исходное предложение в аудит не переписывается: `claims` события сохраняет
`existing_claim_id: null` там, где модель его не принесла; подмена живёт только в staging-операции —
это тот же принцип, что у `relied_claims_rejected` (ADR-0032). Отказ одной операции не отменяет
остальное предложение.

## 3. Почему склейка не может ни понизить, ни подделать оценку

Оценка по-прежнему производится только rules engine (§3); гейт меняет только адрес операции.

- **монотонность union-оценки**: перепроверка добавляет кандидату evidence-строки и группы
  независимости, ничего не снимает; канал текстового слияния доказательств отсутствует
  (`build_source_independence_snapshot` вызывается без sample_text — объединяются только строки
  источников), а единственная новая страница может присоединиться к одной группе через registrable
  domain или parent-указатель (ADR-0029), но не способна разъединить прежние;
- **условие all-supports**: гейт переводит в перепроверку только операции без единой `counters`-связи —
  counterevidence в кандидата не протекает; disputed-семантика (§3) сохраняется;
- **якорь и scope**: `as_of`, `date_anchor` и assessed_scope сохраняет `packages/memory/reverify.py`
  (`resolve_reverify_reference`, `merge_reverify_scope`, правило 8 curator-протокола; непустая дата
  предложения при датless перепроверке — ревизия с аудит-отметкой `as_of_conflict`, молчаливой
  подмены нет);
- **для кандидата фикстуры понижение исключено арифметически**: E4 достигнут (boost
  `rules_engine.py:221–227` требует groups ≥ 2×min_independence_groups и `grade.level < 4` — при
  4 группах и 5 evidence потолок достигнут), confidence-множитель `min(1, groups/2)` насыщен
  (0,95 — потолок связки sources/quote_integrity). Ни одна монотонная добавка групп не меняет head.

## 4. Что увидит человек

Карточка вопроса: значение «5,59» — один раз, отношение «перепроверено этим вопросом»
(`touched_claims` + `claim_reverified`, T7.74); второе утверждение (инФОМ-наблюдение) остаётся
новым claim'ом со своей честной оценкой и, если ответ на него опирается, связью «использовано из
знаний» (ADR-0032). Лента сессии: payload `claim_created` с ключом `value_duplicates` — индекс
операции, target-утверждение, действие и человекочитаемая причина. Сессии без дублей — payload
байт в байт прежние (проверено тестом равенства набора ключей).

## 5. Промпт curator-v10 и config-v20: объяснение, а не зависимость

Гейт хоста работает при любой конфигурации. Тело `curator-v9` сохранено байт в байт; к правилу 7
добавлен абзац (новая версия файла `prompts/curator/curator-v10.md`, sha256
`8b940bf573bcd19a1302b0a6ed48fee00ec87dbc81f71fa56063f510113c040e`): идентичность факта
определяется показателем, значением и периодом, а не формулировкой; перефразу куратор оформляет
перепроверкой с `existing_claim_id` сам, не полагаясь на хост. `config-v20` (canonical
`2b065470…`, полный `2b065470677e167dceecb9c91240c94a7c54d91408000e44e51e97feb3c18f9f`) =
`config-v19` ровно с одной правкой — пин `prompts.curator`; остальное байт в байт. Дефолт стенда —
v20, откат — v19 (`4d76c000…`).

## 6. Пределы и что остаётся честным образом незакрытым

- критерий не понимает метрик: «5,59» значения инфляции и «5,59» значения безработицы одного года
  склеит по типу+числу — типы в фикстуре разные (temporal_fact/external_fact), но полностью
  семантику показателя гейт не проверяет; сознанное упрощение вместо правил-движка;
- уже записанный дубль `e189c80d…` + `9266248e…` на стенде гейтом не переписывается: знание не
  удаляется (§3), задним числом никто оценки не меняет. Существующий инструмент оператора для
  спорного утверждения — `hostctl claim-dispute` (ADR-0031) — здесь неприменим: реального
  расхождения значений нет, заводить counterevidence ради косметики означало бы подделать оценку;
  карточка f452a978 остаётся как есть, повторение дефекта предотвращено гейтом. Разбор — STATUS.md
  T7.83 п. «непроверенное»;
- пороги, scale и rules engine не тронуты; стоп-критерий задачи (миграция / новый AuditEventType /
  пороговый механизм) не задействован.
