# ADR-0015: T7.28 — гейт `due_stale_time_sensitive`: строгое направление `<` по спецификации (уточнение ADR-0004)

- Статус: принято
- Дата: 2026-09-22
- Контекст: `ARCHITECTURE.md:2607` («due/stale time-sensitive claims
  <20%»), ADR-0004 (механика гейтов, пороги), ADR-0014 (T7.27: гейт
  вычисляет правило §8.6/T3.7 на момент расчёта), EVAL-4-freeze §3.1
  (предрегистрация g6: 6 заложенных просрочек в корпусе v3).

## Контекст

Спека §22.2 формулирует гейт 6 как **«due/stale time-sensitive claims
<20%» — строго меньше**. Код (до T7.28) сравнивал по направлению
`at_most`: `ratio <= threshold` (`packages/evaluation/gates.py`) — ровно
20% проходил. Расхождение меняло исход **на границе**: 6/30 = 0.200
по коду — `passed`, по спецификации — `failed`.

Для корпуса v3 это не абстракция: в нём 6 заложенных просрочек (3
old-as_of v2 + 3 T-old, `reverify_after ≤ 2026-07-01` — в прошлом на
момент любого прогона; EVAL-4-freeze §3.1, предрегистрация g6).
Минимальный знаменатель, при котором эти 6 сами по себе не валят гейт:
по коду N ≥ 30 (6/30 = 0.200), по спецификации N ≥ 31 (6/31 = 0.1935).
До решения вопрос держался оговоркой в EVAL-4-freeze §3.1: «до его
решения ориентироваться на N ≥ 31».

## Решение

Привести сравнение гейта 6 к спецификации: новое направление `below` —
`passed` при **`ratio < threshold`** (строго).

- `packages/evaluation/gates.py`: `_GATE_DIRECTION[
  "due_stale_time_sensitive"] = "below"`; в `_gate` направление
  `below` — строгое `ratio < threshold` (направления `at_least` →
  `>=` и `at_most` → `<=` не изменены).
- **Порог 0.20 не изменён** (значения порогов §22.2 immutable,
  ADR-0004; строки ран с зафиксированными порогами не трогаются).
- **Wilson-интервал не изменён** (`wilson_ci95` не тронута; интервал —
  reporting only, исход решает точка ratio).
- **Минимальный N для 6 заложенных просрочек теперь однозначен:
  N ≥ 31** (оговорка EVAL-4-freeze §3.1 снята).
- Сохранённые итоги прошлых прогонов **не пересчитаны и не тронуты**
  (улики, SELECT only). Проверка SELECT'ом по всем `noezema-eval*`
  (13 строк ран: 11 закрытых с сохранёнными гейтами + 2 незавершённые
  без гейтов): сохранённого результата g6
  **ровно на пороге (0.20) нигде нет** — ближайшие: EVAL-3d 8/17 =
  0.4706 (insufficient_sample, N < 20) и EVAL-4d 0/28 = 0.0 — ни один
  исход не меняется от приведения направления.

## Проверка соответствия остальных гейтов спецификации

Все 11 гейтов сверены с формулировками `ARCHITECTURE.md:2602–2611`
(таблица — `docs/STATUS.md`, раздел §22.2). Расхождение было ровно
у гейта 6; остальные направления совпадают с формулировками спеки
(≥ / ≤ / «каждый» → `at_least`/`at_most`; два нулевых — `count == 0`).

## Тесты

`tests/scenario/test_evaluation_gates.py` — граничные тесты для
**каждого долевого гейта ровно на пороге и рядом с ним** (18, по 2 на
гейт): g1 16/20 = 0.80 → passed / 15/20 → failed; g2 20/20 = 1.00 →
passed / 19/20 → failed; g3 12/20 = 0.60 → passed / 11/20 → failed;
g4 3/20 = 0.15 → passed / 4/20 → failed; g5 5/20 = 0.25 → passed /
4/20 → failed; **g6 6/30 = 0.200 → failed / 6/31 = 0.1935 → passed**;
g7 (SLO) 20/20 = 1.00 → passed / 19/20 → failed; g10 18/20 = 0.90 →
passed / 17/20 → failed; g11 16/20 = 0.80 → passed / 15/20 → failed.
В каждом тесте зафиксировано точное значение Wilson-95 интервала
(интервал не изменился). Существующие тесты гейтов (включая регрессию
формы EVAL-4d 22/28 → failed) не изменены и зелёные.

## Не изменено

Пороги §22.2 (значения), `claim_type_rules` и `rules_hash`
(замороженные payload'ы config-v2…v5 и корпуса v2/v3 не тронуты,
хэши перепроверены), схема БД (миграции нет), сохранённые строки
ранов и итоги (улики, SELECT only), `ARCHITECTURE.md`.
