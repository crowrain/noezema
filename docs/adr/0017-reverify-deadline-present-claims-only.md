# ADR-0017: Срок перепроверки существует только у утверждения о настоящем (T7.32, §8.2, §8.6, §8.7, §22.2)

Статус: accepted

Дата: 2026-09-23 (замечание пользователя от 2026-09-23: «срок
перепроверки нужен ТОЛЬКО утверждению о настоящем» — оно же корень
провалов гейта 6)

## Контекст

После T7.30/ADR-0016 базовая дата срока — хост-выводимая `as_of`, и
формула (`rules_engine.py:263–267`, до T7.32) отсчитывала срок **от
`as_of`**:

```python
base = as_of if (as_of is not None and result.reverify_after_days == 30) else now
return base + timedelta(days=result.reverify_after_days)
```

Последствие — класс утверждений, **просроченных навсегда**:

- «Спутник-1 запущен 4 октября 1957» (бездатовый вопрос, модельный
  `as_of` = дата события) → `reverify_after` = 1957-11-03 → due
  всегда. Улика: claim `de9855eb` (as_of 1957-10-04, due) в EVAL-4d;
  тот же класс — «Конституция РФ (1993)», «PostgreSQL 14 EOL (2021)»;
- «По состоянию на 15 апреля 2026 в ООН было 193 страны» (явная
  старая дата) → due всегда (улика: 6 заложенных просрочек v3,
  3/6 v2; T7.29 §3 класс A);
- даже `formal_theorem` (volatility `static`, 90d) числится
  устаревшим через 90 дней — у `VOLATILITY_REVERIFY_DAYS` нет
  варианта «не истекает».

Но **факт о прошедшем событии неизменён**: позднейшие события на него
не влияют, перепроверять его не нужно никогда. Утверждение о
фиксированном моменте (явная дата вопроса ИЛИ бездатовый вопрос с
модельным `as_of` = датой события) вечно верно и не портится.
Портится только утверждение о «сейчас»: «сколько стран в ООН на
текущую дату», «какова ключевая ставка». Обратный случай — документ,
который правят (конституция с поправками): «что говорит редакция от
12.12.1993» — явная дата → неизменно; «что говорит ДЕЙСТВУЮЩАЯ
редакция» — относительная форма → утверждение о настоящем, срок
нужен. Версионность получается из якоря вопроса, отдельный механизм
не требуется.

Класс «просрочен навсегда» — корень провалов гейта 6: в EVAL-4d
16/22 просрочек — as_of-артефакты (ADR-0016), и T7.31 строил корпус
v4, выкидывая бездатные и явно-датированные вопросы, чтобы из
знаменателя гейта убрать непредсказуемые due (EVAL-5-freeze §3.1:
«B. бездатные — due ВСЕГДА», «A. явные старые даты — due ВСЕГДА»).
Никаким поведением системы этот класс не лечился — срок считался от
`as_of`, а `as_of` у фиксированного момента по определению в
прошлом.

## Решение

**Определение: срок перепроверки (`reverify_after`) существует ТОЛЬКО
у утверждения о настоящем.** Одно правило, по якорю вопроса — якорь
уже определяет `derive_claim_as_of` (ADR-0016):

| Якорь (закрытый набор) | Вопрос | Утверждение о | Срок |
|---|---|---|---|
| `explicit` | явная дата | фиксированным моментом | **НЕТ** (NULL) |
| `relative` | «на текущую дату», «сейчас», … (закрытый набор T7.18) | настоящим | **МОМЕНТ ПРОВЕРКИ (`now`) + окно по volatility** |
| `none` | без даты (fallback на модельный `as_of`); вопрос с относительной формой без `session_date` (fail-closed, T7.18); сессия без вопроса | фиксированным моментом | **НЕТ** (NULL) |

1. **Срок больше НЕ отсчитывается от `as_of`.** Формула
   `reverify_after(result, anchor, now)` (`rules_engine.py`):
   `anchor == relative` → `now + VOLATILITY_REVERIFY_DAYS[volatility]`;
   иначе → `None` (сохранённый `reverify_after` = NULL). Окно по
   volatility **не меняется** (`static` 90d, `configurable` 30d,
   `temporal` 30d): якорь решает СУЩЕСТВОВАНИЕ срока, volatility —
   его ДЛИНУ. Отдельный класс volatility «не истекает» **не нужен**:
   фиксированный момент любого типа не имеет срока вовсе (включая
   `formal_theorem` — «устаревающий через 90 дней» класс исчез).
   `claim_type_rules` и `rules_hash` не меняются.
2. **`as_of` остаётся тем, чем является** (ADR-0016 не отменяется):
   опорная дата утверждения, хост-выводимая, приоритет явная дата >
   относительная → дата сессии > модельный fallback. Деривация
   `as_of` (и scope) не меняется — 33 теста `test_scope.py` и тесты
   T7.30 сохраняют смысл.
3. **Якорь возвращается ИЗ ТОЙ ЖЕ функции** — `derive_claim_as_of`
   теперь возвращает `(as_of, anchor)` (`ClaimAsOf`): ветка, давшая
   значение, известна вызывающему, повторного разбора
   `parse_question_date`/`question_uses_relative_date` на месте
   вызова нет — одна функция, один источник истины (как требует
   ADR-0016). Якорь персистируется в host-scope-v1
   (`date_anchor`) — в `assessed_scope` оценок: переоценка (worker)
   не имеет вопроса и применяет то же правило по сохранённому
   якорю (`anchor_from_scope`). **Legacy-склей** (до-ADR-0017 строки
   без `date_anchor`, включая пустой scope) → консервативный default
   `relative`: срок держится/обновляется, а не «вечно валидно» на
   основании отсутствующих данных (fail-closed).
4. **NULL-срок разведён со статусом `unknown`** — новый статус
   `evergreen` (`FreshnessStatus`, §8.2: `fresh | due | stale |
   unknown | evergreen`): «срока нет по построению, утверждение
   вечно валидно». Правило свежести (`freshness.py`): NULL →
   `evergreen`, `now < reverify_after` → `fresh`, иначе → `due`.
   Для любого claim'а с head на действующем snapshot NULL всегда
   означает «нет срока по построению» (оба писателя пишут ровно по
   правилу п.1), поэтому правило остаётся чистой функцией
   `(reverify_after, now)`. **Retrieval**: `evergreen` ранжируется с
   весом **1.0 = fresh** — неизменный факт НЕ опускается как
   сомнительный (прежний NULL → `unknown` → 0.7 опускал «Спутник»
   ниже свежих claim'ов).
5. **Знаменатель гейта 6 — только способные просрочиться.** Гейт
   `due_stale_time_sensitive` (§22.2 «due/stale time-sensitive claims
   <20%») теперь считает знаменателем current `temporal_fact` с
   `reverify_after IS NOT NULL` (срок есть = time-sensitive в смысле
   due/stale), числитель не меняется (`reverify_after <= now`).
   Фиксированные моменты просрочиться не могут: включение их в
   знаменатель проходило бы гейт **композицией** (чем больше таких
   claim'ов, тем «свежее» база) вместо измерения здоровья свежести.
   Порог 0.20, направление `below` (T7.28/ADR-0015) и MIN_SAMPLE = 20
   **не меняются**. Предрегистрация EVAL-5 пересчитана
   (EVAL-5-freeze.md §3.1, T7.32).
6. **Точки записи**: коммит (`service.py`) и переоценка
   (`reassessment.py`) пишут срок по одному правилу (п.1) от якоря:
   коммит — из `derive_claim_as_of` (тот же вызов, что дал
   `as_of`/scope), worker — из сохранённого `date_anchor`.
   Переоценка **не возвращает срок** утверждению о фиксированном
   моменте (NULL остаётся NULL) и **обновляет** срок относительного
   до своего момента проверки.

## Что НЕ меняется

- **Деривация `as_of`** (ADR-0016: приоритет, якорь начала сессии,
  re-деривация на каждом коммите, модельная дата — staging/audit) —
  не меняется; `claims.as_of` не перестаёт быть опорной датой
  утверждения (scope, coverage, display).
- **Окно по volatility** (`VOLATILITY_REVERIFY_DAYS`), **grade/confidence**,
  **`claim_type_rules`**, **`rules_hash`** (payload'ы config-v2…v5),
  **`rules_version`** (rules-v2) — не меняются.
- **Пороги §22.2 и направления гейтов** — не меняются; меняется
  только знаменатель гейта 6 (п.5) — строка матрицы §22.2 в
  STATUS.md + ADR.
- **Механика T7.27/ADR-0014** — не меняется: freshness вычисляется
  при чтении (гейт — в SQL на момент расчёта, retrieval — по строке),
  сохранённая колонка — дисплейный кэш, фоновых свипов нет.
- **Замороженные payload'ы** config-v2…v5, **корпуса** v1/v2/v3/v4,
  **сохранённые данные прошлых прогонов** (`noezema-eval*` — SELECT
  only, не переоцениваются) — не тронуты.
- **Схема БД** — одна миграция (0024): CHECK `claims.
  freshness_status` дополнен `evergreen` (значение из закрытого
  набора §8.2; новых колонок нет).

## Почему не другие варианты

- **Класс volatility «не истекает»** (вместо правила по якорю):
  требует правки `claim_type_rules`/`rules_hash` (запрещено
  задачей) и не покрывает суть: просрочка фиксированного момента —
  не «длинное окно», а отсутствие самого понятия «срок»; правило по
  якорю короче и закрывает все типы сразу.
- **Перетолковать NULL как `evergreen`, не трогая retrieval**:
  NULL-claim'ы ранжировались бы весом `unknown` (0.7) — неизменный
  факт опускался бы как сомнительный (требование задачи п.3).
- **Знаменатель гейта 6 — все current temporal_fact** (как до T7.32):
  под новым правилом в знаменатель попадают claim'ы, которые
  просрочиться не могут — гейт проходил бы добавлением фиксированных
  моментов в корпус (композиция), а не улучшением свежести; предрегистрация
  EVAL-5 (2/22.3) строилась именно на заложенных due, которые под
  ADR-0017 больше не существуют.
- **Legacy (без `date_anchor`) → `none`** (снять срок):
  fail-open — «вечно валидно» на основании отсутствующих данных;
  выбран `relative` (срок держится) — консервативно по назначению
  механизма (перепроверка).

## Известные ограничения

- **Legacy-строки** (до T7.32, в старых БД): у них `reverify_after`
  вычислен старой формулой (от `as_of`) и сохранён; переоценка по
  консервативному default обновит срок до `now + окно`, но не
  разведёт якорь — разведение произойдёт при следующем коммите
  (re-деривация, ADR-0016). Сохранённые прогоны не переоцениваются.
- **Сессия без вопроса** (`question_id IS NULL`) — якорь `none` →
  срока нет: вопрос — единственный доверенный источник якоря
  (ADR-0007/ADR-0016); в реальной сессии вопрос есть (корпус).
- **Статус `unknown`** в закрытом наборе §8.2 остаётся (legacy-строки,
  дисплейный кэш до первой записи); новым кодом не производится —
  правило `freshness.py` отдаёт только `evergreen | fresh | due`
  (как и раньше — только два из четырёх; `stale` кодом не
  производится, ADR-0014 §3).
- **Сопоставимость**: EVAL-5 — новый baseline для гейта 6 (знаменатель
  и due-множество по ADR-0017); предрегистрация заменена
  (EVAL-5-freeze.md §3.1, T7.32). Следствие для корпуса — в STATUS.md
  (T7.32): выброшенные T7.31 бездатные и явно-датированные вопросы
  больше не «due навсегда» и могут вернуться в следующий корпус
  (v5); v4 и v1/v2/v3 не тронуты.

## Тесты

- `tests/unit/test_scope.py` — якорь из `derive_claim_as_of` по
  каждой ветке (явная → explicit; относительная → relative;
  относительная без `session_date` → none; бездатовая → none;
  без вопроса/`as_of` → (None, none)); `date_anchor` в scope для всех
  трёх приоритетов; `anchor_from_scope` (сохранённый якорь; legacy →
  relative; мусор → relative).
- `tests/unit/test_freshness.py` — NULL → `evergreen` (и не
  «переворачивается» со временем); fresh/due/граница — без изменений.
- `tests/unit/test_rules_engine.py` — срок = `now` + окно (relative),
  база — момент проверки; фиксированный момент → NULL для ВСЕХ
  volatility (static/configurable/temporal).
- `tests/unit/test_memory_service.py` — коммит через MemoryService:
  бездатовый вопрос (Спутник 1957) → NULL/evergreen; относительный
  вопрос → `now` + 30d/fresh; claim view согласован.
- `tests/scenario/test_as_of_commit.py` — все три якоря через реальный
  коммит (явная дата → больше НЕ due: NULL/evergreen; бездатовый →
  NULL/evergreen; относительный → `now` + 30d, диапазон
  [as_of+30d, as_of+31d)); сессия через полночь UTC (якорь T7.18);
  dedup (re-деривация, N → N+1); **переоценка не возвращает срок
  фиксированному моменту** (NULL остаётся NULL); форма EVAL-4d: due-
  множество старого правила (8/28) исчезает по построению — гейт 6 =
  0/20 (только относительные) → passed.
- `tests/scenario/test_evaluation_gates.py` — гейт 6 на смеси
  «со сроком / без срока» (фиксированные моменты вне знаменателя:
  3/10 failed вместо 3/20 passed); регрессия EVAL-4d (22/28 — все со
  сроком) без изменений; NULL-claim вне знаменателя (3/21).
- `tests/unit/test_retrieval.py` — неизменный факт `evergreen`, вес =
  fresh (1.0), не опускается ниже.
- `tests/scenario/test_reassessment.py` — legacy-scope (без якоря) →
  консервативный `relative`: срок обновляется к `now + окно`, не от
  `as_of`.
