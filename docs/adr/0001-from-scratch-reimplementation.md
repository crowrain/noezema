# ADR-0001: Реализация с нуля в отдельной ветке `impl/from-scratch`

- Статус: принято
- Дата: 2026-09-14
- Контекст: `docs/PLAN_FROM_SCRATCH.md`

## Контекст

На `main` существует MVP v0.1 (57 тестов, Docker Compose, 16 таблиц). Разбор кода
(таблица G1–G14 в `docs/PLAN_FROM_SCRATCH.md` §2.2) показал, что MVP нарушает ключевые
принципы спецификации: прямые записи в доменные таблицы без `session_staging`, отсутствие
fenced commit/reconciliation, lease, revision vector, capability policy, контейнерной
изоляции и версионируемых правил. Переделка существующего кода на месте унаследует эти
структурные ошибки и не даст проверить контракты спеки «чистыми».

## Решение

1. Создать ветку `impl/from-scratch` от `main` (`e190420`).
2. В ветке — чистое дерево: только `README.md`, `ARCHITECTURE.md`, `LICENSE`, `.env.example`,
   `.gitignore`, `.dockerignore`, `docs/`. Весь код пишется заново по плану вех M0–M7.
3. Код `main` — только reference: переносимые фрагменты (промпты, паттерн LLM-клиента,
   часть тестов) переписываются под новую структуру и проходят её тесты.
4. `main` не изменяется до прохождения MVP-gate (конец M3); merge MVP — отдельное решение.
5. Отказ от Redis/RQ в v1 (см. ADR-0003): фоновые работы — durable-таблицы PostgreSQL.

## Последствия

- Плюсы: контракты спеки реализуются без legacy-долга; каждое guarantee имеет
  failpoint-тест с первого дня; чёткие gates по вехам.
- Минусы: дублирование effort с `main`; `main` остаётся «живым» MVP, пока ветка не дойдёт
  до MVP-gate — поддержка двух кодовых баз ограничена горизонтом ветки.
- Риск дрейфа от спеки контролируется матрицей `docs/STATUS.md` и ADR-традицией.
