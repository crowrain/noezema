# ADR-0006: Серия EVAL-2 — исходы гейтов §22.2 и решение по failed-гейту `significant_claim_reuse`

Статус: accepted, **уточнён 2026-09-16** (пункты «Разбор» 3, «Решение» 1–2 и
«Следствия» — переклассификация по решению пользователя: кросс-язычное
расхождение — дефект механизма, а не свойство корпуса; формулировка
«показано end-to-end» снята как преждевременная)

Дата: 2026-09-15/16

## Контекст

EVAL-1 (ADR-0005) провалилась по одному гейту: `significant_claim_reuse`
1/29 = 3.4% < 25% — модель практически не переиспользовала существующие
claims. Диагноз (T7.7, до EVAL-2):

1. `memory.search` был stub'ом, возвращавшим пусто — у модели не было
   ни одного активного окна в память, кроме FTS-секции
   `claims_evidence` контекст-пака, покрывающей только топические
   совпадения с текущим вопросом;
2. в протоколе не было правила ссылаться на существующие claims;
3. дефект: `executor.snapshot_id` шептался только в phase 3, поэтому
   поиск в ходе exploration всегда получал `snapshot_id=None`
   (фикс — commit `e0a3660`).

Исправления, внесённые ДО серии EVAL-2 (commits `fa8978e`, `e0a3660`):
реальный `memory.search` (тот же retrieval, что контекст-пак, pointer
equality §14.1, результаты — наблюдения, не evidence), правило reuse в
`_protocol_text` (связанные существующие claims указывать в
`dependencies`), phase-1 pinning snapshot_id.

Конфигурация серии заморозка ДО запуска (STATUS, пункт 6): модель
`qwen36-35b-a3b-q6-mtp`, bootstrap snapshot, rules-v1, пороги без
изменений, SLO 3600 с, blind seed 20260915/50, 50 сессий, тот же
корпус v1 (sha256 `9d09e17ca5f388bb…`), чистая БД `noezema-eval2`.
Цель — A/B-сравнение с EVAL-1: изменился только путь reuse.

Первая попытка серии прервана инцидентом (STATUS, пункт 7: холодный
load > 600 с, параллельный smoke-драйвер, дроп БД в ходе серии); серия
проведена на чистой БД, один драйвер, модель загружена.

вопросы 7 сессий в серии не обработаны.

### Разбор reuse-гипотезы

Механизм работает, гейт упёрся в корпус:

1. **Модель пользуется механизмом.** За серию: 16 вызовов
   `memory.search` (аудит `action_started`), 3 dependency-рёбра
   `claim_dependencies`. Все три рёбра — сессия Q46 («создать a.txt
   (3 строки) и b.txt (5 строк)») на существующий claim «В текущем
   workspace присутствуют файлы: a.txt, b.txt, notes.md…» из более
   ранней сессии — ровно то, что просит протокол.
2. **Переиспользование произошло через контекст-пак, не через поиск.**
   Replay всех 16 поисковых запросов против финального snapshot
   (супермножество доступных на момент поиска claims): **0/16
   непустых**. Причины: (а) запросы на английском против русских
   claims — FTS `russian` не матчит («caching»/«кэширование»,
   «theory of relativity»/«теория относительности», «API»/«API
   расшифровка»); (б) по большинству вопросов связанных claims не
   существовало. Topical-совпадение Q46 пришло через
   `claims_evidence`-секцию пака (FTS по тексту вопроса), и модель
   зафиксировала его dependency'ем.
3. **Корпус v1 не содержит переиспользуемого перекрытия.**
   `near_duplicate_questions` = 0 (passed) — вопросы намеренно
   разнообразны; фактически-фактические claims сессии-уникальны
   (арифметика, география, даты). Случайных перекрытий за серию —
   два: «1 сентября 2026 — вторник» (EVAL-1, числитель 1/29) и
   workspace-claim (EVAL-2, числитель 1/28).

   **Расчёт потолка на корпусе v1** (после замечания пользователя —
   явно, поперёк вопросов):
   - знаменатель = significant claims серии: 29 (EVAL-1) / 28
     (EVAL-2) → берём ~28;
   - числитель = claims, упомянутые из ≥2 РАЗНЫХ сессий — возможен
     только там, где два вопроса ссылаются на одно и то же знание.
     Перечень кластеров корпуса v1:
     1. **Дата/время** (Q23, Q24, Q25, Q26, Q30, Q31 — 6 вопросов):
        переиспользуемы только «текущая дата» и «день недели
        01.09.2026» → потолок 2 claims;
     2. **Workspace** (Q44–Q47 — 4 вопроса): список файлов +
        содержимое notes.md → потолок 2 claims;
     3. **О себе/среде** (Q48–Q50 — 3 вопроса): «доступные
        инструменты», «структура сессии», «роль» → потолок 3 claims
        (реализуется, только если модель создаст их claims — в
        EVAL-2 не создала);
     - остальные 37 вопросов имеют сессионно-уникальные ответы → 0.
   - Теоретический максимум: (2+2+3)/28 = **7/28 = 25.0%** — ровно
     порог, и только при 100%-м соблюдении: каждая сессия кластера
     должна найти и сослаться на claims кластера (и при этом
     near_duplicate-гейт при этом всё ещё passed — вопросы
     сформулированы по-разному);
   - Реалистичное ожидание (по факту двух серий): из ~7 возможных
     ссылок материализовалась 1 → **~3.5%**.
   - Вывод: на корпусе v1 гейт 25% недостижим устойчиво; даже
     идеальный механизм даёт в лучшем случае граничное значение.
4. **Meta-вопросы 48–50 не создали переиспользуемых claims** (в
   финальном списке нет claims «доступные инструменты» / «структура
   сессии» / «роль» — либо сессии этих вопросов попали в 7
   LeaseLost, либо модель не предложила claims): потенциальных
   точек reuse у корпуса ещё меньше.

### Решение

1. **Т7.7 «доработка reuse» — частична** (уточнение 2026-09-16 по
   решению пользователя; прежняя формулировка «показано
   end-to-end» снята как преждевременная): путь «поиск → находка →
   ссылка» **ни разу не отработал** — 0/16 поисков вернули пусто,
   единственная засчитанная ссылка (числитель 1/28) пришла из
   контекст-пака + правила протокола, а не из поиска. Реализовано и
   покрыто тестами: сам `memory.search`, правило `dependencies`,
   snapshot-pinning (модель пользуется механизмом, dependency-рёбра
   коммитятся). **Не закрыт**: кросс-язычный дефект поиска —
   см. п. 2.
2. **Failed-гейт `significant_claim_reuse` на EVAL-2 = ДВА разных
   фактора, не «корпус целиком»:**
   (а) **дефект механизма** — поиск не матчит запрос на языке,
   отличном от языка claims (FTS `russian` не матчит английские
   запросы к русским claims; 0/16 в EVAL-2);
   (б) **свойство корпуса v1** — нет тематического перекрытия
   (потолок по п. 3 разбора: 25% только при 100%-м соблюдении).
   Порог §22.2 (25%, MIN_SAMPLE 20) не меняется.
   Замыкание обоих факторов — до серии EVAL-3 (см. п. 3):
   (а) **кросс-язычный поиск** — двуязычный поисковый индекс:
   обязательное англоязычное отображение statement
   (`search_statements`) индексируется в отдельном tsvector
   `english`, retrieval берёт максимум рангов; выбор варианта:
   векторный поиск сейчас недоступен (нет embedding-модели в
   llama-swap, pgvector не установлен в тестовом контейнере, по
   докстрингу retrieval — ADR-gated расширение вне v1);
   trigram/simple-конфиги не мостят языки (разные алфавиты);
   принудительный язык запроса — поведение модели, не гарантия
   (EVAL-2: модель сама переключается на EN), оставляется как
   дополнение в протоколе;
   тест: поиск находит claim по запросу на другом языке (unit +
   scenario);
   (б) **корпус v2** — 50 вопросов с гарантированным перекрытием
   (кластеры по 3–5 вопросов на одно знание).
3. **Валидационная серия EVAL-3** — только после замыкания п. 2(а) и
   2(б): корпус v2 (`docs/eval/question-set-v2.jsonl`) — артефакт
   тестирования (не конфигурация §22.2): 50 вопросов, 10–15
   кластеров по 3–5 вопросов на одно знание (переиспользование) +
   вопросы под редкие типы (external/temporal E3, due/stale,
   reassessment — решение пользователя 2026-09-16: в один прогон,
   исключать типы через ADR не будем). Заморозка конфигурации
   EVAL-3 — отдельный шаг, показывается пользователю ДО запуска
   (запуск — только по его явному OK).
4. **Кросс-языковое дополнение в протоколе** (не замена п. 2(а)):
   «ищи на языке вопроса и/или на языке, на котором написаны
   существующие claims; англоязычное отображение claims — в
   search_statements».
5. **LeaseLost 7/50 (EVAL-2) — не шум** (решение пользователя
   2026-09-16): срываются самые длинные вызовы (самые сложные
   вопросы) → выборка смещается. До EVAL-3: `phase_deadline_seconds`
   600 → 1800 в новом config snapshot (совпадает с
   `session_timeout_seconds`); целевой уровень потерь ≤2–3%.
   Повторный прогон сорвавшихся сессий в рамках EVAL-1/EVAL-2 не
   проводится (серии заморожены, их исходы зафиксированы в
   ADR-0005/0006).

## Следствия

- БД `noezema-eval2` (run `260571ef-cdf9-4f20-90a8-185699002a7b`) —
  доказательная база этого ADR; не трогать. БД `noezema-eval`
  (EVAL-1) — база ADR-0005.
- Общий acceptance MVP по §22.2 (нет failed И нет insufficient_sample
  гейтов) по-прежнему не пройден: failed — `significant_claim_reuse`
  (п. 2–3 решения — путь закрытия), insufficient — редкие типы
  external/temporal E3, due/stale, reassessment SLO. Решение
  пользователя 2026-09-16: редкие типы закрываются в EVAL-3
  (вопросы под них в корпус v2), отдельный прогон не нужен,
  исключение типов через ADR не допускается.
  **Технический предусловие для редких типов (выявлено при
  проектировании корпуса v2):** в текущем MVP нет пути
  research.fetch → evidence вида `source_assertion`
  (`observation_to_evidence` возвращает None для research.fetch),
  активный snapshot — профиль `sealed` (network=none, инструмента
  research.fetch нет), а правила `external_fact`/`temporal_fact`
  требуют ≥2 source_assertion evidence из ≥2 независимых групп
  (разные registrable-домены источников) и grade E3. Поэтому до
  EVAL-3: (1) реализовать связь research.fetch →
  source_assertion evidence (source_id, identity по
  `source_assertion_identity`); (2) новый config snapshot —
  access_profile `curated` (network=research_proxy,
  research.fetch) + allowed_domains источников; (3) в ходе серии —
  цикл `hostctl reassessment-tick` (worker, отдельный процесс),
  чтобы due-claims пересчитывались в пределах SLO.
- Правило эксплуатации, вынесенное из инцидента (STATUS п. 7): два
  драйвера `eval-run` против одной БД/owner одновременно не
  запускаются; БД серии не дропать во время серии.
- EVAL-3 (корпус v2) — новый блок задачи; старт после явного
  решения пользователя.

Постскриптум (T7.33, 2026-09-23, история не переписана): разбор
нулевого переиспользования на EVAL-4d — `docs/eval/EVAL-4d-reuse-

двуязычным FTS (`retrieval.py`): replay на EVAL-4d — 8/14 непустых,

у evidence — есть, §14.3). Идеальное fact-identity дало бы на
сохранённых данных максимум 2/26 = 0.0769 → failed. Варианты —
раздел 4 того же документа.
