## 3. Неприкосновенные инварианты

Нарушение любого пункта — блокер, даже если тесты зелёные.

- **Staging.** Модель меняет знание ТОЛЬКО через `session_staging`-операции
  (claim / evidence / question / identity). Никаких прямых UPDATE доменных таблиц извне сервисов.
- **Fenced commit.** prepared-строка `commit_attempts` пишется отдельной транзакцией ДО финальной.
  Финальная транзакция: locks в каноническом порядке → fencing-предикат (lease, owner, revisions,
  attempt=prepared) → apply_memory → staging → pointer/ревизия → terminal + audit/outbox — одной tx.
- **Reconciliation.** Неизвестный исход COMMIT не превращается в ложный failure; живой finalizer
  (`finalizer_in_progress`) ≠ rollback; unresolved attempt блокирует wake и GC.
- **ID и ретраи.** `turn_id` / `action_id` / `idempotency_key` генерирует хост, не LLM.
  Ретраи: pure=2, idempotent=1, observation/non_idempotent/unknown=0. Тот же key с другим hash —
  security incident (alert + audit).
- **Оценка знания.** grade/confidence производит ТОЛЬКО rules engine. Verifier, оператор, LLM
  grade не назначают. Duplicate evidence не повышает grade; counterevidence → disputed (≤E1).
- **Lifecycle.** head `current` ⇔ `current_assessment_id` и `epistemic_status` NOT NULL;
  pending/invalid ⇒ оба NULL. Pending/invalid никогда не подаются как current: в контексте —
  отдельный лимит и метка в ТОЙ ЖЕ строке; не хватает бюджета на метку — строка исключается целиком.
- **Effective config.** Только через `runtime_config_heads` → `config_snapshots`, fail-closed
  (`ConfigService.get_effective`). Правила и бюджеты живут в snapshot, не в коде.
- **Sandbox.** Одноразовый контейнер: network none, cap-drop ALL, non-root, ro rootfs,
  no-new-privileges. Инструмент, недоступный профилю, отсутствует в схеме модели.
- **Audit + outbox** пишутся в той же транзакции, что и изменение.
- **Host-контур.** Admission и Command API — fail-closed при любом unresolved host/policy state.
  Журнал переходов fsync-safe (tmp→fsync→rename→fsync(dir)); ровно один active head.

## 4. Дисциплина PR и веток

- Ветка `impl/from-scratch`. Один PR = один логический блок задач плана (`T…`), в сообщении
  коммита — номера задач и пункты § спеки.
- Каждый PR: зелёные ruff + mypy strict + pytest; новые/обновлённые тесты; обновлённый
  `docs/STATUS.md` (строка вехи + строки матрицы со ссылками на тесты).
- Gate вехи отмечается в STATUS.md ТОЛЬКО если каждый критерий имеет ссылку на тест.
  Строка матрицы со статусом ⬜/🔄 означает, что gate не пройден — не писать «все закрыты».
- Tag после gate: `noezema-m0…m7`, MVP — `noezema-mvp`.
- **Требует явного решения пользователя, не делать самостоятельно:**
  - merge в `main`;
  - старт M4 (по плану — только после серии реальных MVP-сессий и замеров нагрузки);
  - удаление/переписывание истории, force-push;
  - изменение `ARCHITECTURE.md`.
- Запрещено: обход staging, `print`-отладка, `TODO` без номера задачи.
- Не добавляй заглушки импортов и не меняй публичный контракт модуля ради тестируемости.
  Нужна отдельно тестируемая логика — выноси чистую функцию в отдельный модуль и тестируй её,
  а рабочий модуль пусть её вызывает.

конкуренции нескольких воркеров за общий Postgres их продление аренды опаздывает за запас).
Оба прогона обязательны: суммарно они дают полный набор тестов.
Образ sandbox собирается ОДИН РАЗ до запуска pytest: под xdist каждый воркер — отдельный
процесс со своим session-scope, параллельный `docker build` одного тега — гонка, поэтому

## 7. Известные ловушки

- Docker 29.8: `docker kill -s KILL` (не `-9`); `docker cp` не видит tmpfs — использовать
  bind-mount workspace хоста.
- `created_at` строк, рождённых в долгой phase-1-транзакции (model_runs, audit и т.п.),
  = `now()` = старт транзакции: внутри одной сессии все значения совпадают, хронологию
  строить только по `audit_events.sequence`.
- Локальные reasoning-модели: `reasoning_content` расходует `max_output_tokens`; длина
  reasoning дрейфует между запусками — бюджет держать ≥ P99 (для qwen36-35b-a3b-q6-mtp
  минимум 8192; при 4096 сессии падали `finish_reason=length` с пустым content).
- Движок halogen-flash-next (192.168.1.48:8080): отклоняет JSON Schema-ключевые слова
  `format` и `pattern` (HTTP 400 «unsupported keyword»), и сообщает только ПЕРВОЕ такое
  слово — остальные прятаться могут (замер T7.23, ADR-0012). Для него —
  `NOEZEMA_LLM_SCHEMA_PROFILE=halogen`; ответ движка без format валидирует хост полной
  pydantic-моделью (модель может выдать не-UUID — хост отклонит).

  (не `to_tsquery` — `*` ломает разбор); `ts_rank(to_tsvector(...), tsquery)` — вектор первым.
- ORM: атрибут `metadata` занят `DeclarativeBase` → `meta = mapped_column("metadata", ...)`.

  конвертируется в позиционный (asyncpg не может вывести тип из None), и

  (PostgresSyntaxError). Паттерн: динамическое WHERE-условие — параметр
  присутствует в SQL и в params только когда не None.

  перечитать файл перед edit.

- Гонка двух точек входа (T7.61(а), найдено на стенде .92): admission `decide` видит только **committed**
  строки `sessions`, а phase 1 держит строку запущенной сессии открытой до COMMITTING ⇒ «wake now» (веб) и
  запланированный `noezema-dev-tick.service` (отдельный процесс) получают wake одновременно. Маркер
  `node_state='session_running'` в admission не участвует и не должен (остаточный маркер от убитого юнита
  клинил бы узел). Взаимное исключение даёт `apps/orchestrator/node_guard.py`: session-level advisory lock
  `pg_try_advisory_lock(hashtext(node_session_lock_name(owner)))` на **отдельном** соединении (`NullPool` +
  AUTOCOMMIT), удерживаемое всю сессию; при гибели соединения замок снимает PostgreSQL — убитый юнит узел не
  клинит. Ключ считает Postgres (`hashtext`): Python `hash()` солится PYTHONHASHSEED ⇒ каждый юнит взял бы свой
  замок, и ничего не исключалось бы. Замок не участвует в каноническом порядке блокировок §5.2.2 (живёт вне
  транзакций), не lease и не fencing (§8.7.2, §5.2.3) и не заменяет список admission §5.2.1 — только окно
  decide→start. Не работает за transaction-mode pooler (pgbouncer); прямого pooler в проекте нет — при его
  появлении guard менять на долговременную строку с lease.

- Teardown scratch-БД и асинхронное закрытие соединения (T7.63): `DROP DATABASE` чинящей тест фикстуры падает с
  «database … is being accessed by other users», если в базе осталось **открытое соединение незавершённой
  async-задачи**. Две стороны: (1) `AsyncEngine.dispose()` закрывает только **idle**-соединения пула — сессию,

  тестом; presentation-слой grade и epistemic_status не назначает и не повышает (API-поля только добавляются).
- Простые страницы простого режима (T7.65): весь человеческий текст — из серверных подписей. В разметке
  `/` и `/answer/<id>` и в строковых литералах их JS запрещено писать код перечисления (`session_running`,
  `goal_reached`…), `§`, номер задачи плана, uuid/hex; тест `tests/scenario/test_web_answer_pages.py`
  сканирует статику вне `<script>` плюс quoted-литералы JS и краснеет на любом из этого (своей проверкой
  красноты он же доказывает, что сканер не пустой). Имена свойств JSON (`state_label`) — ключи ответа API, а
  не надпись на экране: в скан они не входят, экранировать их не надо. Прежняя главная закреплена тестами
  (`test_web_questions.py::test_main_page_carries_the_ask_form_and_the_queue_table`, `test_web_mvp.py`,
  `test_web_knowledge.py`) и живёт на `/engineer` без изменений: менять закрепленные строки можно только с
  обоснованием в STATUS.md, а не подгоняя тест под новую страницу.
- Слово «проверено» (T7.65) имеет один источник — бейдж надёжности при `reliability.level == verified` и
  заголовок строки подтверждения `verification_lead` («как проверено» ровно при том же уровне, иначе
  «чем подтверждено»). Страница не имеет права формулировать это сама (в её исходниках этого слова нет), а
  тест карточки требует, чтобы во всей карте ни одна строка не утверждала проверку там, где нет головы оценки
  `current`. Отрицание «Не проверено» утверждением не считается: проверка делает это негативным lookbehind
  (`(?<!не )\bпроверен`) — без него тест краснел бы на честном бейдже pending-оценки.
- Шаги работы в карточке ответа (T7.65) собираются из `audit_events` **по `sequence`** и только из
  реально выполненных действий: `action_started` без парного `action_completed{ok:true}` (обрыв, отмена,
  фаза 1 без COMMIT) и `action_failed` в шаги не пишутся — они дают замечание «часть шагов не удалась: N».
  Подпись действия берётся из категории `action_tool`, значения которой тестируются из реестра
  `packages/policy/tools.all_tools()`: новый инструмент без подписи краснит полноту словаря. Словарь
  обязан покрывать объединение реестра и возможностей снапшота правил (`test_action_names_come_from_the_tool_registry_and_snapshots`):
  в config-v13 есть `artifact.create`, которого в реестре нет и который исполнитель не выполняет («unknown
  tool»), — подпись нужна, чтобы лента не осталась без подписи. Действию, подписи которого в словаре нет,
  имя не выдумывается: используется нейтральное «действие без названия» (запасной путь `describe` вернуть
  сам код сюда не попадает — `answer.known_label` отдаёт пустую строку). Утверждение «сеть закрыта»
  допускается только если это подтверждает снимок правил этой работы (`policy.capabilities.network == "none"`);
  без сессии работает нейтральная формулировка.

- Перепроверка существующего claim'а и гейт staging (T7.73, уточнение ADR-0018): `validate_against`
  (`apps/orchestrator/orchestrator.py:2180`) выполняется ДО подмены типа якоря (:2201–2259), поэтому требование
  `as_of` для `temporal_fact` проверялось по типу из предложения модели, а оценка потом считалась по типу якоря —
  на датless-перепроверке это гарантированно давало `as_of_missing` и падение E3/0.75 → E1/0.30. Теперь гейт не
  требует даты у операции с `existing_claim_id`; дату, `date_anchor` и assessed_scope якоря сохраняет хост
  (`packages/memory/reverify.py`: `resolve_reverify_reference`, `merge_reverify_scope`), а непустая дата предложения
  при датless вопросе молча не подставляется — это revision (в аудит `claim_reverified.as_of_conflict`). Вторая
  половина той же ловушки: `existing_claim_id` отвергается fail-closed, если якорь не попал в контекст-пак
  (`curator_rejected: "claim[0]: reverify reference <id> is not visible to the session"`,
  `curator_reject_kind: "reverify_unresolved"`), а пакет собирается лексикой FTS — формулировка вопроса
  перепроверки обязана цитировать statement якоря, иначе сессия проходит без anchor'а и без доказательств
  (первые версии репродюсера `tests/scenario/test_reverify_temporal_scenario.py` краснели именно на этом).

- Витрина «вопрос → утверждение» (T7.74): перепроверка и дедуп-повтор НЕ заводят строку `claims`
  (`packages/memory/service.py`: ветки `existing_claim_id` и reuse берут существующий claim, его
  `created_in_session` — сессия **прежнего** вопроса), поэтому выборка утверждений только по
  `claims.created_in_session` слепа к ответу нового вопроса (на стенде это читалось как «Ответ не
  записан»). Долговременная связь «эта сессия оценила этот claim» — `claim_assessments.claim_id +
  created_in_session` (тот же источник, что `packages/evaluation/gates.py::_gate_reuse`; worker- и
  активационные оценки имеют `created_in_session IS NULL` и в карточку не попадают). Отдельного
  события дедуп-повтора в закрытом `AuditEventType` нет: отношение `reverified`/`reused` различается
  наличием или отсутствием `claim_reverified` для пары (claim, session) при уже доказанном факте
  оценки этой сессией; текстовые эвристики (statement, публичные summary) запрещены. Окно связи
  общее для карточки и списка (`apps/web/answer.py::touched_claims_cte`, использует и
  `apps/web/questions_view.py`): иначе «Мои вопросы» и карточка показывают разное; бюджет списка
  (≤4 SELECT, без N+1) закреплён тестом.

- `registrable_domain` для `.gov.ru` (T7.75): в PSL-списке `packages/memory/independence.py`
  (`MULTI_PART_SUFFIXES`) нет записи `gov.ru`, поэтому
  `registrable_domain("https://rosstat.gov.ru/") == registrable_domain("https://minfin.gov.ru/") == "gov.ru"` —
  все ведомства с одним `.gov.ru` сворачиваются в одну группу. Всё, что решает «это страница самого
  первоисточника?», обязано сравнивать **метку хоста**, а не registrable domain: в словаре и в
  разрешении родителя (`apps/research_proxy/source_attribution.py::is_home_host`,
  `apps/research_proxy/service.py::_resolve_primary_source`) так и сделано. Тот же подводный камень
  валит тесты независимости: хосты `interfax.example.ru / expert.example.ru / ria.example.ru` дают
  ОДИН registrable domain `example.ru` (PSL не знает `example.ru`), и группы сливаются сами по себе
  — фикстуры обязаны брать заведомо разные домены (`interfax.example / expert.example`) и это
  проверять. Менять PSL-список нельзя молча: это порог группировки, влияющий на прежние прогоны.
- `split` не отменяет parent-склеивание (T7.75): коррекция `source_graph_corrections{split}` снимает
  только прямые relation-основания (edge/correction), а `parent_source_id`, общий домен, общий hash и
  совпадение текста — алгоритмические факты (`packages/memory/independence.py:26–33`, :340–356).
  Ошибочное склеивание производного источника лечится только изменением данных (обнулить
  `parent_source_id`) — это вариант C ADR-0029; с T7.98 он реализован УЗКО: переатрибуция снимает
  хостовый указатель только при положительном противоречии свежего страничного метода
  (`ambiguous_primaries`; `apps/research_proxy/reattribution.py::_plan_window`, `_Plan.clear`;
  только `metadata.derivative_of`, только не-операторские, FOR UPDATE + повторная проверка).
  Значит детектор производности
  обязан оставаться консервативным: ложный пропуск безопаснее ложной склейки, а «исправим потом
  коррекцией» — не план.

- Страничный указатель — свойство страницы, а не значения (T7.98, ADR-0029 дополнение). Фраза
  «Банк России повысил прогноз … до 6–7%» без шаблона атрибуции не была видна детектору, и
  страничный указатель по другой шаблонной фразе («По данным Росстата… 0,17%») сделал Росстат
  «производителем» прогноза ЦБ: два пересказа одного прогноза дали E3 «Проверено», а собственная
  оценка Альфа-Банка попала в группу Росстата. С v4/v6 relay собирает такую пару (гварды (а)–(е),
  `source_attribution.py::_relay_forecast_keys`), переатрибуция снимает ложный указатель. Ловушки
  самой правки: (1) relay обязан различать «чей прогноз назван на странице» и «этому ли значению
  принадлежит первоисточник» — без гварда (е) (`required_numbers`) фраза «составила 5,59%, оказавшись
  ниже прогноза Банка России 6–7%» приписала бы 5,59 ЦБ (ложная производность); (2) гвард (б) —
  маркеры третьего актора по фону замазанных алиасов: «Альфа-Банк» ловится маркером `банк[а-яё]*`
  только после замазывания алиаса «Банк России» — порядок замазывания критичен; (3) снятие
  указателя трогает группировку через `parent_source_id` — каскад переоценок обязателен
  (`apply_source_graph_change` + `run_reassessment_batch`), а операторские коррекции не трогаются;
  (4) гейт дублей читает целые диапазоны («6–7%» → {6.0, 7.0}), а витрина `estimates.py` — нет
  (сознательное расхождение, STATUS T7.98); backfill у гейта нет: прежние утверждения стенда он не
  склеивает.

- Дубли значения на карточке сворачивает витрина, а не гейт (T7.99, ADR-0033 §13). Решение
  пользователя 2026-10-12: уже записанные дубли показывать свёрнутыми под якорем, знание —
  нетронутым (обе записи в базе, в `/knowledge` и в `/claim/<id>`). Критерий пары — строгий
  критерий кандидата гейта (тип + значения + покрытие периода + показатель, с чтением целых
  диапазонов) МИНУС `relied_claim_ids` и минус условия улик: `relied` и улики про склейку при
  записи, витрина решает только показ. Чистый предикат `value_duplicate_pair` лежит аддитивно в
  `apps/orchestrator/value_duplicate.py`, тело гейта не изменено и предикат не вызывает (тест
  проверяет это по исходнику) — поведение гейта закреплено прежними тестами побайтово. Ловушки:
  (1) якорь — более РАННЯЯ запись по `claims.created_at` (при равных датах — меньший `id`),
  никогда не «более сильная метка»: на карте `c3d5cd03` якорь — relied со «Подтверждено слабо»,
  а свёрнутая запись несёт «Опубликовано производителем»; витрина не выбирает, чья оценка
  представляет факт; (2) свёртка обязана читать гейтовый `statement_values` (диапазоны!), а не
  витринный `_value_occurrences` (см. предыдущую ловушку, пункт 4); (3) факты свёртки date-aware
  (`as_of` DATE → год), а пул оценок `_estimate_record_of` по-прежнему требует
  `isinstance(datetime)` и в проде даёт `as_of_year=None` — прежнее расхождение, пул не менялся;
  (4) свёрнутая запись убирается из списков карточки, но обязана оставаться в `answer_claim_count`
  и в отношениях итога — иначе итог станет «Ответ не записан» (ложью); зеркальная строка
  `other_record` подавляется только у якоря этой пары, кандидаты пула (запись не на карте)
  свёртке не поддаются.

- Модель не видела ни схем инструментов, ни своего бюджета (T7.76). `model_tools_schema` (полные схемы
  аргументов из реестра) до этой задачи **использовали только тесты**: в контекст шага исследоватора уходил
  один список имён инструментов, а хостовый текст протокола перечислял поля кураторского конверта
  (`claim_type`, `as_of`, `scope`, `dependencies`, `search_statements`, `evidence_links`) так, что читались
  как аргументы инструмента. Отсюда стендовые отказы: `question.create` с `search_statements`
  («argument ('search_statements',): Extra inputs are not permitted»), раньше — `memory.search` с лишним
  `limit` и три отказа `artifact.create`; **отклонённое действие тоже стоит один шаг**, и на 10 шагах такие
  повторы съедали половину бюджета, а лимит `session_limits.max_explorer_steps` модели вообще не
  сообщался. Правка — аддитивная: `apps/orchestrator/tool_context.py` рендерит схемы из реестра
  (`get_tool(name).args_model.model_json_schema()`, тот же источник истины, что шлюз; копировать схемы в
  текст нельзя), блок бюджета шага и отметка повторного чтения адреса. Ловушки самой правки: потолок
  (`TOOL_SCHEMAS_CHAR_LIMIT`) применяется к склеенным строкам инструментов и снимает **целые строки** —
  обрезанная посередине схема уже не схема; надбавку обязано сопровождать увеличение
  `EXPLORER_CONTEXT_BUDGET` (= `RESEARCH_CONTEXT_BUDGET + 8_000 + TOOL_CONTEXT_ADDENDA_CHARS`), потому что
  контекст-пак режется по свежести (T7.10) и без роста тихо выбрасывал бы наблюдения поиска. Видимость —
  не ослабление: `extra="forbid"`, `policy_engine.evaluate` и `tool_schema_hash(allowed_tools)` не тронуты
  (текст контекста в хеш схем не входит), новый «охранник» поверх реестра не добавлялся.
- Тестовые ловушки двустороннего поиска (T7.76): (1) фикстура «официальная сторона» обязана ставить
  первоисточник на **home host словаря атрибуции** (`rosstat.gov.ru`), иначе пересказ склеивается с заново
  созданным якорем и вторая группа независимости появляется сама — тест был бы зелёным при дефекте
  (`rosstat.example` именно так и вела себя); (2) отметка повтора адреса попадает в контекст **следующего**
  шага: проверять её нужно на `prompts[3]`, а отсутствие — на `prompts[:3]`; (3) имя инструмента живёт в
  payload'е `action_started`, а `action_completed` несёт только `{action_id, ok, error, data}` — считать
  выполненные действия надо связкой по `action_id`; (4) бейдж надёжности — у строки утверждения
  (`card["claims"][i]["reliability"]`), а не в `card["result"]`.
- Семантика повторного вызова закреплена тестами и «по вкусу» не правится (T7.76): гейт
  `TOOL_REPEAT_DENY_LIMIT = 2` считает **буквально** совпадающие пары (tool, аргументы) — повтор с другой
  формулировкой аргументов ему не повтор; поведение второго `research.fetch` того же URL закрепляет
  `tests/scenario/test_research_provenance.py::test_repeated_tool_call_is_denied_after_limit`. Поэтому вторая
  сторона двусторонней проверки — ДРУГОЙ адрес и ДРУГОЙ запрос, а не второй заход на ту же страницу: хост это
  объясняет отметкой, а не новым отказом. Канонический ключ адреса (`fetch_url_key`) используется только
  отметкой; сделать его жёстким гейтом — отдельная задача (кандидат вместе с лимитами fetch, T7.72).

- Типографическая слепота детектора и ловушка фикстур (T7.77): живые русские страницы набраны неразрывными
  пробелами (NBSP U+00A0 — сберсибовское «По\xa0данным Росстата», узкий U+202F), софт-гифеном U+00AD и
  ZW-символами; шаблоны `ATTRIBUTION_TEMPLATES` требовали ровно одного ASCII-пробела — вся страница
  пересказа осталась `no_value_attribution`, а утверждение получило E3 с ложной формулировкой. С v2
  (`host-source-attribution-v2`) типографика нормализуется над **копией** текста на входе детектора:
  хранимые артефакты и их хеши не меняются, `MAX_SCAN_CHARS` считается по копии, `basis_fragment` — из
  копии (невидимые символы видны оператору как пробелы). Одинарный `\n` теперь мягкая граница (фрагменты
  шире) — окно 120, вето `OWN_ASSESSMENT` и отказ при двух первоисточниках не ослаблены. Ловушка тестов:
  фикстура дефекта обязана содержать Unicode прямо в литерале (`"По\xa0данным …"`); если редактор/копипаст
  заменит NBSP на обычный пробел, фикстура станет зелёной при сломанном детекторе. Переатрибуция прошлых
  решений — команда `research-reattribute` (`python -m hostctl.cli research-reattribute --since`; её идемпотентность закреплена
  `tests/scenario/test_research_reattribute.py`): окно — журнал `research_fetch_completed` с
  `payload->>'attribution_method'='host-source-attribution-v1'`, помечаются только непомеченные строки,
  пересчёт — каскад `apply_source_graph_change` + рабочий переоценки (прямых UPDATE нет).
- Производность уровня значения и её носитель (T7.78, ADR-0029): решение «чей пересказ читает ЭТО
  утверждение» живёт на улике — `evidence.scope.value_attribution`. Ключ в конверт staging-операции `evidence`
  кладёт хост (`apps/orchestrator/orchestrator.py::_value_attribution` :2127, вызов из `_curator` :2411–2438),
  в `evidence.scope` его переносит commit boundary (`packages/memory/service.py:917–944`). Ловушки правки:
  (1) перескопирование scope по T7.17 (`service.py:998`) обязано нести этот ключ, иначе следующий коммит того
  же утверждения тихо сотрёт решение — носитель `packages/memory/scope.py::carry_value_attribution`, факт
  закрепления закреплён тестом повторного коммита; (2) дедуп-повтор той же улики (`identity_hash` решения не
  включает) дописывает решение к существующей строке, а не плодит вторую; (3) загрузчик снимка меняет только
  ВХОДЫ `group_source_graph` (`packages/memory/source_graph.py:57`, `:148`) — эффективный родитель добавляется
  туда, где страничный указатель отказался; страничный родитель старшего, а у одной улики одного утверждения
  два разных первоисточника — родителей нет вовсе; алгоритм группировки, `TEXT_OVERLAP_THRESHOLD` и PSL-список
  трогать нельзя: это смена шкалы независимости (вариант D); (4) число обязано считаться значением только
  рядом с единицей измерения (`_UNIT_TAIL_CHARS = 8`; «1,2 п.\u00a0п.» — тоже значение), иначе годы 2025/2024
  сойдут за значения и склеят несвязанное; (5) ловушка фикстуры: неоднозначная страница обязана быть длинной
  (навигация + две атрибуции разных первоисточников) и набранной NBSP прямо в литерале, а прочитанный
  первоисточник — на home host словаря (`rosstat.gov.ru`), иначе «родитель» в тесте — заново заведённый якорь
  и тест зелёный при дефекте; независимые сайты — заведомо разные registrable domains (AGENTS §7, T7.75).
- Причины оценок рабочего переоценки (T7.77): reassessment-worker НЕ пишет `CLAIM_ASSESSED` (это язык
  staging-пути, `packages/memory/service.py`); у таблицы `claim_assessments` колонки причин нет вовсе.
  Grade/status/причины рабочей оценки — в payload события `reassessment_job_completed`; тестам читать
  последнее по нему (`ORDER BY occurred_at DESC LIMIT 1`). Хронология по `audit_events.sequence` действует
  только внутри одной сессии (sequence per-session) — кросс-сессийные ORDER BY sequence невалидны.
- TLS research-proxy и инертный `SSL_CERT_FILE` (T7.77): httpcore строит контекст сам
  (`create_default_context()` + certifi, `httpcore/_ssl.py`) и переменные окружения OpenSSL не читает —
  подстановка `SSL_CERT_FILE` на стенде не помогла (`rosstat.gov.ru` → CERTIFICATE_VERIFY_FAILED). Единственный
  штатный способ дополнить доверие egress — `NOEZEMA_RESEARCH_EXTRA_CA_FILE` (модуль `apps/research_proxy/tls.py`):

- Точный якорь окна доказательства (T7.79, ADR-0011 доп.): поиск ведётся по **свёрнутому** тексту
  (пробелы, NBSP U+00A0/U+202F, софт-гифен U+00AD, ZW, BOM), но окно вырезается из **исходного**
  нормализованного текста: позиции возвращает карта `_fold_with_map`. Потеря карты = тихая порча
  фрагмента (из источника исчезает типографика, меняется normalized-вид), а тест на NBSP зелён при такой
  ошибке, если сверённый текст сравнивается сам с собой — фикстура обязана проверять NBSP **внутри
  вырезанного окна**. Год-одиночка якорем не считается (дата есть в навигации каждой страницы), число не
  матчится внутри большего числа («5,6» не цепляет «15,6%»). Порядок сигналов второго окна зафиксирован:
  терминальное окно T7.16 → цитаты исследователя → значения вопроса → общий value-якорь T7.22;
  перестановка (например цифры раньше цитат) возвращает стендовый промах — ранний числовой блок
  перетягивает окно (замеры STATUS.md T7.79 §1).
- Текст модели в окне доказательства — **только поисковый сигнал**: `researcher_quote_terms` принимает
  фразу, лишь если она дословно есть в этом же источнике (1..3 вхождения, потолок 8 цитат, кавычки или
  придаточное от 60 знаков). Репродюсер обязан проверять обе ветки (цитата есть → фраза появляется во
  фрагменте; цитаты нет → фрагмент не меняется и текста модели в нём нет), иначе тест зелёный при дефекте,
  а «дотягивание» выдуманного не заметить. Payload улики и идентичность §14.3 от выбора окна не зависят
  (`test_assertion_text_budget_is_explicit_and_identity_ignores_text`) — новый payload-ключ не требовался.
- Ноль утверждений ≠ «ответ проверен» (T7.79): terminal вопроса `verified` требует claims>0 в
  оркестраторе **и** `applied_claims > 0` на границе финальной транзакции (`packages/domain/services/commit.py`,
  fail-closed по staging-операциям: перепроверка и дедуп-повтор считаются применёнными — T7.74). Проверить
  итог по БД можно только по новому аддитивному ключу `question_state` в payload'е
  `commit_attempt_committed`: в доменных таблицах терминал виден лишь строкой `questions`. Тесты, ждавшие
  `verified` при нуле применённых утверждений (например plan-fallback, где хост отклоняет конверт куратора
  `evidence_link[0]: index 0 out of range`), закрепляли сам дефект — менять такое ожидание можно
  только с обоснованием в STATUS.md и с проверкой, что ветка «есть утверждение → verified» осталась зелёной.
- Тест на упрощённом вопросе скрывал дефект окна (T7.79a): короткий вопрос («публикуется ли точное значение
  5,59%?») меняет плотность терминов так, что терминальное окно само накрывает фразу со значением — промах
  исчезает, и репродюсер зелёный при дефекте. Воспроизведение обязано подавать **полный текст вопроса из
  стенда** и **дословный нормализованный текст страницы** (content-addressed фикстура
  `tests/fixtures/artifacts/21/218e9a1ea…`, её SHA входит в `test_artifact_integrity`). Тот же класс маскировки
  на синтетике: термино-плотный блок, стоящий рядом с ключевой фразой, тоже накрывает её окном — нужен
  нейтральный разрыв (замер: ≥20 предложений), а для HTML-страницы он другой, чем для plain-text, потому что
  `normalize_content` сдвигает offsets.
- Складка `_fold` склеивает ряды цифр (T7.79a): неразрывные пробелы и переводы строк выбрасываются, поэтому
  колонки таблицы «8,0 \n 7,7 \n 6,6 \n 5,6» в свёрнутом тексте выглядят одним непрерывным рядом цифр. Граница
  числа проверяется по соседним символам **исходного** текста на raw-границах из `_fold_with_map`
  (`_numeric_boundary_ok`): собственная ячейка «5,6» принимается, «15,6», «5,64» и «5,60» — нет (слева или справа
  стоит цифра). Проверять границу по свёрнутому тексту — тихий отказ значения, набранного таблицей.
- У точного якоря обязана быть ветка вытеснения (T7.79a): сигнал, найденный в источнике, чьё единственное окно
  пересекается с терминальным, фиксирует своё окно, а освобождённый слот занимает общий value-якорь T7.22;
  прежний отказ по пересечению выбрасывал такой якорь целиком, и слот доставался хронологии или навигации.
  Одновременно держать: значение уже покрыто терминальным окном → вытеснения нет
  (`test_value_already_inside_the_term_window_is_not_duplicated`); сигналов нет → прежнее поведение T7.22 без
  изменений (`test_overlap_case_without_signals_loses_the_value`); окон ≤ 2 и каждое ≤ бюджета
  (`test_real_cbr_page_displacement_keeps_the_window_count_and_budget`). Классы точных сигналов: цитата →
  десятичные значения (специфичное раньше: «5,59» до «5,6») → даты д.м.гггг; даты опущены ниже значений по той
  же причине, по которой год-одиночка значением не считается (дата есть в навигации почти каждой страницы).
  `question_value_terms` сохраняет порядок упоминания: сортировка — свойство выбора окна, а не данных наблюдения.
- Дополнение к пункту про локальные reasoning-модели (T7.80, ADR-0030): **у halogen-flash-next комната ответа
  фиксирована** — рассуждение закрывается признаком `reasoning_closed_by="answer_room"`
  (`usage.completion_tokens_details.reasoning_closed_by`) примерно за ~1000 токенов до потолка, поэтому
  подъём потолка ответа (`model.max_output_tokens`) обрезку длинного структурированного JSON не лечит:
  срез лишь переезжает. Замер (сессия `1d0886fa`, .92): три ответа куратора
  ровно по 8192 completion tokens, «Unterminated string … char 3350». Лечит другое: `reasoning_effort: "none"`
  (halogen) и `chat_template_kwargs {"enable_thinking": false}` (llama.cpp Qwen3.x) дают `reasoning_tokens = 0`
  и валидный JSON за доли секунды; `reasoning_effort: "low"` и `thinking_budget` движок **игнорирует** — проверять
  ключ надо одним запросом до активации профиля, а не подбором в проде.
- Повтор идентичного запроса при температуре 0 бессмыслен (T7.80, ADR-0030): сервер отвечает идентично, поэтому
  прежний цикл «три попытки одной схемы» при обрезке тратил ~450 с и три слота движка на три копии одного
  оборванного JSON. Повтор обязан менять сам запрос (выключенное рассуждение), иначе это не ретрай, а повторение
  отказа; менять температуру «чтобы получилась другая длина» нельзя — ломает сравнивость замеров ADR-0011 §7.
  Обрезка (`finish_reason=length` либо упор в `max_output_tokens`) — отдельный исход `LLMTruncatedResponseError`,
  а не схемная осечка: обрезанный документ отказывается, даже если он чудом оказался синтаксически целым, и каждая unusable-попытка
  обязана оставить строку `model_runs` (`output_schema_valid=false`) — иначе «почему куратор молчит» читается
  только из дампа HTTP.

- Улики `source_assertion` реселектируются после исследования (T7.82(а), ADR-0011 §12): окно выбрано при

  по ФИНАЛЬНОЙ rationale — тесты, asserting `payload["assertion_text"]`, обязаны закладывать сигнал

  промахнувшееся окно; без единого точного якоря фрагмент остаётся оконным как при fetch. Правка одна —
  `payload["assertion_text"]`; identity/дедуп улики (§14.3) не тронуты, на staging-операции реселекция не влияет.
- Опора ответа на прежнее знание (T7.82(б), ADR-0032): `relied_claim_ids` разрешаются хостом ТОЛЬКО по строкам
  контекст-пака `[c:<uuid>]`; неразрешимый id — честный отказ в payload того же `claim_created`

- Дополнение опоры из финального ответа (T7.115, ADR-0032 §8): хост добавляет в `relied_claim_ids` id ссылок `c:<полный uuid>` / `c:<hex-префикс от 8>` из public_rationale шага `complete` — целиком сохранённой в памяти сессии (`ctx.final_answer_rationale`, аудит-обрезок [:500] и оконный сигнал не пригодны, в БД ничего не пишется); разрешает их тем же разрешителем и по тому же паку (`resolve_claim_reference` + `_pack_claim_ids`): неоднозначный префикс — отказ `answer[k]:`, а не догадка; промежуточные шаги не берутся; id операции этой сессии (перепроверка/склейка, включая value-dup-конверсии) не дублируется; приоритет за куратором, потолок `RELIED_CLAIMS_LIMIT` общий. Ключ `relied_from_explorer` пишется только непустым — сессии без ссылок в ответе байт в байт прежние (пинится и «ссылка только в промежуточном шаге»). При целом отказе предложения (четыре гейта T7.105) `CLAIM_CREATED` не пишется вовсе — опора не записывается (поведение не изменено, документировано). Тесты: `tests/scenario/test_relied_from_answer_t7115.py`, `tests/unit/test_relied_from_answer_t7115.py`.

- Дубль по значению и гейт кураторского предложения (T7.83, ADR-0033): byte-exact дедуп T7.9 слеп к
  перефразе — новый claim с тем же `claim_type`, равным НЕПУСТЫМ множеством десятичных значений и
  покрытым периодом он не ловится. Значение = maximal-последование `5,59`-подобных токенов; границы числа
  зеркалят `_numeric_boundary_ok` (ADR-0011): `5,6` ≠ `5,59`, «105,59» — одно число и никогда вхождение
  «5,59», целые без разделителя и годы значениями не считаются; неразбираемый токен — молчание про всю
  формулировку. Период: годы операции (текст + `as_of`) непустые и ⊆ годов кандидата (текст + `as_of`).
  Гейт в `_curator` после T7.34-гейта перепроверки и разрешения relied-id, до стейджинга; кандидаты — id
  контекст-пака ∩ головы оценки снапшота сессии; операции с явным `existing_claim_id` не трогает никогда.
  Ровно один строгий кандидат и все связи `supports` → staged-копия получает `existing_claim_id` (оценка
  монотонна, якорь хранит reverify.py); кандидатов ≥2 / есть counters / нет supports / кандидатов нет —
  операция остаётся как предложена. Новых enum/подписей/миграций нет: решение — ключ `value_duplicates` в
  payload уже существующего `claim_created`, только при непустом списке (тест равенства наборов ключей);
  массив `claims` аудит-события НЕ переписывается (`existing_claim_id: null` на месте, подменённый id живёт
  только в staging-операции). Уже записанные пары задним числом не склеиваются: знание не удаляется, а
  фиктивный `claim-dispute` ради косметики подделал бы оценку (STATUS.md T7.83 п.7). Тесты сначала красные:
  unit — отсутствующий импорт чистой функции, сценарий — второй claim с тем же значением на карточке.
- **Значение ≠ показатель (T7.83a, ADR-0033 §7):** равные `claim_type` + множество значений + период НЕ
  делают два утверждения одним фактом — «13,7%» инфляционных ожиданий гейт T7.83 склеил с «13,7%» средней
  ключевой ставки, то есть пристегнул улику чужого показателя к чужому утверждению (и поднял бы его оценку).
  Склейка теперь требует обоих условий: кандидат объявлен куратором в `relied_claim_ids` (хост не решает за
  модель, какой из видимых claim'ов она имела в виду; счёт «ровно один кандидат» берётся ПОСЛЕ этого фильтра —
  иначе неопорный совпаденец создавал бы ложную неоднозначность), и это тот же показатель. Метки показателя
  (`SCOPE_METRIC_KEYS` = metric/indicator/показатель/объект) приоритетнее формулировок: есть у обеих сторон →
  обязаны совпасть после нормализации; у кандидата метка читается из `assessed_scope` текущей головы снапшота —
  колонки `scope` на таблице `claims` нет вовсе (`ORMClaim`), а host-scope-v1 (`packages/memory/scope.py`) метки
  показателя не несёт, поэтому на свежих стендовых claims решает словарь слов. Ловушки словаря: `_STOP_WORDS`
  сравниваются **только точно** (префикс «и» убил бы «инфляцию», «в» — «вклады»), префиксные основы
  `_STOP_STEMS` сравниваются префиксом по цельным корням служебных слов (кратчайшая — «год», она же
  снимает и «город…»: город — не показатель),
  месяцы отсекаются как маркеры периода (`_MONTH_PREFIXES`); основа слова — **префикс** фиксированной длины
  `INDICATOR_STEM_LEN = 5` (суффикс в русском меняется сильнее начала, а длиннее 5 — разные показатели сливаются);
  отношение пересечения к объединению сравнивается точной дробью (`fractions.Fraction`, без float), порог
  `INDICATOR_OVERLAP_MIN = Fraction(3, 5)` — нижняя граница реальной пары фикстуры .92 (3/5) над ближайшим
  ложным кандидатом («ставка по вкладам» ↔ «ключевая ставка», 1/2). Территория — часть имени показателя:
  `_TERRITORY_GROUPS` замкнут (12 групп), конфликт засчитывается только если территории названы **обеими**
  сторонами, поэтому неполнота словаря не может создать ложную склейку; без словаря территорий «наблюдаемая
  инфляция России» ↔ «…Беларуси» дают ровно 3/5 — одного порога не хватило бы. Типографика та же, что у
  атрибуции T7.77: NBSP U+00A0 и узкий U+202F → обычный пробел, софт-гифен U+00AD убирается, NFKC, ё→е; без
  этого `«декабрь\xa02025»` даёт выброшенное слово и перекрытия не хватает. В любом сомнении — `kept`: лишний
  дубль на карточке дешевле чужой улики у утверждения.
- **Одно слово разделяет показатели лучше любого порога (T7.96, ADR-0033 §10).** Один опрос инФОМ даёт два
  показателя: «наблюдаемая населением инфляция» (насколько цены УЖЕ выросли) и «инфляционные ожидания населения»
  (какими их ждут на следующие 12 месяцев). Формулировки различаются одним словом при остальной идентичной
  лексике, поэтому порог тут бессилен: дефектная пара `7c8c9afe…` ↔ `cc75e97f…` даёт 3/4, ровно столько же даёт
  законная пара «тот же показатель, другой месяц» (`391c4388…` ↔ `7c8c9afe…`, 3/4), а синтетика с одним и тем же
  значением («Наблюдаемая населением инфляция … 14,5%» против «Инфляционные ожидания населения … 14,5%») — ровно 3/5. Поднять порог выше 3/4 значит
  разорвать законную пару; опустить — оставить дефект. Решает третий замкнутый словарь различителя,
  `_INDICATOR_QUALIFIER_GROUPS` (`apps/orchestrator/value_duplicate.py:221`: наблюдаем*/воспринимаем* против
  ожидани*/ожидаем*/ожидающ*) по образцу территорий: форма та же (совпадение префиксом; конфликт только когда
  уточнитель назван **обеими** сторонами и группы не пересекаются), ветка отказа идёт после территорий и до
  подсчёта перекрытия (:369–385), поэтому в причине сначала территория, потом уточнитель (пин тестом). Такое
  вето способно только **отменять** склейку: оно не входит ни в числитель, ни в знаменатель overlap и возвращает
  исключительно `matched=False`; замер всех 105 пар 15 подлинных формулировок дампа — было 6 склеек, стало 5,
  новых нет (таблица в STATUS.md T7.96, она же закреплена тестом).
- **Слова атрибуции из словаря показателя исключать нельзя (замер T7.96, ADR-0033 §10.4).** Казалось, что
  «опрос», «инФОМ», «ООО» и названия организаций надувают пересечение. Замер трёх вариантов исключения на всех
  105 парах: убрать опрос/инфом/ооо — дефект не чинится (перекрытие дефектной пары поднимается с 3/4 до ровно
  3/5, то есть пара остаётся склейкой), но при этом `9266248e…` ↔ `c6729d4c…` (официальный ИПЦ 5,59% против
  прогноза ЦБ 6,0–7,0%) растёт 1/3 → 2/3, а вариант с «медиа/офици/факти» поднимает `2f456e85…` ↔ `7cc2b578…`
  1/2 → 3/5: правило начинает называть один показатель у записей, которые к нему отношения не имеют, то есть
  **добавляет** склейки — направление ошибки, запрещённое в гейте дублей. Классы, которые в словарь уточнителей
  сознательно НЕ внесены: месяцы/«год»/«с начала года» (это период — правило периода и `_MONTH_PREFIXES`),
  «медианная/средняя» (агрегация того же измерения), «базовая» против общего ИПЦ (расходятся только объявленными
  метками, §7.2(а)), прогноз и ожидания как **роль значения** (`value_roles`, закрытые `_EXPECTATION_FORMS` —
  T7.88b/T7.94; расширять их без замера живых формулировок нельзя). Форма «наблюдаем*» покрывала
  «наблюдаемая/наблюдаемой/наблюдаемые», но не «наблюдает»: этот предел закрыт T7.96a после замера всех
  пар корпуса — группа уточнителей расширена формами `наблюда`/`ощуща` и словом `оцен` (ADR-0033 §11.4),
  причём именно двусторонней формой правила (асимметричное вето «оценка против ожиданий» ломало 21
  законную склейку). Неполнота словарей по-прежнему даёт только пропуск отказа, никогда — ложный отказ.
  Витрину правка не трогает (`apps/web/estimates.py` идентичен): отказ по уточнителям при
  overlap ≥ 3/5 выносит кандидата из обеих веток отбора строк — молчание плюс честная строка отсутствия (та же
  форма, что у отказа по территориям), а при меньшем перекрытии остаётся нейтральная «Связанная запись».
- **Тот же опрос различается ещё двумя осями: чьи показания названы и какой горизонт назван словами
  (T7.96a, ADR-0033 §11).** Пробы приёмки T7.96 нашли на `c221369` ещё три ложные склейки того же класса:
  «ожидания населения **на годовом горизонте**» 14,2% ↔ «… **на 5 лет вперёд**» 10,7% (2/3), «ожидания
  **населения**» 14,2% ↔ «ценовые ожидания **предприятий**» 7,0% (3/5 — ровно порог) и «годовая инфляция
  **по оценке** населения» / «население **наблюдает** годовую инфляцию» 15,1% ↔ ожидания 14,2% (6/7 и 2/3).
  Добавлены два замкнутых словаря той же двусторонней формы: `_INDICATOR_RESPONDENT_GROUPS`

  «год» и «месяц» остаются служебными словами `_STOP_STEMS` и в словарь показателя не возвращаются. Замер

  ожиданий» (отказ при различителе, названном только с одной стороны) измерено и отвергнуто: оно ломает

- **Проверка, зависящая от ВИДА операции, обязана идти после того, как этот вид окончательно определён

  проверки операция ещё выглядела как «новый temporal_fact без даты» и красила отказом всё предложение

  после разрешения перепроверок, relied-id и обоих гейтов дублей (после T7.85 — `orchestrator.py:2927`). Ловушки самой
  правки: (1) exemption берётся из **`staged_claims`** (списка после подмен гейта), а не из
  `proposal.claims` — иначе операцией, которую гейт дублей сам же и конвертировал в перепроверку, дата
  всё равно потребовалась бы; (2) `validate_against` оставлен и обязан отвечать ровно те же строки в том
  же порядке: разделение сделано общим обходом `_walk` с флагом `check_as_of`, иначе половины тихо
  разъезжаются, а прежние тесты (`tests/unit/test_staging_schema.py`) краснеют на пустом месте; порядок и
  тексты закреплены посимвольно (`tests/unit/test_staging_check_order.py`); (3) политика не изменилась:
  оставшаяся новой `temporal_fact` без даты по-прежнему отклоняет всё предложение тем же текстом причины —
  менять семантику отказов ради удобства нельзя; (4) датless операция в гейте дублей ведёт себя
  консервативно: период строится из лет формулировки, пустой период не склеивает («period [] is not
  covered»), кандидат без даты матчится по текстовым годам (`apps/orchestrator/value_duplicate.py::_period`,
  закреплено `tests/unit/test_value_duplicate_dateless.py`); (5) отказ по дате обязан нести рядом и дайджест
  отклонённого предложения (T7.84(а), ключ `rejected_proposal`), и решения гейта дублей (`value_duplicates`)
  — без них читается не всё, что хост уже решил про эти операции. Пооперационный отказ вместо отказа всем
  предложением — отдельное решение пользователя: анализ и варианты в ADR-0034 (**proposed**, кода нет).

- Живой пересказ: первоисточник назван НЕ у числа (T7.85). Строгое сопоставление «число + шаблон + алиас в
  одном фрагменте» не видит самый частый формат: «…вырос до 13,7%, следует из опроса «инФОМ», опубликованного
  ЦБ. Оценка наблюдаемой населением инфляции … составила 14,5%.» Для этого на уровне улики разрешено окно
  публикации (`apps/research_proxy/value_attribution.py:209–290`): только после честного строгого отказа,
  никогда поверх `own_assessment`/`self_primary`, обязательно с маркером публикации и ровно одним названным
  первоисточником реестра. Ловушки этой правки: (1) **«инФОМ» нельзя добавлять в `PRIMARY_SOURCES`** — опрос
  заказан и опубликован Банком России, и своя страница ЦБ (`self_primary`) плюс пересказы, привязанные к
  инФОМ, дали бы две группы независимости там, где одно исследование (ложная независимость из структуры
  словаря); текст, называющий только «инФОМ», обязан оставаться отказом. (2) Публикационных шаблонов в
  **страничном** словаре нет намеренно: иначе целая страница kommersant стала бы пересказом ЦБ, хотя её собственные
  числа таковыми не являются; расширение разрешено только поуровнево. (3) Новые страничные шаблоны
  «сообщил*», «сообщени*» ловят и обвязку страницы: `interfax_1068021_a` из-за соседства меню («Банк России») с
  блоком «Росстат сообщил… 1,26 %» стала `ambiguous_primaries` на страничном уровне, хотя по значению 5,59 %
  решение осталось строгим. Это цена консервативности, а не дефект: лечить её сужением окна (< 120) или
  выкидыванием фрагментов нельзя — это порог группировки. (4) `research-reattribute --evidence-level` теперь
  пересматривает и уже записанные улики (по номеру метода в записи); маркер схемы
  `VALUE_ATTRIBUTION_SCHEMA` поднимать нельзя — прежние записи должны читаться, их пересматривает метод;
  коррекции оператора (`source_graph_corrections`, актор `operator:*`) неприкосновенны, отказ свежего метода
  сохраняет прежнюю запись, а записанный родитель переиспользуется, пока первоисточник тот же (иначе на стенде
  появился бы второй якорь Росстата рядом с `33912509…`). (5) Побайтовый дубль при другом `claim_type`
  (`find_identical_statement_duplicates`, `apps/orchestrator/value_duplicate.py:429`) подменяет тип операции
  типом якоря **в двух местах сразу** — `reverify_anchor_types` и `claims_for_validation[i]["claim_type"]`
  (`orchestrator.py:2888–2913`); если подменить только первое, предпроверка дат T7.84 снова отвергнет всё
  предложение как «новый temporal_fact без as_of», и ловушка T7.73 вернётся с другой стороны. relied-фильтр
  T7.83a для этого случая не нужен (при побайтовом равенстве спор о том, какое утверждение имела в виду
  модель, исчезает), но числовой гейт остаётся relyed-зависимым и ослаблению не подлежит.
- **Окно публикации не видит смены источника внутри окна (T7.85a, найдено на приёмке T7.85; продолжение —
  T7.85b, найдено на приёмке T7.85a).** Пока окно содержит маркер публикации и ровно один первоисточник
  словаря, оно приклеивало число к этому первоисточнику даже тогда, когда между фразой атрибуции и числом
  стоит чужая оценка: «…опубликовал отчёт Росстат … Аналитики Сбербанка ожидают инфляцию 6,3%» решалось как
  `derivative → Росстат`. С v3 (`host-value-attribution-v3`) внутри оконного режима действует вето «другого
  источника числа» (`_other_source_sign`/`_veto_zones` в `apps/research_proxy/value_attribution.py`): от конца
  каждой фразы атрибуции, закончившейся до числа, до конца предложения с числом запрещены актёры-оценщики (в
  т.ч. банки без границы слова — «Сбербанка»), конечные глагольные формы оценки/ожидания и обороты «по
  оценке/по расчётам/по мнению», названия в кавычках вне словаря, «опрос/исследование» с чужим заказчиком;
  алиасы словаря перед проверкой замазываются, поэтому «Банк России» не стреляет как банк-актор. Ловушки самой
  правки: (1) голое существительное «оценка» маркером НЕ является — в kommersant-форме «Оценка текущих темпов
  роста цен … осталась на уровне 14,5%» это имя показателя, и строка обязана оставаться пересказом ЦБ (тест);
  то же с «ожидаемой инфляцией»; (2) вето живёт только внутри `_publication_decision` — трогать строгий
  pairing нельзя; (3) вето умеет лишь снимать кандидатов: разночтение окон (`ambiguous_primaries`) проверяется
  раньше и остаётся отказом даже если один из кандидатов затронут вето, а снятие единственного кандидата даёт
  честный отказ («сомнение — не приписывать»); (4) ложное вето («независимую оценку объявили пересказом») —
  риск сознательный и описан в ADR-0029 (дополнение T7.85a): направление ошибки безопасное, но завышенную
  независимость такой пропуск лечит только вручную/переатрибуцией; (5) номера методов: пины тестов поднимаются
  на каждом изменении поведения (v2→v3→v4), пересмотр прежних записей опирается ровно на несовпадение метки.

  15,2%» решалось как `derivative → Банк России`: кавычек нет, ВЦИОМ/ФОМ/ЦСР — не «компания» и не «центр»,

  Левада-Центр вне словаря — это и есть механизм отказа). (4) Глагол сам по себе не признак: публикация

  «Банк России зафиксировал оценку…» пересказом: замазанное имя оставляет пробелы длиной с имя, и связки нет.
  Ослаблять соседство нельзя: оно дало бы ложные признаки на именах словаря и обычных словах. (5) Имена белого
  списка не считаются субъектом глагола («ИПЦ зафиксировал рост» — не действующее лицо). (6) Принятые ложные

  переатрибуцией/коррекцией оператора (ADR-0031). (7) v4 поднимает метку, но НЕ схему
  (`VALUE_ATTRIBUTION_SCHEMA` остаётся `host-value-attribution-v1`): переатрибуция тем же предикатом пересматривает
  записи эпохи v2 И v3 (тест `test_records_tagged_v2_and_v3_methods_are_reconsidered_by_current_version`), и это
  единственный способ снять последствия ложного вето задним числом.
- **Язык маркеров режима обязан быть подмножеством языка его собственной охраны (T7.85c, найдено на

(1) Вето собственной оценки читает копию скан-текста, из которой сохранением длины вырезаны фразы ЗАКРЫТОГО списка `SITE_DISCLAIMER_PHRASES` (шаблонные плашки площадок). (2) Третий pairing-режим `bibliography_known_producer`: страница назвала строку-список из закрытого маркера («Источники:» …), в ней стоит производитель X из словаря, значение утверждения измерено на странице, а ДРУГАЯ улика того же утверждения уже записала X строгим режимом или режимом публикации — запись пишется той же формой, что у строгого режима. - **`docker inspect` сразу после kill может врать: «контейнер ещё работает» (T7.91).** Убийство контейнера

  поэтому не доказательство: убитый контейнер превращался в «чистую» ошибку `exit code 137` вместо

  промеров: непрерывный быстрый поллинг docker API во
  время всего окна сам грузит dockerd и завышает измеренное окно — поллинг надо включать только после возврата
  exec-клиента (первая версия промера давала 30–54 мс и ложную картину).

- **Отказ движка (`SandboxError`) в брокере тоже не доказывает, что контейнер жив (T7.92).** Ветка
  `except SandboxError` для `shell.execute`/`python.execute` раньше делала ОДНУ пробу `is_running` и на ответе
  «жив» ставила `transient=True`; теперь там тот же ограниченный второй взгляд (`_await_container_death`, те же
  `CONTAINER_DEATH_RECHECK_SECONDS = 1,0 с` / `…_INTERVAL = 0,1 с`, новых констант нет). Инвариант не изменился:
  unknown — только когда движок САМ ответил «не запущен»; если `is_running` бросает — без ожидания, прежний
  `transient=True`; `SandboxHealthError` (`container engine not found`) окна не получает вообще: движком нельзя
  воспользоваться, команда не запускалась, и перепроверка была бы повтором отказавшей команды. Живой контейнер
  до конца окна → прежний transient: ложных unknown правка создать не может. Перепроверка остаётся только для
  контейнерных инструментов (`question.create`/`workspace.*` опросов не делают). Соседняя честная деталь пути,
  важная при обсуждении «таймаута движка»: в `packages/sandbox/runtime.py::_run` потолок охраняет только spawn
  CLI, а `proc.communicate()` вне `asyncio.wait_for` (промер: движок `sleep 3` при потолке 0,5 с вернулся через
  3,003 с без `SandboxError`) — зависший docker CLI даёт неограниченное ожидание, а не классифицированный отказ;
  bounded ceiling и пересмотр `transient` для движковых отказов — отдельные задачи (решение пользователя).
  Задача закрыта в T7.93: потолок на весь вызов введён (см. следующий пункт); пересмотр `transient` — остаётся отдельной задачей.

- **`asyncio.wait_for(create_subprocess_exec)` ограничивает только запуск процесса, а не его работу (T7.92/T7.93).** В `packages/sandbox/runtime.py::_run` потолок стоял на одном await запуска CLI: уже запущенный docker/podman-клиент висел сколько угодно — `proc.communicate()` был вне `wait_for`. Промер (движок `sleep 3` при потолке 0,5 с): возврат rc=0 через 3,003 с без `SandboxError`; зависший `docker exec`/`inspect`/`rm -f` (подвис dockerd, сеть) подвешивал сессию узла навсегда — ни unknown, ни transient, и потолки 15/30/60/+15 с в вызовах фактически не срабатывали. Закрыто в T7.93: один потолок оборачивает spawn и ожидание завершения; по истечении CLI-процесс убивается и дожидается его пожатие (`_kill_and_reap`, `ProcessLookupError` подавлен — не остаётся ни сирот, ни зомби), затем поднимается тот же `SandboxError("engine command timed out: ...")` — классификация брокера (T7.91/T7.92) без изменений, значения таймаутов вызовов тоже. Не путать host-потолок с внутренним лимитом команды: убийство клиента `docker exec` НЕ гарантирует остановку процесса в контейнере — там главный охранник `timeout -k 5 N` (exec_command). - **`git checkout -- <файл>` после подмены незакоммиченного файла стирает правку (T7.91).** `git checkout --`
  возвращает версию ИЗ ИНДЕКСА/HEAD, а не «ту, что была до подмены»: если исправление ещё не закоммичено, а файл
  временно подменён на старую ревизию для проверки красноты, checkout уничтожает фикс (так в первой,
  остановленной попытке T7.91 и было потеряно исправление broker.py). Безопасный протокол: `cp <файл>
  <резерв>.new` → `git show <старый-коммит>:<файл> > <файл>` → прогон тестов → `cp <резерв>.new <файл>` (возврат
  ИЗ КОПИИ) → `diff` копия↔файл обязан быть пустым. `git checkout --` допустим только ПОСЛЕ коммита исправления.
  Вторая половина той же hygiene: при ручных циклах «прогнать один тест N раз» проверять, что путь действительно
  дошёл до pytest (в collect-only/первой строке вывода должно быть ровно N выбранных тестов) — кавычки в
  `xargs bash -c` уже превращали «один тест ×6» в шесть полных прогонов.

- **Отмена `asyncio.wait_for` не убивает подпроцесс и НЕ проходит веткой `TimeoutError` (T7.95).** Потолок T7.93 спасал только от истечения: внешняя отмена (от дренажа остановки веба, `apps/web/api.py`, 20 с) отменяет внутреннюю корутину с `proc.communicate()` и возвращает управление за 0,000 с — `except TimeoutError` не выполняется никогда, `proc.returncode is None`, а запущенный docker/podman-клиент остаётся живым: замер на `6ee80c5` — состояние «S (alive)» через 1 с после отмены, одинаково на 3.11.15 (`.venv`, прогоны §6) и 3.12.3 (стенд); повторная отмена тоже ничего не убивает, а при закрытии цикла о клиенте вспоминает только `BaseSubprocessTransport.__del__` с «Event loop is closed». Следствия, которые надо помнить при правке sandbox: (1) любую новую ветку ошибок в `_run` следует спрашивать «а где уборка child-процесса» — ответ по умолчанию «её нет»; (2) имя контейнера, выданное движку в `start`, доступно для уборки только через `SandboxHandle`: без него `close_session` при `handle is None` ничего не убирает, поэтому после `create` обязаны убирать и отмену, и истечение потолка — а вот отказ движка (`rc != 0`) остаётся без уборки, потому что удалять не подтверждённое движком имя значит мочь зацепить чужой контейнер с тем же префиксом; (3) уборка обязана быть ограниченной САМА: `_REAP_CEILING_SECONDS = 2,0` и `_CLEANUP_CEILING_SECONDS = 8,0` (сумма 10 с < 20 с дренажа), прежний же потолок `destroy` (30 с) был больше дренажа — именно поэтому обрывался на середине и терял контейнер; значения обычных движковых вызовов (15/30/60/+15 с) от этого не меняются; (4) защита от повторной отмены — отдельная задача + `asyncio.shield` + собственный потолок + done-callback, потребляющий результат (тот же приём, что `apps/orchestrator/node_guard.py::release`), и отмену нельзя превращать в `SandboxError`: брокер её не классифицирует и проглотить не может; (5) `close_session` с T7.95 — единственное исключение из «never raises» (`CancelledError` поднимается наружу из `finally`), но каталог overlay убирается на любом пути. Регрессия: `tests/unit/test_sandbox_cancellation.py` (фейковый движок, зависший глагол спит дольше всех потолков; краснеет на `6ee80c5`).
- **Дополнение к предыдущему пункту (T7.95a): убитый docker-клиент НЕ отменяет операцию в dockerd, а rc=0 `rm -f` ничего не доказывает — уборка действительна только при подтверждении движком (docker 29.8; замеры STATUS.md T7.95a п.2).** Замеренное поведение CLI: `rm -f` с rc=0 и пустым stderr отвечает и по никогда не существовавшему имени, и по уже удалённому, и по ещё незавершённому `docker create` — после чего контейнер «появляется» (замеры: 14–131 мс); отказ rc=1 «removal … is already in progress» означает, что dockerd удаляет САМ (завершает за 22–86 мс) — это не утечка, а состояние «ждать и перепроверять». Поэтому `remove_container_best_effort` после каждого `rm -f` ведёт серию `inspect` ВНУТРИ прежнего потолка 8 с: отсутствие подтверждено, когда имя непрерывно отвечает «no such» окно `_CONFIRM_ABSENT_WINDOW_SECONDS = 1,5` с (≈10 худшей измеренной задержки появления); reappearance после «успешного» rm — ровно один повторный `rm -f`; LEAKED — одна строка на уборку и только по истечении потолка, с различением «контейнер присутствует» / «отсутствие неподтверждено (причина)». Drain-арифметика прежняя: 2+8=10 < 20. Каталог `<work_root>/<session_id>` убирается при любом выходе `start` без хэндла (отмена/поток/отказ движка), исходное исключение побайтово прежнее. Регрессия: те же файлы тестов, 7 новых красных на `d0e27c1`; фейковый движок моделирует существование контейнера и три измеренных поведения — с него нельзя снимать state-модель, проверяя подтверждение.

- **Пооперационный отказ на границе куратора (T7.105, ADR-0034 §8, вариант B).** Проверки, называющие одну
  claim-операцию, снимают только её с прежней причиной дословно; свойства предложения — прежний целый отказ.
  Ловушки: (1) отдельно на уровне операции — ровно строки `claim[i].search_statements[k]`,
  `claim[i]: temporal_fact requires
  as_of`, неразрешимая ссылка перепроверки (включая «якорь без головы») и предпроверка движком правил

  `SessionOutcome.claims_proposed` = предложено, применённое — только в `claim_created.claims_applied`

- **Один раунд исправления при отказе целиком (T7.106, ADR-0034 §9, вариант C поверх B).** Когда хост
  отклоняет ответ куратора ЦЕЛИКОМ (любой из четырёх гейтов после модельного ответа: structural, снятие
  перепроверкой всех операций, as_of, движок правил), ровно ОДИН раз на вызов куратора (= на сессию)

  тем же помощником `_curator_boundary` (до staging — только чтения). Маркеры: событие
  SESSION_STATE_CHANGED с ключом `curator_correction_requested` (причины
  дословно + дайджест ПЕРВОГО ответа, summary «curator proposal returned for one correction round») —

  (3) раунд не расходует шаговый бюджет исследователя (`max_explorer_steps`), второй вызов живёт в фазе

Версии методов: `host-source-attribution-v10`, `host-value-attribution-v15`. Новое правило снятия: сохранённая запись значения с устаревшей меткой, не проходящая публичный гейт `record_pairing_gate_passes` против собственного `basis_fragment` (при свежесобранном решении НЕ derivative), снимается планом «будет снята: значение утверждения отсутствует во фрагменте основания прежней записи» — тот же путь UPDATE скоупа + каскад T7.117, нового AuditEventType нет; усечённое основание, библиографические и «известный производитель упомянут» pairing, операторские коррекции и записи текущего метода сохраняются (инвариант «записи прежних эпох не удаляются никогда» теперь имеет ровно одно именованное исключение — основание записи лжёт, что доказано гейтом).
- Отчёт честности `honesty-report` — только наблюдатель (T7.118, `packages/memory/honesty_report.py`, STATUS T7.118). Модуль читает записанное и никогда не пишет (тест т6 сверяет счётчики восьми таблиц до и после); правки правил/промптов/карточки ради «улучшения отчёта» запрещены самой задачей. Ловушки: (1) отчёт усечает id до первых 8 hex-знаков — в тестах фиксированные uuid обязаны различаться первой hex-группой, иначе словари и матчинги id сливают разные сущности; (2) флаги Ф1–Ф3 — эвристики «требует ручной проверки»: Ф2 — якорное правило (пустое пересечение основ ИЛИ одна общая основа при 3+ значимых), доля пересечения не реализована — она ложит на честных развёрнутых ответах; Ф3 не знает словарь народных имён из `apps/` («Росстат» против полного названия — закрепленное unit-тестом ложное срабатывание); ветка Ф1 «текст группы называет производителя» не реализована (потребовала бы атрибуционных детекторов из `apps/`); (3) зеркала нормализации ворот (`normalize_search_query`, `_prefix_stem`, `content_word_stems`, служебный список) продублированы в модуле и закреплены тестом равным `apps/orchestrator` — смена нормализации ворот требует синхронной правки зеркал отчёта (и наоборот, молча не «подстраивать»); (4) CliRunner-ловушка T7.59 здесь двойная: команда CLI сама поднимает `asyncio.run`, поэтому тесты команды — синхронные, каждый engine свой из scratch-URL; (5) миграций, enum-значений и AuditEventType ради отчёта не добавлять — наблюдателю хватает записанного; `deploy/dev-stand/control-run.sh` (контрольный набор пяти вопросов) агентом никогда не запускается.
- Ф3 отчёта честности (T7.118a): имя производителя считается названным только при совпадении ВСЕХ значимых основ имени в формулировке (падежный двусторонний допуск; значимые — без чисел и без общей основы-якоря страны `росси`, выведенной тем же `_prefix_stem`); имя только из якоря («Россия») сравнивается по полному набору, как прежде. Прежний порядок «хватает одной основы» глушил Ф3: подпись «Банк России» молчала из-за слова «России», присутствующего почти в каждой формулировке (дефект найден на данных стенда). Команда отчёта на dev-стенде — `.venv/bin/python -m hostctl.cli honesty-report …` из каталога репозитория (не `noezemactl`/`hostctl`).

## 8. Гигиена длинных сессий

- После каждого закоммиченного PR: обновить STATUS.md, отметить todo, и только потом начинать
  следующий PR — это естественная точка для сжатия контекста.
- Решение, принятое по ходу работы и не очевидное из кода (почему выбран вариант X), записывать
  в STATUS.md (раздел вехи) или ADR, а не держать только в диалоге.
- Найденный инвариант — закреплять тестом; найденную ловушку окружения — дописывать в §7.
- Отвечать пользователю по-русски; выполнять план без лишних вопросов, но пункты из §4
  «требует решения пользователя» — только после явного подтверждения.
- Новый номер конфигурации = НОВЫЙ файл в `docs/eval/` (config-v13), прежние payload'ы не переписываются
  никогда. Два разных хеша, их путают: хеш ФАЙЛА (байты JSON) и canonical-хеш payload'а
  (`canonical_sha256(json.loads(...))`) — в БД в `config_snapshots.payload_sha256` попадает **canonical**
  (`packages/memory/activation.py:374`), поэтому проверить активный снапшот по хешу файла нельзя;
  `input_budget = min(context_window, backend_context_limit) − max_output_tokens − safety_margin_tokens`
  (связь `context_window == backend_context_limit` нигде не проверяется — менять надо оба).
- Операторский спор утверждения (T7.81, ADR-0031): единственный санкционированный спекой lever оператора над
  независимостью — строка `source_graph_corrections` + существующий каскад `apply_source_graph_change`, а дальше
  оценку считает rules engine. Три подводных камня: (1) **голова самоуничтожается** — прямой перевод головы в
  `pending`/`invalid` без изменения фактов worker вернёт в `current` с прежней оценкой на ближайшем maint-тике
  (60 с на стенде): «снятое руками» знание держится один тик; (2) идемпотентность по естественному ключу
  `(actor, from_source_id, to_source_id, kind, rules_version)` означает, что повтор **тем же актором** — это
  replay (200, `replayed=true`), а отказ «источники уже объединены» возможен только для другого актора: тест
  «второй оператор не может…» обязан звать сервис с другим `actor`, иначе получит зелёный повтор; (3) сравнение
  адреса оператора с `sources.canonical_uri` — **без схемы** (`normalize_uri` приводёт и хост, и порт, и query):
  со схемой в сравнении «тот же источник» превращается в «адреса нет среди источников», то есть честный отказ
  подменяется ложным. Бейдж надёжности при проверке витрины читать у строки списка
  (`/api/v1/knowledge/claims` → `reliability`), а не у голов `claim_detail`: у heads его нет (T7.76).
- Дополнение к предыдущему пункту (T7.114, решение пользователя 2026-10-15 «вариант 1», дополнение ADR-0031 §9):
  кандидатами первоисточника спора, кроме источников улик утверждения, являются производители, уже
  записанные хостом на этих уликах: страничный указатель `sources.parent_source_id` и запись значения
  `evidence.scope.value_attribution.parent_source_id` (любая версия метода — по маркеру формы
  `host-value-attribution-v1`). Пересказ по-прежнему только собственная улика утверждения; «уже
  сгруппированы» для производителя читается из снимка независимости действующей оценки по уликам, которым
  он записан родителем (у самого производителя строк участников нет), ноль или несколько производных
  групп — отказа нет. Группировщик, каскад и rules engine не тронуты. Тесты
  `tests/unit/test_claim_dispute_producers_t7114.py` и `tests/scenario/test_claim_dispute_producers_t7114.py`.
  Разбор: STATUS.md T7.114.

- Приоритет входа группировки и read-only предпросмотр смены групп (T7.117, решение пользователя
  2026-10-15 «вариант 1», дополнение ADR-0029 §22): если по уликам утверждения по записям значения
  записан ровно один эффективный родитель, во вход группировщика идёт он (`grouping_arguments` в
  `packages/memory/source_graph.py`); `sources.parent_source_id` — фолбэк (нет записи или конфликт
  записей — консерватизм T7.78). Группировщик, каскад, rules engine, пороги и версии детекторов не
  тронуты; прежние оценки пересчитываются только явно: `noezemactl independence-preview [--apply]`
  (`packages/memory/independence_preview.py`). Ловушки: (1) «было» в предпросмотре берётся из
  ЗАПИСАННОГО снимка независимости оценки головы, а не из пересчёта старым правилом в памяти — иначе
  повторный предпросмотр после применения никогда не станет пустым (идемпотентность пинится тестом);
  (2) `--apply` = существующий каскад §11.3 + батч `run_reassessment_batch`, новых AuditEventType и
  миграций нет; каскад — надмножество (объединение источников улик перечисленных утверждений, как у
  переатрибуции), повторный `--apply` на пустом предпросмотре — no-op; (3) «стало» оценки — чистый
  `evaluate()` без записей: при отказе правила строка обязана честно сказать «не пересчитана» и
  показать только группы — выдумывать оценку нельзя; (4) записанный родитель становится узлом графа
  даже без указателя, но «родитель-призрак» без строки источника узлом не делается; CliRunner-тесты
  новой команды — по образцу T7.59 (свой engine на операцию, dispose в том же event loop).
  Разбор: STATUS.md T7.117.

- **Подраздел «Независимые оценки» карточки (T7.88, ADR-0035 §11).** Три ловушки самой правки:
  (1) различитель показателя — ОДИН на весь проект (`indicator_check` из `apps/orchestrator/value_duplicate.py`),
  а его словарь основ кураторский и скудный: «Росстат» даёт основу `росст`, «России»/«Росстата» — `росси`,
  «Банка» — `банка` ≠ `банк`. Формулировки кандидатов (и тестовых, и будущих стендовых) обязаны калиброваться
  по тем же основам, что и источник; при объявленных РАЗЛИЧНЫХ метках витрина молчит даже при высокой лексике
  (записанное противоречие не переигрывается), при конфликте территорий запись исключается целиком.
  (2) Производители и группы читаемы только там, где они записаны В ОЦЕНКЕ: факты улик приходят через роль
  `assessment_evidence` (тот же контур, что у подписи T7.87). Прямой посев атрибуции/улики без роли даёт пустые
  `producers`/`groups`, и независимая оценка деградирует до «Другая запись того же показателя» — репродюсеры
  обязаны вписывать роль (иначе тест зелёный при дефекте проводки). Слово «независимая» запрещено строке,
  когда независимость не выведена из групп одного снимка или непересекающихся записанных производителей.
  (3) Цена — ровно один запрос `WITH pool …` на карту с приоритизацией карточных утверждений
  (`ORDER BY (c.id = ANY(...)) DESC`): пул ≤60, кандидаты за пределом не показаны — это documented-молчание,
  а не полнота; потолок бюджета поднят 10→11 одним обоснованным местом, N+1 по утверждениям и кандидатам
  красится тестом.

- **Словарная смежность ≠ доказанное различие показателя (T7.88a, ADR-0035 §12).** Подраздел карточки
  обязан молчать там, где молчит различитель. Пересечение основ в диапазоне `[1/6, 3/5)` — это сигнал
  «показать рядом, но ничего не утверждать», а НЕ вывод о том, что показатель другой: на живом экране
  витрина называла «другим показателем» пересказы той же официальной цифры (`73d52835…`, `c970bc08…`,
  `e2c52955…` — 5,6 % против 5,59 % того же годового ИПЦ), то есть делала ровно тот вывод, который
  ADR-0033 §7 запретил дублирующему гейту. Разрешены только два утверждения: «Запись, вероятно, о том же
  показателе … независимость не установлена.» — и только когда значение записи арифметически совпадает со
  значением карточки или является его округлением (`_rounding_agreement`, `ROUNDING_MAX_PLACE_GAP = 2`,
  одиночное существенное значение, одинаковые единицы); и нейтральная «Связанная запись: … — показатель
  автоматически не сопоставлен». Формулировку «другой показатель» в витрине использовать нельзя нигде:
  различие доказуемо только записанной меткой `assessed_scope.metric`, и там код остаётся молчаливым.
  Симметричная ошибка запрещена так же: вероятный пересказ не имеет права стать «независимой оценкой».
- Ловушки той же правки: (1) честная строка отсутствия обязательна при отсутствии независимой оценки и
  добавляется ПОСЛЕ всех потолков, последней строкой; её отмена соседней «Другой записью того же показателя»
  — прежний дефект (краснеют тесты обоих слоёв); (2) потолок связанных строк `MAX_ADJACENT_ROWS_PER_CLAIM = 3`
  срезает хвост по приоритету «вероятно тот же → прогноз → связанная запись», а остаток сворачивается в
  строку-счётчик без текстов записей; независимые оценки и другие записи того же показателя этим потолком не
  обрезаются — иначе правка прятала бы доказанную связь ради компактности; (3) многозначная запись никогда не
  называется «тем же показателем» (витрина не знает, какое значение относится к карточке), а при объявленных
  метках у обеих сторон строка «вероятно тот же» запрещена даже при идеальном округлении; (4) расширение перечисления `kind` аддитивное:
  код `adjacent_metric` сохранён (переименование значения API — отдельное обоснование), подписи новых значений
  добавляются в `apps/web/labels.py`, полнота берётся тестом из кода подборщика; ни в одной новой строке нет
  утвердительного «проверен/проверено» (T7.65).

- **Слово в формулировке ≠ роль значения (T7.88b, ADR-0035 §13).** Прежний гейт витрины объявлял запись
  прогнозной по одному слову «прогноз»/«предсказание» где угодно в её тексте; на живом экране это читалось как
  ложь: `7cc2b578…` («Фактическая годовая инфляция … (5,59%) оказалась ниже всех прогнозов аналитиков:
  прогноз Банка России — 6,5–7%, Минэкономразвития — 6,8%, консенсус-прогноз ЦБ — 6,6%») — это измерение,
  сопоставленное с чужими прогнозами, а витрина подписывала её «Смежный прогноз, не измерение» против
  `391c4388…` (наблюдаемая инфляция 14,5 %) и прятала в счётчик как прогноз против `9266248e…` (её 5,59 %).
  Роль теперь принадлежит значению: `value_roles` (`apps/web/estimates.py:289`) разбирает формулировку тем же
  сканом и той же каноизацией, что сравнение (`_VALUE_TOKEN_RE`, `_canonical_value` из
  `apps/orchestrator/value_duplicate.py` — файл не меняется), и роль берёт у ближайшего маркера ПЕРЕД значением
  в том же отрезке: основа прогноза (`_FORECAST_STEMS`) или маркер факта (`_REALIZED_STEMS` = «факт*»); маркеров
  нет — реализованное. Утверждение — прогноз только когда `ValueRoles.is_forecast_only` (все существенные
  значения прогнозны), а смешанная запись сравнивается ТОЛЬКО своими реализованными значениями
  (`_comparison_values`). Ловушки этой правки: (1) окно основы `FORECAST_BASIS_WINDOW_CHARS = 60` и второй путь
  «основа в голове отрезка» `FORECAST_HEAD_CHARS = 12` — числа замерены по подлинным формулировкам (в `7cc2b578…`
  маркер факта «Фактическая» стоит в 48 знаках от 5,59 %, а основы прогнозов — в 6, 16 и 44: окно обязано быть
  меньше пути от перечисления до следующего значения и больше самой короткой атрибуции); молча поднять порог —
  значит вернуть дефект; (2) маркер факта — только «факт*»: «составил» и «по итогам» встречаются и у прогнозов
  («Прогноз аналитиков … составил 6,3%», `2d010d53…`), поэтому они маркерами не считаются, а отсутствие
  маркера перед значением означает реализованное; (3) границы отрезка — `. ; ! ?` и перенос строки, двоеточие и запятая
  границами НЕ являются: с запятой перечисление «6,5–7%, 6,8%, 6,6%» потеряло бы свою основу; (4) диапазон
  «6,5–7%» — одно значение (целое «7» после тире не значение), и целые числа по-прежнему значениями не считаются:
  прогноз из «4%» и «5%» не даёт ни одной строки со значением, правка это поведение сохраняет; (5) пустое множество
  сопоставляемых значений — не равенство: `source_values_match` сравнивает только непустые наборы, иначе строка
  сказала бы «значение — совпадает с» без чисел; отношение к показателю при этом остаётся (его вывел различитель
  по меткам) и витрина честно пишет «единицы значений неясны»; (6) направление консерватизма сохранено: формулировка
  «Фактическая годовая инфляция … оказалась ниже прогноза Банка России и составила 5,59%» даёт ближайший маркер
  «прогноза» (26 знаков против 76 у «Фактическая») — измерение будет скрыто как прогноз, а не названо независимым:
  витрина ошибается в сторону «меньше показано», и это сознательно (ADR-0035 §13.6), так же как свёрнутые в
  счётчик записи; (7) изменённые ожидания тестов потолка — следствие новой роли, а не подгонка: число скрытых
  записей (4) и потолок `MAX_ADJACENT_ROWS_PER_CLAIM = 3` остались прежними, ослабла только гарантия §12.3 «видимая

- **Прогноз может быть высказан без слова «прогноз» (T7.94, ADR-0035 §13.7).** Кроме основ «прогн*»/«предсказ*»
  признаками прогноза у значения стали закрытые списки **точных форм**: `_EXPECTATION_FORMS`
  (`apps/web/estimates.py:182`: ожидают/ожидает/ожидается/ожидаем + прошедшие; предполагают/предполагается,
  рассчитывают, допускают и их прошедшие), причастная основа `_EXPECTATION_STEMS` (:195: ожидаемая/ожидаемые,
  предполагаемая) и `_FUTURE_FORMS` (:201: составит/составят, будет/будут, достигнет/достигнут, превысит,
  снизится/замедлится/ускорится/вырастет, окажется, сохранится — единственное и множественное число). Ловушки:
  (1) списки точные, а не стемовые: «составила», «составляет» и «оказалась» оставляют значение реализованным;
  стем схлопнул бы их с «составит»/«окажется» и вернул дефект T7.88b на `7cc2b578…` («…оказалась ниже всех
  прогнозов»), а предыдущий пункт §7 («маркер факта — только „факт*“, „составил“ маркером не считается») остаётся
  верным для прошедшей формы; (2) слово «консенсус» и оборот «по ожиданиям» признаками НЕ стали: знак берётся из
  собственного сказуемого или будущей формы рядом со значением («консенсус … достигнет 5,2%» — прогноз, «консенсус
  аналитиков по инфляции на 2026 год — 5,2%» — запись о состоявшемся значении; «консенсус-прогноз» ловится основой
  «прогн*», потому что `_MARKER_WORD_RE` разбивает дефис); (3) измерение чужих ожиданий — НЕ прогноз:
  `_MEASURED_EXPECTATION_RE` (:219) снимает атрибуцию ожидания там, где оборот называет показания опроса

  состоявшийся ответ респондентов, имя измеряемого показателя (explorer-v9, правило 12), и существительное
  «ожидания» признаком не стало; охрана снимает ТОЛЬКО атрибуцию ожидания — явная основа прогноза и будущее время
  внутри такого оборота остаются признаками («Прогноз по инфляционным ожиданиям населения — 13,7%», «Ожидаемая
  населением инфляция вырастет до 12,4%»), и она никогда не добавляет маркеров факта; отношение записи к показателю
  по-прежнему решает различитель T7.83a, а не эта регулярка; (4) принятая граница: «Окончательная оценка … будет
  опубликована 16 января: она составила 5,59%» даёт роль прогноза (будущее время относится к публикации), ошибка
  направлена в сторону «меньше показано», как вся схема §13.6; морфологического разбора нет, и расширять списки
  без замера живых формулировок нельзя; (5) ни окно `FORECAST_BASIS_WINDOW_CHARS = 60`, ни голова

  признак меняет только роль значения внутри уже выбранной записи; среди десяти подлинных формулировок карты
  `7ceb8047…` ролей не изменилась ни одна (закрыто тестом).
